## 0. The story so far (v1.0 → v1.5: multiprocessing → shm → async)

Three architectural moves, each fixing the bottleneck the previous one exposed:

1. **v1.0 — same process, multithreaded.** `VLLMService` and the pipeline stage ran on the same
   process, talking via direct function calls — no IPC, no problem, but no isolation either.
   This stops making sense the moment StageWeaver enters the picture: a DAG with up to 10 stages
   means up to 10 stages' worth of CPU-bound Python code sharing one process, all fighting over
   the same GIL. Adding the VLM's own request/response bookkeeping into that same process just
   piles more work onto the same GIL — it doesn't matter that `LLM.generate()` itself releases
   the GIL while it runs, because everything *around* the generate call (prompt prep, response
   handling) doesn't.
   **Fix — v1.1: move `VLLMService` to its own process.** Communication becomes explicit: a
   `request_queue`, a `response_queue` per stage, and a stop `Event`, all from `multiprocessing`.
   The stage and the VLM no longer share a GIL.
2. **Problem this exposed: communication latency on heavy payloads.** `mp.Queue.put()`/`.get()`
   pickle the object and copy it across a kernel pipe — cheap for small messages, but a VLM
   prompt carries PIL images (3–12 MB each), and that kernel copy (not pickle CPU time) turned
   out to be the dominant IPC cost, measured at ~1.7 ms/item each way, ×2 directions × batch size,
   all with the GPU idle while it happens (see Problem 1 below for the numbers).
   **Fix — v1.2: shared memory (`shm`).** `request_queue`/`response_queues` now carry only a small
   `int` slot index; the actual payload is pickled directly into a fixed-size slot of one
   `multiprocessing.shared_memory.SharedMemory` block, skipping the kernel copy entirely.
3. **Problem this exposed: one straggler stalls its whole batch.** Neither move above touches the
   inference call itself. `LLM.generate()` is called over a whole batch and returns only when the
   *last* sequence finishes — so if the Nth item in a batch of N is slow or hallucinating, the
   other N−1 already-finished results just sit there, unreturned, and the running batch shrinks
   toward empty with nothing new able to join until the next `generate()` call. This is Problem 4
   below, and it's the one Phases A/A2/shm cannot touch — they only close gaps *between*
   `generate()` calls; this barrier is the `generate()` API itself.
   **Fix — v1.5: `AsyncLLM` continuous batching.** One request added per submission, one async
   generator per request, finished items stream back the instant they complete, and fresh/retry
   work joins the running engine immediately. A slow item now only delays itself, and because the
   stage side became a streaming pump to match (see Phase C), communication and computation are
   truly overlapped rather than merely interleaved. This is where the ~29% throughput jump
   (measured in `examples/chandra_testing/testing_result.txt`, see Phase C.1 below) comes from —
   confirmed by the fact that turning on async alone (shm still off) already captures almost the
   entire win; shm's kernel-copy savings mostly get hidden under it.

The rest of this document is the detailed problem analysis and phase-by-phase design behind step
3 (Phases A, A2, B, C) — steps 1 and 2 above were v1.1/v1.2 and are recorded in `CHANGELOG.md`.

## 1. Problems v1.5 is solving

### Problem 1 — GPU idles during IPC (pickling) around `model.generate()`
In the old multithreaded design (pre-v1.1), `retry_validate` called the VLM service directly —
submit/collect were effectively free. The queue/shm multiprocessing design added real
serialization cost on both sides of the process boundary, and none of it overlaps with
`model.generate()`. Measured (see `examples/shm_testing/results.md`): ~1.7 ms/item pickle into
shm on submit, ~1.7 ms/item unpickle in the worker — ×2 directions × batch_size, all while the
GPU sits idle between consecutive `generate()` calls.

### Problem 2 — Retry batches are tiny
`generate_with_validation()` retries in lock-step rounds: attempt 1 = full batch, attempt 2 =
only the failures (e.g. 5 items), attempt 3 = the still-failing (e.g. 2 items). Each round is a
full `generate()` call on a nearly-empty GPU, and the *next* macro-batch (prompts already
prepared!) waits until every retry round finishes.

### Problem 3 — Phase A's fetch cadence starves the GPU every other iteration
*(Discovered 2026-07-13, after Phase A was implemented — a flaw in the Phase A design itself,
not in the implementation.)* Trace steady state with no failures, `fetch_n = batch_size -
pending_count`:

- It 1: pools empty → fetch B → submit **0**, prep B → pending = B
- It 2: fetch_n = 0 → submit B, prep **0** → pending = 0
- It 3: fetch B → submit **0** (pools were emptied last iteration), prep B → pending = B
- It 4: fetch 0 → submit B, prep 0 → …

The CPU/GPU overlap inside `run_iteration` never engages: iterations alternate GPU-only /
prep-only. With partial failures it oscillates instead of alternating (submit 2 / prep 8, then
submit 8 / prep 2, …) — same disease. The old 3-phase loop overlapped prep(i+1) with GPU(i) by
holding **two** batches' worth of work at once; Phase A's `fetch_n = B - pending` caps total
held work at B, which makes overlap arithmetically impossible. The fetch target must be **2B**
worth of predictor-owned items (pools + in-flight).
Fixed as part of Phase A2 (below) — Phase A2's pipelining cannot engage without it.

> **Implementation correction (2026-07-13).** The design first sketched the fetch size as
> `fetch_n = 2B - pending - in_flight`. Tracing the actual submit-before-prep loop shows that
> subtracting `in_flight` **oscillates** (steady state alternates full / empty submissions again):
> in-flight items are about to become *terminal*, not resubmittable supply, so counting them
> against the pools starves the pools exactly when the in-flight batch drains. The correct,
> traced formula targets the **pools alone**: `fetch_n = 2B - pending` (pending = retry + ready
> pool size). At equilibrium this settles at `pending ≈ B`, `in_flight = B` (so pools + in-flight
> ≈ 2B, the intended target state) with a steady `fetch_n ≈ B` every iteration — full batches, no
> oscillation, and a ~3B simultaneous-slot budget. Implemented in `prediction.run_iteration`.

### Problem 4 — Intra-batch tail: one straggler starves the whole batch
*(Raised 2026-07-13 while designing Phase B. Observed: large-prompt workloads have large tails —
a few items run much longer or hallucinate; small-prompt workloads have small tails. Fixing the
tail is monotone: low-variance batches gain ~nothing but never lose.)*

Inside one `LLM.generate()` call vLLM already does continuous batching — short samples are NOT
slowed by the straggler while decoding; they finish at their own pace and leave the running
batch. The damage is entirely a **call-boundary artifact**, in two forms:

1. **Finished results are held hostage** — `generate()` returns only when the LAST sequence
   finishes, so B−1 completed outputs sit inside the call with their validation / retry
   classification / writer handoff all stalled behind one hallucinating sample.
2. **The GPU drains to near-idle** — as samples finish, the running batch shrinks toward one
   sequence, and nothing new can join mid-call even though batch i+1 is fully staged and
   sitting in the request queue.

Phases A/A2/B cannot touch this: they close the gaps BETWEEN calls; the barrier is the
`LLM.generate()` API itself. This is Phase C's problem. Note the same barrier exists on the
stage side too — `collect()` waits on the full req_id set — which is why Phase C must be
two-sided (see §2 Phase C).

**Mitigation available today, independent of any phase:** a tight `max_tokens` in
`get_sampling_params()` converts a hallucination runaway into a bounded-length output that
fails validation and re-enters the retry pool (which Phase A coalesces cheaply). Caps the worst
case; does nothing for genuine long-output variance.

### Root cause (shared by Problems 1 & 2): lock-step at the macro-batch boundary
Between two consecutive `generate()` calls, ALL of this runs serially with the GPU idle:
worker pickles responses → stage unpickles → stage validates → retry rounds (shrinking batches,
each with its own IPC round-trip) → stage pickles next batch's requests → worker unpickles them.

Batching decisions are currently made in **three places**: `cli_utils.py` (macro-batch via
`fetch_batch`), `retry_validate.py` (shrinking retry rounds), and `vlm_service._worker()`
(drain-up-to-batch_size-or-max_wait). The worker's dynamic batching never gets used because the
stage feeds it in lock-step.

## 2. Agreed design

**Core idea: batching happens in exactly ONE place. The stage side becomes a submission
scheduler with a strict invariant; retries are just items that re-enter the submission flow and
ride along with fresh work.**

Split into two independent phases (they touch disjoint code and can ship separately):

### Phase A — Single batching point + retry carry-over (stage side)
*Touches: `prediction.py`, `cli_utils.py`, `retry_validate.py`. Does NOT touch `vlm_service.py`
or anything across the process boundary.*

`VLMPrediction` maintains two small pools:

- **retry pool** — items that failed validation with attempts remaining.
  Entry = `(path, original prepared prompt, attempt_count, last_error)`.
- **ready pool** — prepared-but-not-yet-submitted fresh prompts (overflow displaced when
  retries took their slots).

**Invariant (write it at the top of the file): every item is in exactly one of
{ready pool, retry pool, in-flight to GPU, terminal}, and in-flight ≤ batch_size.**

Per iteration:
1. **Submit exactly `min(batch_size, len(retry_pool) + len(ready_pool))` items — retries
   first, fresh prompts fill the remainder.** Displaced fresh prompts wait in the ready pool.
2. Collect + validate. Each result becomes: success → returned to cli for writer;
   failed with attempts left → retry pool (with penalty bump + error appended);
   attempts exhausted → returned as failed (state=3).
3. Tell cli how many fresh paths to fetch next:
   `batch_size - len(retry_pool) - len(ready_pool)` (as known at fetch time).

**Why the ready pool exists (the timing lag):** batch i+1 is fetched and its prompts prepared
*while* batch i is still generating — that's the CPU/GPU overlap. Batch i's failure count is
only known after it completes, too late to shrink batch i+1's fetch. So the fetch size can't be
exact; the pools absorb the error. Without the ready pool, applying the shrink one iteration
late would make batch i+1's submission = `failed_i + batch_size` (overshoot).

Effects:
- Exactly `batch_size` items hit vLLM per iteration in steady state, regardless of failures.
- Retries coalesce with the next batch's fresh prompts in the same `generate()` call — the
  tiny-retry-batch problem dissolves with no special machinery.
- In-flight work strictly bounded (no backpressure buildup): ≤ batch_size in GPU + small pools.
- `generate_with_validation()`'s retry loop is **deleted**; `submit()`/`collect()` survive only
  as thin IPC helpers. Retry state becomes per-item records in `prediction.py`.

**cli_utils changes:**
- `process_batch` no longer assumes vlm_predict fully resolves cur_batch. An iteration returns
  a mix of terminal results from *whichever* batch they originated in, while retried items stay
  inside the predictor. Fine because everything downstream is per-path (`writer.enqueue`,
  `db.mark_failed`, `fetched_paths.discard`).
- The sanity check at `cli_utils.py:60` ("VLM returned no results for non-empty batch") must
  become an accounting check: `submitted == successes + terminal_failures + newly_pooled_retries`.
- Metrics/checkpoints count terminal items only.
- `fetch_batch` size becomes variable (`batch_size - pool sizes`).
- **Fetch tops up the pools; the iteration runs with whatever the pools hold.** This one rule
  covers both special cases:
  - *End of run (flush)*: loop submitting `min(batch_size, pools)` until both pools empty.
    Tail retries run as small batches — inherent, bounded by max_attempts, one-time cost.
  - *Multi-stage waiting* (fetch empty, upstream still promoting): don't let pooled items sit
    while sleeping 1 s/retry — run partial-batch iterations. The "sleep and retry" branch
    applies only when the pools are empty too.

### Phase A2 — Stage-side pipelining: pre-staged shm slots + submit-before-collect
*Touches: `prediction.py`, `cli_utils.py` (and slot-count sizing where the Shm pool is created).
Does NOT touch `vlm_service.py` — this is Phase B's mirror image on the stage side. Agreed
2026-07-13, not yet implemented.*

**Goal: the only stage-side work between generate(i) ending and generate(i+1) starting is
`request_queue.put(int)` per item. Everything else — response unpickle, validation,
classification, writer handoff, DB fetch, next batch's prompt prep AND its pickle into shm —
runs under GPU time.**

Two moves, which compose:

**(a) Pre-stage into shm at prep time.** Prep produces a staged slot, not a prompt dict: when
Thread B finishes building a fresh prompt (already under GPU time), it immediately generates
the `req_id`, builds the `VLLMRequest` (fresh-item sampling params are known then), `acquire()`s
a slot, and pickles into it. Pool record becomes
`{path, orig_prompt, slot_idx, req_id, attempts, last_error}` — `orig_prompt` stays in RAM
because retries rebuild "original + error" (already resident today, no new memory). Retries get
*re-staged at classification time* (different payload: error-appended prompt + bumped penalty —
can't reuse the old slot's bytes), which also runs under GPU time per (b). So every item in
either pool is always already staged, and `submit()` collapses to `request_queue.put(slot_idx)`
per record — microseconds. Bonus: oversize becomes a prep-time terminal failure, surfacing
before the item ever counts toward a submit set.

**(b) Submit-before-collect (one-batch software pipeline).** `_infer` currently couples
`submit(i) → collect(i) → validate(i)`; none of that work needs to happen *before* the next
submit. Reorder `run_iteration`:

```
1. Submit batch i — queue.put of pre-staged ints, ~instant. GPU is fed.
2. In parallel (existing 2-thread executor, contents shifted by one batch):
     Thread A: collect + unpickle + validate + classify batch i-1's responses
               (retries re-staged into slots here)
     Thread B: prep + stage batch i+1's fresh prompts
3. Return batch i-1's terminal results.
```

Because the GPU is fed in step 1 (not at the end), cli's writer enqueue, `mark_failed`, and the
next `fetch_batch` also run under GPU time. The collect/validate work doesn't get cheaper — it
gets hidden under generate() of the batch just fed.

Why this lands softly:
- **No new threads, no collector daemon.** The `ThreadPoolExecutor(max_workers=2)` structure
  survives verbatim; only *which batch* each thread works on shifts. (A free-running collector
  thread + results mailbox achieves the same overlap with more machinery and new shutdown
  surface — rejected until Phase C.)
- **`collect()` unchanged** — already keyed by req_id and order-independent; it's just handed
  batch i−1's id set while batch i sits in the queue/GPU.
- **cli almost unchanged** — Phase A already made results "terminal items from whichever batch
  they originated in", so the one-batch lag is invisible to writer/DB/metrics. Bootstrap =
  first iteration submits nothing and collects nothing (prep only); flush = keep iterating
  "submit what pools hold, collect previous" until a final collect-only iteration. The
  "fetch tops up pools" rule survives with the 2B target (Problem 3 fix); `run_iteration`
  should return `fetch_n` directly instead of `pending_count` so the formula lives next to the
  pools it describes.
- **Retries lag one extra batch** (batch i's failures join batch i+2 — i+1 is already
  submitted when they're classified). They were already asynchronous to their origin batch;
  nothing downstream cares.

**Boundary (be honest):** after generate(i) the *worker* still serially pickles/sends batch i's
responses before draining the already-full request queue — that residual gap is exactly Phase
B's sender/receiver threads. A2 + B together mean the queue never starves from either end.

### Phase B — Overlap IPC with generate() (worker side)
*Touches: `vlm_service.py` (+ `timed_worker.py`) only. Contract with the stage unchanged.
Designed in detail 2026-07-13; not implemented.*

**Where generate() still waits post-A2:** batch i+1's slot indices are already sitting in
`request_queue` while `generate(i)` runs, but the worker is single-threaded, so between two
generate calls it still serially does B × (shm.acquire + response pickle + response_queue.put)
followed by B × (request_queue.get + request unpickle + shm.release). At the measured
~1.7 ms/item each way that's ~100–200 ms of GPU idle per iteration at B=64 — plus the
`max_wait_ms=5000` hazard on partial batches. All of it hideable: vLLM's `generate()` releases
the GIL for essentially its whole runtime (V1 engine core is a separate process anyway).

**3-stage internal pipeline** (mirrors the bootstrap/overlap pattern `prediction.py` already
uses, on the other side of the queue):

```
Receiver thread                Main thread                     Sender thread
───────────────                ───────────                     ─────────────
loop:                          loop:                           loop:
  idx = request_queue.get(0.25)  batch = assemble(ready)         item = out.get(0.25)
  req = shm.get(idx)             if model is None: load          idx = shm.acquire(stop)
  shm.release(idx)               outputs = generate(batch)       shm.put(idx, (req_id, output))
  ready.put(req)                 for pairs: out.put(pair)        response_queues[stage].put(idx)
```

- `ready` / `out` are ordinary `queue.Queue`s — no new IPC, everything in one process.
  Unpickling batch i+1 overlaps `generate(i)`; pickling batch i's responses overlaps
  `generate(i+1)`. The inter-generate gap collapses to `assemble()` (list pops) + handing B
  tuples to `out` — microseconds.
- Both threads keep the `use_shm=False` baseline branch (pass the payload through directly) so
  the A/B timing comparisons stay possible.
- Bonus: the receiver runs during lazy model load, and it releases request slots EARLIER than
  today (during generate, not at drain time) — slightly loosens the 3B slot budget.

**assemble() = the max_wait fix.** Block for the first item; then take everything available; if
still short of batch_size, wait at most `max_wait_ms` (small — ~50 ms) since the first item
arrived; go. In steady state A2 has pre-submitted a full batch, so `ready` already holds B
items and assemble returns instantly — max_wait only fires at bootstrap and flush tails,
exactly where the 5000 ms hardcode could stall 5 s per iteration. Restore the ignored
constructor arg.

**Bounds (do NOT leave the internal queues unbounded):**
- `ready = Queue(maxsize=2*batch_size)` — if it fills, the receiver blocks, indices back up in
  request_queue with their slots held, and the documented free_slots/acquire() backpressure
  re-engages on the stage side. Nothing new to reason about.
- `out = Queue(maxsize=2*batch_size)` — if the sender stalls (stage not releasing response
  slots), the main thread blocks on out.put BEFORE starting another generate. Correct behavior:
  downstream is the bottleneck, so the GPU should wait.
- Unbounded, the worker silently becomes an unbounded RAM buffer.

**Shutdown — one genuinely new hazard: the ready list can strand requests.** Today every
request consumed off request_queue gets a response in the same loop iteration. With the
pipeline, on an unexpected main-thread death items can sit in `ready` (consumed, never
generated) while the stage's collect() waits on their req_ids. Main-thread finally: push
(req_id, None) for everything in `ready` + any assembled-but-not-generated batch into `out`,
then a sentinel; the sender drains until the sentinel, then exits. generate() exceptions keep
today's behavior (None outputs, loop continues). No new cancel_join_thread work — the
sender's/receiver's queue writes (response_queues, free_slots) happen in the same process,
already covered by run()'s finally.

**Instrumentation:** fold the timing into the new worker behind DEBUG_LEVEL and retire the
timed_worker.py fork — the three-thread structure diverges too much to maintain a parallel
instrumented copy (the stage side already made this exact consolidation with
timed_retry_validate). Add the KPI that matters more than all per-item timings: log the
inter-generate gap (generate(i+1) start − generate(i) end) per batch at DEBUG_LEVEL ≥ 1 —
that's the before/after number for the whole phase.

**Honest caveats:** pickle holds the GIL, so the sender/receiver's ~100 ms of pickle work per
batch now contends with vLLM's in-process output handling during generate — net should be
strongly positive (gap eliminated ≫ slight generate slowdown), but the timing test should
confirm, not assume. Phase B does NOT fix: stage prep throughput, prefill ramp, or Problem 4's
intra-batch tail (Phase C's job). A "batch all B responses into one shm slot" variant was
considered and rejected: it changes the collect() contract across the process boundary to
optimize work that's already hidden under generate.

### Phase C — AsyncLLM / continuous batching (promoted: fixes Problem 4; TWO-SIDED)
*Designed 2026-07-13, superseding the earlier "optional endpoint, later" sketch. Touches BOTH
sides: `vlm_service.py`/`timed_worker.py` (worker goes async) AND `prediction.py` /
`retry_validate.py` / `cli_utils.py` (stage goes streaming). An AsyncLLM worker alone does NOT
fix Problem 4 — it relocates the barrier to the stage's collect() (see "the crux" below). The
stage half is the bigger design job.*

**Why AsyncLLM fixes Problem 4:** per-request add (`generate(prompt, sampling_params,
request_id)` → async generator), per-request finish. Finished items stream back immediately
(validation / retry / writer proceed), fresh items and retries join the running batch
immediately, and a straggler delays only itself while the GPU stays full around it.
`LLM.generate()`'s barrier — and with it the worker's whole batching/max_wait logic — ceases to
exist.

**API verified against the installed vLLM 0.19.0 (2026-07-13):**
- `vllm.v1.engine.async_llm.AsyncLLM` (alias `AsyncLLMEngine`); its generate() docstring says
  "Main function called by the API server" — the most production-exercised path in vLLM,
  including VLMs.
- `AsyncLLM.from_engine_args(AsyncEngineArgs(...))` — AsyncEngineArgs is a superset of
  EngineArgs, so the existing engine_args dict maps over.
- `generate()` accepts multimodal prompt dicts (our `{'prompt': ..., 'multi_modal_data': ...}`
  shape) and per-request SamplingParams — structured outputs and the per-item
  repetition-penalty bumps ride along unchanged.
- `abort(request_id | iterable)` and `shutdown(timeout)` exist.

**Compatibility verdict: "works with LLM ⇒ definitely works with AsyncLLM" is NOT a safe
blanket assumption — but the risk lives in OUR integration code, not in model/feature
support.** Since V1, `LLM` is a synchronous wrapper over the same EngineCore that AsyncLLM
drives, so model support and EngineArgs are identical by construction. The genuinely new
surface:
- **asyncio machinery**: the worker main thread becomes an event loop; mp.Queue is blocking, so
  Phase B's receiver/sender threads survive as the bridges into the loop (B is a stepping
  stone, not throwaway work).
- **Rewritten shutdown protocol**: abort() every in-flight request on stop; engine death makes
  all pending generators raise — catch and map to the existing "emit (req_id, None), never
  leave collect() hanging" contract.
- **Streaming semantics**: cumulative RequestOutputs per request — take the final one
  (finished=True); RequestOutput.metrics fields differ from LLM.generate's.
- **API churn**: AsyncLLM's signature historically moves more than LLM.generate between vLLM
  versions — pin 0.19.0 and treat every upgrade as a re-verify event.
- **Admission control moves to us**: generate() accepts unlimited in-flight; `max_num_seqs`
  governs the running batch. Phase A's pools already bound stage-side in-flight; "batch_size"
  becomes a concurrency target.

**The stage-side barrier (the crux — why C is two-sided):** `_collect_and_classify` hands
collect() the FULL req_id set of batch i−1, and collect()'s `while pending > 0` blocks until
every one of them responds; run_iteration can't return before that, and batch i+1 is only
submitted by the NEXT run_iteration. So with an async worker and unchanged stage code, the A2
one-batch lag buys exactly one batch of slack: the engine stays full only while the previous
batch's tail is shorter than the current batch's body; a longer tail drains the engine toward
one sequence — same starvation, relocated. (The converse also holds: a streaming stage against
the barrier worker ≈ current behavior, since responses arrive all-at-once per generate call.
Both halves must ship together.)

**Stage side becomes: streaming collect + target-driven submission.**
- `self.inflight`: dict `req_id → record` with a TARGET (~2B, roughly tied to max_num_seqs) —
  no longer a list-per-batch.
- Each pump iteration: drain the response queue (every arriving (req_id, output) classified
  immediately — terminal → returned to cli; retry → re-staged → eligible for IMMEDIATE
  resubmission), then top up submissions from retry/ready pools until inflight == target, then
  absorb Thread B's freshly-staged records.
- The batch-set collect(req_ids) is replaced by a drain-whatever-has-arrived primitive (keep
  the 0.25 s stop_event poll).
- The straggler now delays only itself; its cohort has already been classified, written, or
  resubmitted around it.

**What survives untouched (the A/A2 payoff):**
- The INVARIANT verbatim ({ready, retry, in-flight, terminal}); in-flight ≤ target instead
  of ≤ B.
- Accounting is already per-item inside _collect_and_classify's loop; the batch-level sum check
  becomes a running counter.
- cli barely changes: Phase A already normalized returns to "terminal items from whichever
  batch they originated in", so (failed, successful, fetch_n) per pump keeps working.
- Crash safety unchanged: everything predictor-owned is state=1; the existing finally resets
  1→0.
- stage()/submit_token() are already the right primitives — pre-staged slots don't care whether
  submission is batched or per-item.

**Open design item (needs Problem-3-level trace rigor BEFORE implementing):** the fetch_n
formula — the "fetch tops up pools" rule survives, but `2B − pending` was derived for the batch
iteration cadence and must be re-traced for the pump cadence.

> **Implemented 2026-07-14 (eyeballed, not traced — by decision).** We did NOT re-trace the
> formula with Problem-3 rigor; over-fetching a bit is harmless (the fetched rows just sit in
> state=1 and reset 1→0 on crash), so the only real requirement is "don't let *too many* paths
> hang idle in the pools ahead of the engine." Implemented as a bounded predictor-owned total:
> `fetch_n = desired_total − in_flight − pending − in_prep`, with `target = 2·B` (in-flight
> concurrency target) and `desired_total = 3·B` (so at most ~one batch of prepared/ready buffer
> sits ahead of a full engine). Unlike the A2 batch formula, in_flight/pending/in_prep ARE all
> subtracted here — the pump refills continuously, so the goal is a bounded backlog, not a
> guaranteed-full batch per step. `in_prep` = paths inside fired-but-not-yet-absorbed prep
> futures (tracked as `(future, n_paths)` in `prediction.py`), which stops consecutive fetches
> from over-issuing while prep is still running.

**Watch items that batch mode currently hides:**
- **Prep throughput becomes a sustained-rate requirement** — no batch boundary to hide behind;
  get_prompts + staging must keep up with GPU consumption on average. reader_pool sizing
  matters.
- **Slot budget** grows to pools + target-inflight + responses in transit ≈ 3–4B (same warning
  mechanism, new number).
- **AsyncLLM per-request overhead** (an asyncio task per request, incremental streaming instead
  of one bulk return) — noise at B≈64; it's why the gains are "less or same, never more"
  rather than strictly positive for low-variance workloads.

**B-vs-C ordering decision (open):** tails are large on the large-prompt workload, which is
exactly where C stops being "eventual destination" and becomes "fixes the actual bottleneck".
Going straight to C avoids building B's batch-assembly main loop only to delete it (the
receiver/sender threads get built either way as the loop bridges). Decide on one measurement:
per batch, max vs median output token counts (or time from first to last finish). Large tail
fraction → C directly; small → B first as the safer, contract-preserving step.

### Phase C.1 — Final simplification: prep/collector threads replace the single-call "pump"
*Implemented 2026-07-17. Touches only `prediction.py` (`cli_utils.py` unchanged — the
`run_iteration(fresh_paths) -> (failed, successful, fetch_n)` contract, and the
`pending_count()`/`inflight_count()`/`in_prep_count()` introspection methods, are all identical
in shape; only what happens inside `VLMPrediction` changed).*

**Why:** the Phase C "pump" design (`run_iteration` itself firing a prep future, absorbing
completed prep futures, topping up submissions to a `target`, then draining+classifying inline —
`_topup_engine`/`_drain_and_classify`/`_absorb_prep_futures`/`_wait_for_prep`, a `ThreadPoolExecutor
(max_workers=2)`, and a `List[tuple]` of `(future, n_paths)` to track in-prep work) worked, but
every one of those responsibilities had to be re-derived inside a single call each time
`run_iteration` ran, with explicit bookkeeping (`prep_futures`, `retry_pool`, `ready_pool` as
plain lists popped/appended by hand) for state that is naturally just "a thread reading a queue in
a loop." It was correct but not the simplest expression of the design.

**What changed:** `VLMPrediction.__init__` now starts two **persistent daemon threads** —
`_prep_loop` and `_collect_loop` — once, for the object's whole life, instead of firing one-shot
futures per `run_iteration` call. Three plain `queue.Queue`s (`paths_in`, `retry_q`, `terminals`)
replace the pool lists and prep-future list as the hand-off points between cli, the prep thread,
and the collector thread. `run_iteration` is reduced to: push `fresh_paths` onto `paths_in`
(non-blocking), then block on `terminals` until a chunky return condition is met (`MAX_LINGER_S`
below), then return. All the "top up / drain / absorb prep" logic that used to live in
`run_iteration`'s loop body is now just "what the prep thread and collector thread each do,
continuously, on their own." Ownership accounting collapses from three separately-tracked
collections (`inflight` dict + `pending_count()` derived from two pool lists + `in_prep_count()`
summed from a futures list) to **one integer** (`self._owned`, incremented on hand-in / decremented
on return) plus `inflight`/`retry_q`/`terminals` sizes for the two now-directly-observable pieces;
`in_prep_count()` becomes the derived remainder (`owned - inflight - pending`) instead of a
separately maintained sum.

**New in this pass — `MAX_LINGER_S` (5.0s) chunky-return bound.** The old pump returned after
classifying however many responses arrived in one `drain_available()` call (often just 1–2,
paced by GPU completions). The new `run_iteration` instead *waits* for either `batch_size` results
to accumulate or `MAX_LINGER_S` to elapse since the first result of this call, so cli's DB fetches
stay sized in worthwhile chunks rather than 1–2 rows at a time — a direct win for fetch overhead
that the pump design didn't have a natural place to add (adding a wait loop to a function that
already had four responsibilities would have made it harder to follow, not easier).

**What is unchanged:** the invariant (every path is in exactly one of {being prepped, retry_q,
inflight, terminals, returned}); the `fetch_n = desired_total − owned` formula (now exact by
construction rather than by re-summing three counters each call); retries-first submission
ordering; oversize/prep-failure terminal-immediately handling; crash safety (everything
predictor-owned is still state=1, `cli.py`'s `finally` still resets 1→0 — more items can be
"in flight" at once now since prep/collect run continuously rather than in lockstep with
`run_iteration` calls, but the reset logic doesn't care how they got to state=1).

**Concurrency note:** the Phase C "pump" had an explicit `target` field (2·batch_size) capping how
many requests could be in-flight in the AsyncLLM engine at once. The prep thread has no such
explicit cap — it submits continuously as fast as paths/retries are available. Concurrency stays
bounded in practice by `desired_total` (3·batch_size) limiting how much cli fetches, plus the shm
`free_slots` pool as hard backpressure (`stage()` blocks in `acquire()` if every slot is held).
This is a slightly looser bound than the explicit `target` (nothing stops the prep thread from
pushing up to `desired_total` requests in-flight rather than pacing at `2·batch_size`), traded for
much simpler code; `desired_total` was already sized to keep DB rows bounded regardless.

**Verified:** `examples/chandra_testing/testing_result.txt` — 1024-image end-to-end run on the
final code, 0 failures, DB fully consistent (state_2=100%), 456.75s vs. v1.0's 588.31s (~1.29×
throughput, 1.74 → 2.24 img/s). Same dataset also run across the other three configs:
`use_async=False`/shm off (577.47s), `use_async=False`/shm on (570.4s), and `use_async=True`/shm
off (460.1s). Confirms the win is specifically from Phase C's continuous-batching +
streaming-stage design, not from shm alone: mp.Queue-only and mp.Queue+shm (no async) are both
small, real wins over v1.0 (~2% and ~3% respectively — GIL relief from moving the VLM to its own
process, then the kernel-copy savings from shm) but nowhere near the ~29% the async worker
delivers by itself. Turning on `use_async` with shm still OFF (460.1s) already captures almost
the whole win — shm on top of async saves only another ~3s (456.75s), because async's overlap of
communication and computation already hides most of what shm's kernel-copy savings would
otherwise buy.

## 3. Things to remember / be careful about

- **Items whose prompt preparation failed (`None` prompts): terminal-fail immediately.** Do NOT
  route through the retry pool — the prompt won't be re-prepared, so retrying wastes GPU.
- **Oversized-shm-slot items (`shm.put` ValueError → req_id=None): terminal-fail immediately.**
  The retry prompt only grows (error text appended), so it can never fit later.
- **Retry prompt construction: store the ORIGINAL prompt and build "original + latest error"
  each attempt.** Never append to the already-mutated prompt (errors would stack). Current
  code in `generate_with_validation` gets this right — preserve that behavior when moving it.
- **Per-item sampling params are already supported by the IPC layer** — `VLLMRequest` carries
  `sampling_params` per request and the worker builds a per-item list for `generate()`. The
  penalty bump just becomes part of the per-item retry record (cleaner than today's per-round
  deepcopy).
- **Crash-safety is unchanged, verify nothing breaks it**: pooled items stay state=1; on
  crash/shutdown the existing finally-block resets 1→0 and they're reprocessed from scratch
  (attempt counter resets — same semantics as today, where retry state also lived only in
  memory). `fetched_paths` needs no change: a path stays in it until terminal, which is exactly
  right for pooled items.
- **Writer/recovery untouched**: commit sequence, FSYNC_EVERY_LINES, recovery's
  last-250-lines assumption — all per-path / per-flush-group, none of it assumes batch
  boundaries. Keep it that way.
- **"Exactly batch_size" holds per stage, not per generate() call, when multiple stages share
  one VLLMService** — the worker batches whatever arrives from all stages within max_wait_ms.
  That's fine (more coalescing); don't build logic assuming a generate() call contains exactly
  one stage's batch.
- **Phase A alone does NOT fix GPU idle between batches** — each iteration is still lock-step
  (collect → validate → submit → worker unpickle with GPU idle). Its throughput payoff is when
  failures are common, plus the structural cleanup. Phase B is what closes the IPC gap.
- **Phase B shutdown rules**: worker threads must check `stop_event`; if the generate loop
  dies, the sender thread must still emit `(req_id, None)` error responses before exiting —
  preserve the "never leave collect() hanging" contract. The existing `cancel_join_thread()`
  finally-block already covers the queues (see `shm/exit_hang_postmortem.md`); the new threads
  must not add new queue-writers without extending it.
- **Backpressure**: the shm `free_slots` pool is the natural backpressure — a runaway
  submitter blocks in `acquire()`. Phase A's bounded pools mean we never hold more than
  ~batch_size + small-pool request slots. No new deadlock: the worker receiver always drains
  and releases promptly.
- **Phase A2 invariant update:** "in-flight ≤ batch_size" becomes "GPU in-flight ≤ B;
  predictor-owned total (pools + GPU + awaiting-collect) ≤ 2B + retry residue." Still strictly
  bounded — no backpressure runaway. The accounting check spans the lag: verify
  `submitted(i-1) == successes + terminal + re-pooled` against the batch being *collected*,
  not the one being submitted.
- **Phase A2 slot budget (the real constraint):** simultaneously held slots ≈ staged pool (≤ B)
  + in-GPU requests (≤ B) + batch i−1 responses not yet released (≤ B) ≈ **3B + margin**, vs
  ~2B today. At 10 MB slots and B=64 that's ~2 GB of /dev/shm — size `num_slots` explicitly
  and document the formula. `acquire()` is the backpressure; undersizing is not a deadlock
  (Thread A's releases always eventually satisfy Thread B's acquires) but it silently
  serializes the pipeline back into lock-step.
- **Phase A2 crash/shutdown:** more items sit in state=1 at any instant (up to 2B + pools) —
  all reset 1→0 by the existing finally block; staged slots leak only on hard kill and are
  reclaimed by the stale-block recovery at next start. At graceful shutdown there's an extra
  submitted-but-uncollected batch: abandon it (slots freed by cleanup()'s unlink, rows reset
  1→0); collect already polls stop_event every 0.25 s and the worker still emits
  `(req_id, None)`, so the "never leave collect() hanging" contract holds. No new queue
  writers → cancel_join_thread coverage unchanged.
- **Phase A2 multi-stage waiting branch:** before the sleep-1s branch, run a collect-only
  iteration if a batch is in flight — don't sleep on results already sitting in the response
  queue. The sleep applies only when fetch is empty AND pools are empty AND nothing is in
  flight.
- **`max_wait_ms` interaction with A2:** with batches pre-submitted, the worker's drain sees
  the full batch instantly, so max_wait shouldn't trigger in steady state — but a *partial*
  flush batch could stall up to max_wait per iteration. The 5000 ms hardcode gets more
  expensive under A2; verify the drain starts generate as soon as batch_size items are present.
- **`get_prompts` future-polling:** the `while not f.done(): sleep(0.1)` loop adds up to
  ~100 ms dead time per batch; wait on the futures with a timeout instead (micro-fix, fold
  into A2).
- **`max_wait_ms` is currently hardcoded to 5000 in `vlm_service.py.__init__` (debug value,
  constructor arg ignored).** In the Phase A/B world the worker should generate as soon as it
  has a full batch OR the GPU is idle and anything is pending — a long fixed wait adds tail
  latency. Phase B's assemble() policy resolves this (~50 ms since first item, arg restored).
- **Phase B: bound the internal ready/out queues (≈2B each)** — unbounded they turn the worker
  into an unbounded RAM buffer; bounded, backpressure re-engages via request_queue/free_slots
  (receiver side) and blocking before the next generate (sender side).
- **Phase B: drain-with-None on the way out.** Anything consumed off request_queue but not yet
  responded to (ready list, assembled-but-not-generated batch, out list) must get
  (req_id, None) before the threads exit — ready-list stranding is a NEW hazard the
  single-threaded worker didn't have.
- **Phase C: AsyncLLM alone does NOT fix Problem 4.** With the batch-set collect() unchanged
  the barrier just moves to the stage (one batch of slack from the A2 lag). Worker-async and
  stage-streaming must ship together.
- **Phase C: pin vllm==0.19.0** — AsyncLLM's surface churns more than LLM's between versions;
  every vLLM upgrade is a re-verify event (constructor, generate signature, streaming
  semantics, RequestOutput.metrics).
- **max_tokens mitigation is independent of all phases** — a tight max_tokens in
  get_sampling_params() bounds hallucination runaways today (they become validation failures →
  retry pool, which Phase A coalesces). Worth doing regardless of B/C.

  the AsyncLLM worker; skips the sync `_load_model` pre-load). This OVERRIDES `debug_timing` /
  `_worker` / `timed_worker`, which remain only as the pre-C batch-boundary baseline. Set
