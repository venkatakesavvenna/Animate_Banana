# v1.9.2 — One `WorkerPool`, one channel-visible `ServiceStatus`, vLLM stops being special

> **STATUS: AS BUILT (2026-08-12).** Implemented; see "As built — deviations from this proposal"
> below for the six places the implementation departs from the text, one of them a correctness fix
> that changes the design's central mechanism.
>
> Supersedes the health/service half of v1.9.1's design (the taxonomy, wire contract, DB machine,
> writer, and recovery halves are untouched and still authoritative). GPU validation constraint is
> unchanged: everything here was verified with the no-GPU fake-backend harness only.

## As built — deviations from this proposal

**1. The shared request queue could not stay shared. §2's "N processes competing on one
`request_queue.get()` is work-stealing by construction" is true and unusable.** `mp.Queue.get()`
acquires the queue's shared reader lock, polls the pipe, and releases it; a process SIGKILLed while
holding it never releases it, and CPython has no robust-futex recovery, so every surviving consumer
then blocks on that lock forever — the pool would recover the dead worker's requests, respawn it,
report the service healthy, and consume nothing ever again.

An idle worker is inside `get()` continuously, but only one consumer holds the lock at a time, so the
per-kill odds are roughly 1/N: measured at 3 of 8 trials with two workers, in ~20 lines of pure
`multiprocessing` with none of this code involved (`examples/no_gpu_validation/mp_only.py`). 1/N is
not a reprieve — the outcome is total, unrecoverable and silent whenever it lands, and a long run
kills workers more than once. §8 scenario 8 is what caught it; scenario 3 passed because a *busy*
worker is rarely inside `get()`, and the first `mp_only.py` run passed too, which is why that script
now reports a rate over several trials instead of a single verdict.

This is a pre-existing flaw — v1.9's `FunctionService` had the same exposure — but it makes
`on_worker_death="respawn"` a promise the code cannot keep, so it had to be fixed here. The shared
queue now has exactly ONE consumer, a dispatcher thread in the pool, which assigns each request to
the least-loaded worker with free capacity through a private per-worker queue. A killed worker can
only poison its own inbox, which the pool discards when it respawns it; the poison is contained in the
thing being thrown away anyway. Load balancing is unchanged in effect — a worker stuck on a slow item
stops being least-loaded and the others keep taking work.

The inversion paid for itself three times over, because the pool now knows what every worker owes
*before sending it*:

  - **§3's shared byte arrays are gone.** `req_ids` / `stages` / `n_inflight`, their fixed field
    widths, their truncation rules and their documented write ordering were only needed because the
    *worker* recorded the checkout. The pool records assignments in ordinary Python, in its own
    process, because it is the only reader and the only writer. What crosses a process boundary is
    two acknowledgements: `worker_ready` and a per-slot `done_seq` counter.
  - **§3's "known, bounded hole" is closed**, not documented. There is no window between `get()` and
    the ledger write, because the record exists before the request is sent.
  - **§2's `asyncio.Semaphore` is gone**, and so is §3's ledger-overflow path and the boolean return
    `set_inflight` needed for it. The dispatcher never assigns more than
    `max_inflight_per_worker`, so the ceiling is enforced once instead of in two places that can
    disagree.

Residual, and stated rather than papered over: workers still share the per-stage *response* queues, so
a worker SIGKILLed inside the window where its feeder thread holds one's write lock can still wedge the
response path. The window is far smaller than the request side's — microseconds of pipe write per
response, against a reader lock held across a 0.25s poll — but it is the same class of bug, and closing
it would mean routing every response through the pool process too. Left as a known limitation, and
recorded so it is a decision rather than an oversight.

**2. `health.py` became `core/status.py`, and `wire.py` became `core/wire.py`.** §1 kept
`ServiceStatus` in `vllm_module/health.py`. But §0's own complaint is that a health object named
"VLM" is published by chrome workers — leaving a backend-agnostic status object inside `vllm_module/`
keeps exactly the naming lie the release exists to remove. It now sits next to the thing that writes
it. `wire.py` moved for the same reason and one harder one: `core/service.py` imports `VLLMResponse`,
so with `specs.py` importing `core.service` the old location was a genuine import cycle. This also
retires the apology in `core/__init__.py` about one module being imported "the other way around".

**3. `BackendGone`, a third worker-side exception** (`core/task.py`), next to `InputRejected`. §4 had
the online spec discover a dead `vllm serve` through a 5-second `proc.poll()` timer and the async spec
through `_is_engine_dead_error` writing a shared flag — i.e. two per-backend death mechanisms, which
is the shape this release is supposed to be deleting. A worker that knows its own resource is gone now
says so once, in the framework's vocabulary: the request in hand is answered `infra`, the worker
drains, runs `term_fn`, and exits with a distinct status so the pool can report *why* rather than
"exitcode 1". Chrome workers get it for free.

**4. `call_fn(ctx, payload, params)` — one more argument than §2 specified.** §2's
`call_fn(ctx, payload)` silently drops `sampling_params`, which a vLLM `call_fn` cannot do without.
The alternatives were worse: folding params into the payload dict would put a `SamplingParams` object
into the JSONL's `prompt_str`, and passing the whole `VLLMRequest` would hand every task the `req_id`
and `stage_name` that are the framework's business. `params` is `None` for every non-model backend.
Relatedly, a `call_fn` may return a `CallResult(output, stats)` instead of a bare value when it counted
something the record should carry — an explicit type rather than "return a 2-tuple and we'll unpack
it", because plenty of honest `call_fn`s return a pair.

**5. `init_fn` receives the group's `stop_event`** on the namespace built from `spec.args`. §4's
online `init_fn` waits up to `ONLINE_HEALTH_TIMEOUT_S` (1800s) for `/health`; with no shutdown signal
to poll, Ctrl-C during a half-hour model load would either hang for the rest of it or leave the pool
to SIGTERM a worker mid-launch and orphan its GPU subprocess. `spec.args` stays JSON-able — the
framework supplies the primitive, which the worker process already holds.

**6. Deleted files were archived, not removed.** `docs/archive/{health.py,vlm_service.py,timed_worker.py}.removed`,
matching the existing `shm.py.removed` convention. The v1.9.1 versions of `health.py` and
`vlm_service.py` existed only in the working tree (v1.9.1 is uncommitted), so deleting them outright
would have destroyed the only copy.

**Open questions (§9), as resolved:**

- **Q1 — `on_worker_death` for the vLLM specs: `"abort"`**, as proposed, and the reasoning is recorded
  on `vllm_spec()`. `"respawn"` stays the default for `WorkerSpec` generally, which is right for pools
  of many cheap independent workers.
- **Q2 — `STALE_S` stays 30s, still unmeasured.** Its scope narrowed as predicted: it now guards only
  the group leader's own death, verified end-to-end (§8 scenario 6 detects at exactly 30.0s).
- **Q3 — `MAX_INFLIGHT_HARD_CEILING = 512` kept.** Its meaning shifted slightly: it now bounds what
  the *dispatcher* will assign, not what a worker may claim.
- **Q4 — one breaking release**, as proposed. StageWeaver shipped docs-only 1.1.1 with zero source
  changes (§6 held exactly).

One §6 claim weakened: `MAX_STAGE_NAME_BYTES = 255` is no longer load-bearing for the reason given
there, because the ledger no longer stores stage names in a 256-byte shared field. StageWeaver's check
is now a plain sanity check. It was left in place — it costs nothing and an absurd stage name is still
worth refusing at construction.

## §0 Motivation — where the complexity actually came from

v1.9 added `FunctionService` *beside* `VLLMService` instead of *under* it. The result is two
parallel supervision stories for what is one problem:

| Concern | `VLLMService` (v1.4 lineage) | `FunctionService` (v1.9) |
|---|---|---|
| process management | is itself a `Process`; nobody watches it | pool + supervisor thread |
| worker death | invisible → per-rank heartbeat hack (v1.9.1) | `proc.is_alive()` @0.5s |
| in-flight recovery | none (single implicit slot) | ledger → `infra` responses |
| restart | never | respawn budget |
| concurrency | hand-rolled asyncio queue loops (`online_worker`, `async_worker`) | strict get-one/answer-one |
| health | `VLMHealth`, built by *user code*, size-validated against the pool | same object, same ceremony |

Every duplicated concept the codebase is criticised for — two service classes, two `from_channel`s,
a health object named "VLM" that chrome renderers use, the `_RankState_{k}` ctypes factory with a
module `__getattr__` so it survives pickling, `STALE_S`-based 30-second SIGKILL detection — exists
to keep those two columns in sync. v1.9.2 deletes the left column.

**Three design rules, and everything below follows from them:**

1. **One backend manager.** `WorkerPool` (the renamed `FunctionService`) is the only thing that
   spawns, watches, restarts, or buries a backend process. vLLM is a `WorkerSpec` like chrome is.
2. **The channel is the only cross-process surface consumers see.** What crosses to `cli()` is a
   single fixed-shape `ServiceStatus` — `ready`, `failure_reason`, one heartbeat — published on
   `channel.extras` by the pool itself. Consumers ask "is the service up"; only the pool asks "are
   my workers up", because only the pool holds `Process` handles.
3. **The ledger goes pool-private.** "Which worker took which req_id" is a conversation between a
   worker and its supervisor. It stays shared memory (a queue message can die in the feeder thread
   at the exact SIGKILL that matters) but it is created in `WorkerPool.__init__`, inherited only by
   worker processes at spawn, and never appears on the channel.

What this is **not**: a removal of edge-case handling. The ledger write-order race, the
publish-before-spawn ordering rule, the exit-hang `cancel_join_thread()` discipline
(`docs/archive/exit_hang_postmortem.md`), and the ok/reject/infra taxonomy with both fuses are
properties of the problem. Each survives — handled once instead of twice.

**What this touches, at a glance:**

| Piece | Action |
|---|---|
| `core/service.py` | `FunctionService` → `WorkerPool`; async `call_fn` support; abort flag; owns status+ledger |
| `vllm_module/health.py` | rewritten: `ServiceStatus` (one fixed struct) + pool-private `Ledger`. ~700 → ~150 lines |
| `vllm_module/specs.py` | **new** — `vllm_online_spec()` / `vllm_async_spec()` return `WorkerSpec`s |
| `vllm_module/vlm_service.py` | **deleted** (`VLLMRequest` moves to `wire.py`) |
| `vllm_module/online_worker.py` | queue loop deleted; launch/payload/classify helpers survive into `specs.py` |
| `vllm_module/async_worker.py` | queue loop deleted; engine/render/classify helpers survive into `specs.py` |
| `vllm_module/timed_worker.py` | **retired to `docs/archive/`** (`backend="batch"` removed) |
| `core/channel.py` | unchanged shape; `set_health` now called by the pool, not by user init_fn |
| `drivers/cli.py`, `modules/prediction.py` | no structural change — same `channel.health` reads |
| StageWeaver | **zero code changes** (§6) — docs + version only |
| every `main.py` / `init_fn` | 5-step dance → 2 lines (§7) |

## §1 `ServiceStatus` — the only health object consumers ever see

One fixed `ctypes.Structure`, defined at module level in `health.py` (importable by qualname, so it
pickles across `spawn` with no factory and no `__getattr__` dance — the per-`k` class problem dies
with the per-rank array):

```python
class _Status(ctypes.Structure):
    _fields_ = [
        ("ready",       c_int8),        # 1 once the pool reports the service usable
        ("failed",      c_int8),        # 1 once the pool has given up (cooperative)
        ("reason_code", c_int8),        # REASON_* taxonomy, kept from v1.9.1
        ("heartbeat",   c_double),      # monotonic(), stamped ~1s by the POOL process
        ("detail",      c_char * 256),  # human-readable failure detail, written by the pool
    ]

class ServiceStatus:
    def __init__(self):
        self._s = mp.Value(_Status, lock=False)   # lock=False: v1.9.1 deviation #2 reasoning
                                                  # holds verbatim — single writer (the pool),
                                                  # SIGKILL must not poison the reader path
    # pool-side (single writer):
    def mark_ready(self): ...
    def mark_failed(self, code: int, detail: str): ...   # detail before failed flag —
                                                         # a reader seeing failed=1 must find text
    def start_heartbeat(self): ...                       # daemon thread in the POOL process
    # consumer-side (cli / prediction, read-only):
    def is_ready(self) -> bool: ...
    def failure_reason(self) -> Optional[str]:
        # non-None iff failed==1  OR  (heartbeat != 0.0 and monotonic()-heartbeat > STALE_S)
```

**What each field answers, and why all three are needed** (the design discussion's conclusion —
"pool alive" alone is *not* the service-liveness predicate):

- `ready` — cli's "wait for the backend, then start the clock". Set once, when every initial rank
  has finished `init_fn`. Never un-set by a respawn: capacity dips are throughput, not readiness.
- `failed` + `reason_code` + `detail` — **the exact-failure-reason mechanism, preserved.** The pool
  is alive after its workers die; it is the only thing that knows the story (exit codes, which rank,
  respawn count) and it writes one string, e.g.
  `"all 8 workers dead; rank 3 exitcode=-9, respawn budget (3) exhausted"`.
- `heartbeat` — the one failure the pool cannot cooperatively report: its own SIGKILL/OOM. One slot,
  stamped by the pool's supervisor process, checked against `STALE_S` (stays 30s, still unmeasured —
  v1.9.1 §6 Q2 remains open, now scoped to this single check). A pool that never ticked is never
  stale. Semantics are honest: if the process responsible for restarting workers is gone, the
  service is unsupervised and aborting cleanly (rows reset, nothing FAILED) is correct even if
  workers are still momentarily draining.

**Publication**: `WorkerPool.start()` calls `channel.set_health(status)` itself. User `init_fn`
no longer constructs, sizes, or publishes any health object — the v1.9.1 "build a `VLMHealth` with
matching `n_workers`/`max_inflight` or get a `ValueError`" ceremony is deleted because a mismatch
is no longer representable. The `extras["health"]` key and the `channel.health` property keep their
names so `cli()`/`prediction.py` churn is near zero.

**CPU-only groups** publish nothing: `channel.health is None` still means "no backend to wait for",
and remains why the framework must never pre-create a status object (a group whose `init_fn` starts
nothing would hang cli's readiness wait — v1.9.1's rule, unchanged).

**The ordering rule, restated once**: `init_fn` runs to completion before any stage worker spawns,
and the channel is pickled at each spawn — so anything the pool puts in `extras` during `start()`
reaches every stage worker exactly as reliably as the queues do. Nothing placed on a channel after
a spawn reaches the already-spawned process.

**Deleted from the consumer surface**: per-rank `ready`/`dead`/`reason` flags and their aggregates,
per-rank heartbeats, `attach_process` / `attach_worker_process` (the supervisor holds the handles;
nobody else needs an accelerant), the `_RankState_{k}` factory, the module `__getattr__`.
`VLMServiceDown` keeps its name (it is cli/prediction's exception, not the backend's), as do the
`REASON_*` codes; add `REASON_SUPERVISOR_LOST` for the heartbeat-stale case.

## §2 `WorkerPool` — the backend manager

`core/service.py`. Rename of `FunctionService`, absorbing everything `VLLMService` did that was
worth keeping. Everything in v1.9.1's supervisor design that is not explicitly changed below
carries over verbatim (backoff, recovery-as-infra, leaving an exhausted rank dead, log wording).

```python
pool = WorkerPool(spec, channel, logs_dir="./logs")
pool.start()     # creates status + ledger, publishes status, spawns workers,
                 # starts supervisor thread + status heartbeat
...
pool.stop()      # stop_event.set(); join workers (term_fn runs in each worker's finally);
                 # join supervisor; final status flags
```

`WorkerSpec` gains two fields and one capability:

```python
class WorkerSpec(NamedTuple):
    init_fn: Callable                    # (args, rank, device) -> ctx
    call_fn: Callable                    # (ctx, payload) -> output   — may be ASYNC (see below)
    term_fn: Optional[Callable] = None
    args: Optional[dict] = None
    devices: Optional[List[str]] = None
    n_workers: int = 1
    max_inflight_per_worker: int = 1     # ceiling 512 (MAX_INFLIGHT_HARD_CEILING), unchanged
    on_worker_death: str = "respawn"     # "respawn" | "abort"   ← the flag from the design discussion
    max_respawns: int = 3                # was the class constant MAX_RESPAWNS_PER_RANK
```

**The worker loop has exactly one degree of freedom.** `inspect.iscoroutinefunction(spec.call_fn)`
picks it at spawn; there is no other branching:

- **sync** — today's `_worker_main` verbatim: get one, ledger-checkout, `call_fn`, respond,
  ledger-clear. `max_inflight_per_worker` is almost always 1 here.
- **async** — the worker runs one asyncio loop: pull from the same `request_queue` (via
  `run_in_executor`, exactly as `online_worker._amain` does today), gate on
  `asyncio.Semaphore(max_inflight_per_worker)`, ledger-checkout **before** the task is scheduled,
  respond + ledger-clear in the task's `finally`. On `stop_event`, stop pulling and drain in-flight
  tasks before exit. This is `online_worker._amain`'s structure promoted to framework code, so it is
  written once instead of twice.

Failure classification at the loop is unchanged from v1.9: `call_fn` returns → `ok`; raises
`InputRejected` → `reject`; raises anything else → `infra`. An async `call_fn` follows the same
rule per task.

**Supervisor** (thread in the pool's process — the group leader under StageWeaver, `__main__`
standalone):

1. `proc.is_alive()` every 0.5s. **This replaces per-worker heartbeats outright**: SIGKILL/OOM-kill
   detection drops from ~30s to ≤0.5s, because the watcher now always lives where the handles live.
2. On a death: read that rank's ledger slots, emit one `VLLMResponse.infra(req_id, ...)` per entry
   on the correct response queue, clear the slots. (Unchanged: this is what stops `prediction.py`'s
   `_owned` from leaking and the pipeline from stalling in silence.)
3. Then, per `spec.on_worker_death`:
   - `"respawn"` — backoff `RESPAWN_BACKOFF_S`, respawn up to `max_respawns` per rank; a rank that
     exhausts its budget stays dead. When **every** rank is dead,
     `status.mark_failed(...)` + `channel.stop_event.set()`.
   - `"abort"` — first unexpected death ends the service:
     `status.mark_failed(REASON_WORKER_DIED, "<rank/exitcode detail>")` + `stop_event.set()`.
     Stages see `failure_reason()` → `VLMServiceDown` → rows reset, nothing marked FAILED.
4. Aggregates readiness: per-rank ready flags live in the pool-private array (§3); when all initial
   ranks have flagged, `status.mark_ready()`.

**Deleted**: the health `n_workers`/`max_inflight` validation block in `__init__` (the pool builds
both from its own spec), `from_channel()` (there is one construction shape now, and it takes the
channel), `FunctionService`/`VLLMService` as names.

## §3 The ledger — pool-private, flat, no custom ctypes classes

Created in `WorkerPool.__init__`, passed to worker processes as a spawn argument, never on the
channel. Consumers cannot see it; `cli()` cannot even tell a worker died.

The per-`k` `ctypes.Structure` (and therefore the pickling factory) is replaced by **flat
lock-free arrays of primitive types with index arithmetic** — primitive ctypes pickle by reference
natively:

```python
class Ledger:                                # health.py; internal to core/service.py
    def __init__(self, n_workers: int, k: int):
        self.n, self.k = n_workers, k
        self.worker_ready = mp.Array(c_int8,  n_workers,                          lock=False)
        self.n_inflight   = mp.Array(c_int16, n_workers,                          lock=False)
        self.req_ids      = mp.Array(c_char,  n_workers * k * REQ_ID_FIELD_BYTES, lock=False)
        self.stages       = mp.Array(c_char,  n_workers * k * STAGE_NAME_FIELD_BYTES, lock=False)
    # slot (rank, i) of req_ids spans [(rank*k + i)*37, +37); same shape for stages at 256.
```

Carried over **verbatim** from v1.9.1 (these are the problem's edge cases, not the old code's):

- `lock=False` and the single-writer-per-rank argument (a rank's slots: its own process while
  alive, the supervisor only after it is dead; ranks never share slots).
- Write order: `stages` before `req_ids` on checkout (a torn read sees an empty slot, never a
  req_id with no route home); `req_ids` cleared first on completion.
- Checkout recorded **before** work starts; the microseconds between `queue.get()` and the ledger
  write remain the known, bounded hole.
- Overflow (`set_inflight` → `False`): log loudly, drop the recovery record, run the request anyway.
- Field widths: `REQ_ID_FIELD_BYTES = 37`, `STAGE_NAME_FIELD_BYTES = 256` — which is why
  StageWeaver's `MAX_STAGE_NAME_BYTES = 255` check stays (§6).

**Why shared memory and not a "rank took req X" message to the supervisor**: `mp.Queue.put()` hands
off to a background feeder thread; a SIGKILL landing between `put()` and the pipe flush destroys
exactly the record needed at exactly the moment it is needed. The synchronous array store is the
point.

## §4 vLLM becomes a `WorkerSpec` — `vllm_module/specs.py` (new)

The only genuine difference between vLLM and chrome is that one vLLM worker must hold many requests
concurrently. §2's async loop is that difference; everything else about `VLLMService` was a second
backend manager, and is deleted.

```python
def vllm_online_spec(args) -> WorkerSpec:
    # init_fn : _launch_server() + _verify_served_model() (moved from online_worker.py, minus
    #           self), build an httpx.AsyncClient -> ctx {proc, base_url, model, client}
    # call_fn : ASYNC — _build_chat_payload() + POST /v1/chat/completions + classify:
    #           per-request HTTP 4xx -> InputRejected (reject); connection refused / 5xx /
    #           server process gone -> raise (infra). This is _handle_http()'s body with the
    #           queue plumbing removed.
    # term_fn : _terminate_server()
    return WorkerSpec(..., n_workers=args.n_vllm_servers,          # 2 servers = free load
                      devices=args.gpu_groups,                     # balancing on the one queue
                      max_inflight_per_worker=args.batch_size,
                      on_worker_death="abort")                     # see §9 Q1

def vllm_async_spec(args) -> WorkerSpec:
    # init_fn : _build_async_engine() (moved from async_worker.py), EAGER — `lazy_loading`
    #           is retired; ready means ready.  call_fn : ASYNC — _render() + engine.generate()
    #           (_handle()'s body); _is_engine_dead_error -> raise (infra).  term_fn: shutdown.
```

- `examples/*/main.py` map `args.backend` (`"online"` | `"async"`) to the spec builder. The string
  no longer reaches any service class.
- **`backend="batch"` is retired**: batch-boundary `LLM.generate()` cannot be a call-per-request
  worker, and it existed as an A/B timing baseline. `timed_worker.py` (and `debug_big_payload`,
  and therefore `_unwrap_token`'s list case) move to `docs/archive/`. No escape hatch is added to
  keep a benchmark alive.
- `vlm_service.py` is deleted. `VLLMRequest` moves to `wire.py`, which already owns the wire
  contract it is half of.
- Two `vllm serve` processes for two models (digital_twin's case) remain **two pools on two
  channels** — one group, one backend, unchanged topology.

## §5 Consumer side — `cli.py` / `prediction.py`: no structural change

- `cli()` signature unchanged. `channel.health` is now a `ServiceStatus`; the two calls it makes —
  `is_ready()` in the startup wait, `failure_reason()` via `_check_service_alive` — keep their
  names and meanings. Import moves with the rewrite of `health.py`.
- **The failure taxonomy is untouched and remains authoritative** (`prediction.py`): worker tags
  `ok`/`reject`/`infra`; `ok`-but-invalid retries on the model budget (`max_attempts=3` → FAILED);
  `reject` is terminal on first occurrence; `infra` retries on `MAX_INFRA_ATTEMPTS=5` with the
  blame-the-item rule gated on `others_are_working`, the consecutive-infra fuse at
  `max(2·batch_size, 64)` → `VLMServiceDown`, and the health check on every infra failure. The
  streak fuse is deliberately independent of §1: it catches "alive but failing everything", which
  no liveness mechanism can see.
- One behavioural improvement falls out for free: a single dead-then-respawned worker is now
  *invisible* to prediction (its in-flight arrives as `infra`, the pool respawns silently), and an
  all-dead backend surfaces in ≤0.5s + one supervisor pass instead of 30s.

## §6 StageWeaver — exactly what to do: **no code changes**

This is the v1.9.1 boundary design paying rent: StageWeaver constructs a bare 4-field channel,
calls `init_fn(args, logger, channel)`, spawns stage workers, and treats `extras` as opaque. Every
v1.9.2 change happens on the far side of that boundary.

| File | Action |
|---|---|
| `src/stageweaver/**` (all code) | **none** — locked signatures, channel dataclass, `MAX_STAGE_NAME_BYTES` all unchanged |
| `CLAUDE.md` | update the `init_fn` reference pattern to the `WorkerPool` 2-liner; note that the group's backend supervisor (and the service heartbeat) runs **in the group-leader process**, so killing a group leader is detected by its stages as `VLMServiceDown` after `STALE_S` |
| `CHANGELOG.md` | `[1.1.1]` — docs-only entry pointing at this file |
| `pyproject.toml`, `__init__.py` | 1.1.0 → 1.1.1 |

`MAX_STAGE_NAME_BYTES = 255` stays load-bearing: the ledger's stage field is still 256 bytes (§3).

## §7 Migration — every `init_fn`/`term_fn`, mechanical

Before (v1.9.1, vLLM group):

```python
def model_init(args, logger, channel):
    vlm_health = VLMHealth()
    svc = VLLMService.from_channel(channel, engine_args, gpus, batch_size,
                                   backend=args.backend, vlm_health=vlm_health, ...)
    svc.start()
    vlm_health.attach_process(svc)
    channel.set_health(vlm_health)
    return svc

def model_term(svc, stop_event):
    stop_event.set(); svc.join(); ...
```

After (v1.9.2, any backend):

## §9 Open questions

- **Q1 — `on_worker_death` default for the vLLM specs.** Proposed `"abort"`: a vLLM death is
  usually OOM or a driver fault that respawning reproduces, and a relaunch costs minutes of GPU
  time invisible to the operator. But `"respawn"` with `max_respawns=1` would ride out the
  transient-crash case. Decide at implementation; it is one field.
- **Q2 — `STALE_S` (inherited from v1.9.1 §6 Q2, still open).** Now guards only the
  group-leader-death check, so a false positive requires the *supervisor thread* (not a worker) to
  starve for 30s — strictly rarer than before. Keep 30s until measured.
- **Q3 — retire `MAX_INFLIGHT_HARD_CEILING = 512`?** Keep. Its reasoning (an absurd value is a
  units mistake that would disable the overflow signal) is unchanged by who owns the ledger.
- **Q4 — migration order.** One breaking release across Patram-Ingest and the parent repo's
  `init_fn`s; StageWeaver ships a docs-only 1.1.1 and is compatible with both sides throughout.
