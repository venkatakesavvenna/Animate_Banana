# v1.7 — Failure honesty: no silent skips, no silent image drops, no dataset-wide false failures

Working-notes record, same spirit as `docs/v1.5_changes.md` / `docs/v1.6_changes.md`.

> **Looking for a specific reported bug?** `docs/v1.7_reported_issues.md` is the short version:
> each issue as reported → root cause (with file:line) → what changed. This file is the design log.

v1.6 added the online backend on top of v1.5's async backend on top of v1.0's batch backend. Each
layer preserved the wire contract (`request_queue` in, `(req_id, output)` out) but nothing enforced
that the two sides *agreed*, and every failure mode — a dead engine, a missing file, a wrong
`is_llm`, a backend mismatch — collapsed into the same signal: `output = None`. `prediction.py`
could only read that as "retry, then mark the path FAILED".

**The theme of v1.7 is making different failures look different.** Concretely:

| Failure | Before | After |
|---|---|---|
| Engine / `vllm serve` died | every remaining row retried 3× and marked **FAILED** | run aborts (`VLMServiceDown`), in-flight paths reset 1 → fetch_state, **nothing** marked failed |
| VLLMService SIGKILLed | pipeline blocked forever on responses that never come | parent-side liveness check → same abort |
| `backend` mismatch between worker and prompt builder | images silently dropped, model answered from text | `BackendPayloadMismatch` on request one |
| `is_llm: true` + images | images silently dropped (online) / prompt-vs-payload mismatch (offline) | `PromptConfigError`, run aborts |
| image missing / corrupt / outside allowed root | opaque HTTP 400, retried 3×, no reason recorded | precise pre-submit error naming the file and the reason |
| image path with `#`, `?`, `%` | server silently read a *different* file | percent-encoded `file://` URL, exact round-trip |
| oversized image | rejected online, silently accepted offline | same pixel ceiling on both |
| stale server on port 8000 | run silently generated by **someone else's model** | ephemeral port + `/v1/models` identity check |
| `async_scheduling` unset | vLLM 0.25+ silently enabled it | pinned `False` unless the yaml opts in, on all backends |
| second Ctrl+C during shutdown | rows stranded in state=1 | signals shielded until teardown finishes |
| `write_local_json` raising | swallowed by an unread Future, for the whole run | logged (first 20 in full, count kept after) |
| ~5000 rows left on a 10M-row DB | loop exited: `get_state_pct` rounds to 0.0% | exact counts (`get_state_count`) |

## 1. VLM service liveness — `vllm_module/health.py` (new)

The single highest-severity bug. Any backend failure produced `(req_id, None)`; the collector
retried it `max_attempts` times and then marked the path FAILED. So one dead engine converted the
entire remaining dataset into state=3 at maximum speed, and a run ending with 10M FAILED rows was
indistinguishable from one where the model genuinely refused them.

`VLMHealth` gives "the engine is gone" its own channel:

- **`dead_event`** (`mp.Event`) — set by the VLLMService child the moment it cannot serve:
  `run()`'s `finally` (any exit at all), `_is_engine_dead_error()` in `async_worker`, the serve
  subprocess exiting in `online_worker`, an undecodable request, or a payload-kind mismatch.
- **`proc`** — the `Process` object, parent-side only. Covers SIGKILL/OOM-kill, where the child
  never got to set anything. Dropped in `__getstate__` so the object still pickles into the child.
- **`_reason`** (`mp.Value("i")`) — a small int code, so the child can say *which* failure it was
  without a Manager or a pickled exception.

Create it in `main.py` before spawning (same rule as every other IPC primitive), hand it to both
`VLLMService(...)` and `cli(...)`, and call `vlm_health.attach_process(vllm_proc)` after `start()`.

### How `prediction.py` uses it

`_validate_one()` now returns four statuses instead of two:

| status | meaning | action |
|---|---|---|
| `ok` | valid output | terminal success; resets the infra streak |
| `fail` | model answered, output invalid | retry on the normal `max_attempts` budget |
| `reject` | server refused **this** input (4xx) | **terminal immediately** — re-sending the identical request cannot change the answer, and the server's own message is carried through |
| `infra` | backend produced nothing | never a FAILED path while the backend is at fault |

`infra` handling (`_classify_infra`):

1. Its own retry budget (`MAX_INFRA_ATTEMPTS = 5`), which does **not** consume `max_attempts` — an
   item that never reached the model has not been "attempted".
2. Ask `VLMHealth`. Dead → `VLMServiceDown`, run aborts, nothing marked failed.
3. Fuse: `max(2·batch_size, 64)` consecutive infra failures with no success in between → treat the
   backend as down even if nothing set the flag.
4. Only blame the individual item (`terminal fail`) when there is evidence the backend is fine:
   `_total_success > 0` **and** not currently in a failure streak. Without that second condition a
   totally dead backend still failed every path — each item just exhausted its own infra budget
   before the global fuse had counted enough failures. (Caught by the verification harness, not by
   reading the code.)

`_collect_loop` also checks health when a drain returns empty while requests are in flight — that is
the SIGKILL case, which otherwise blocks forever.

`cli()` catches `VLMServiceDown` explicitly so the shutdown reason says so, and its `finally` resets
the in-flight paths exactly as it does for any other shutdown.

## 2. Backend / payload-shape agreement

`args.backend` reaches two places by two different call chains — `main.py → VLLMService` (which
worker runs) and `cli.py → VLLMConfig` (which prompt shape gets built). Nothing checked they matched,
and the failure was silent in **both** directions: the offline engine ignores an unknown
`"image_paths"` key, and `online_worker` read `prompt.get("image_paths") or []` → empty → a
text-only request. Either way the model answered without ever seeing the image. This is the most
likely single cause of "we send images and get blank/no-image output".

Fix: every prompt dict is stamped with `_payload_kind` (`"online"` / `"offline"`) by
`get_prompt_with_image`, and each worker calls `assert_payload_kind()` on the first thing it
receives. A mismatch marks the service dead and stops — it is a configuration error, not data.

`examples/chandra_testing/main_test.py` never passed `backend` at all, so it was pinned to `"async"`
regardless of intent; all three examples now derive both call chains from the one `args.backend`.

Also added, offline only: after `apply_chat_template`, the number of image-placeholder tokens in the
rendered prompt must equal the number of attached images (`_assert_image_placeholders`). The chat
template is the only thing that inserts that token, and it silently emits none if the message shape
is not what it expects.

## 3. Image input validation — `vllm_module/media.py` (new)

One place where every image path is checked, before either backend touches it. Each check raises
`ImageValidationError` naming the reason and the `repr()` of the path:

- must be a `str`, non-empty, **absolute**, encodable as UTF-8 (catches surrogates from an
  undecodable filename, which otherwise blow up much later somewhere unrelated);
- must exist, be a regular file, be non-empty;
- must be under `allowed_media_roots`;
- online only: header must decode (`PIL.Image.open`, header-only — cheap next to a VLM call), and
  `width * height` must be within the pixel ceiling.

`repr()` is deliberate: it is the only way a bad encoding shows up *as itself* in a log rather than
as a look-alike character.

### The em-dash investigation (issue 6)

Two independent mechanisms, both now closed:

**a. `file://` URLs were never percent-encoded.** vLLM parses them with `urllib3.util.parse_url` and
un-quotes with `urllib.request.url2pathname`. Verified against the installed vLLM 0.25.1 /
urllib3 2.7.0:

```
'/fsx/a—b/c.jpg'     -> '/fsx/a—b/c.jpg'    round-trips fine
'/fsx/a#b/c.jpg'     -> '/fsx/a'            TRUNCATED at the fragment
'/fsx/a?b/c.jpg'     -> '/fsx/a'            TRUNCATED at the query
'/fsx/a%20b/c.jpg'   -> '/fsx/a b/c.jpg'    SILENTLY DECODED to a different file
```

So the em-dash itself was *not* the problem — but `#`, `?` and `%` were, and they fail as "file does
not exist" or, worse, as reading a different file. `media.to_file_url()` uses `quote()`; all seven
tested path shapes now round-trip byte-exactly.

**b. The `—` seen in the JSONL is not a conversion.** `writer.py` already writes with
`ensure_ascii=False`, so a real em-dash is written as a real em-dash. A literal `—` in the
output means the DB genuinely holds those six ASCII characters — i.e. the *source path list* has
them, and the file on disk does not (or vice versa). Postgres is not involved: `psycopg3`'s
`copy.write_row` escapes properly and the connection is UTF-8.

That leaves a genuine source-data mismatch, which is now reported precisely instead of guessed at:
the offline backend used to turn it into a generic "Unreadable image" and the online backend into an
anonymous HTTP 400. Both now say `image file does not exist: '/path/with/—/x.jpg'` with the
exact bytes visible.

### Resolution handling (issue 3) — what is actually true

- **Hard ceiling.** `VLLM_MAX_IMAGE_PIXELS` (default 178,956,970) is enforced by `vllm serve`
  server-side and by **nothing** offline — `cv2.imread` accepted anything. Offline now enforces the
  same number from the decoded size, so "what counts as a legal image" no longer depends on backend.
  Over-limit is a terminal failure for that one image; it cannot crash a run.
- **The model's own downscaling is real, and cannot be switched off.** For
  `datalab-to/chandra-ocr-2` the processor is `Qwen2VLImageProcessorFast` with
  `size.longest_edge = 16777216` — an **area**, not an edge length. Anything above ~16.7M pixels is
  smart-resized down (and anything under `shortest_edge = 65536` is scaled *up*). This is part of
  how the model was trained and is applied **identically** online and offline, because both run the
  same HF processor inside vLLM. It is not a vLLM default we can override safely.
- What changed is that it is no longer invisible: `VLLMConfig._processor_max_pixels()` reads the
  threshold and `cli()` logs it at startup as `processor_downscales_above_pixels`, next to the
  allowed roots, the pixel ceiling, and the per-prompt image limit.
- Note `size` is a transformers `SizeDict` — attribute access, **not** a `dict`. An `isinstance(...,
  dict)` check silently reports "unknown" (found while testing this against the real processor).

## 4. `async_scheduling` and node crashes (issue 1)

Confirmed against the installed source (`vllm/config/vllm.py:992-1003`): in vLLM 0.25.1
`async_scheduling` defaults to `None`, and `None` resolves to **enabled** unless some other option
forbids it. So it was on by default in every backend, on every run, with nothing in the logs saying
so.

`VLLMConfig.get_engine_args()` now does `engine_args.setdefault("async_scheduling", False)` —
`DEFAULT_ASYNC_SCHEDULING`. A model yaml can still opt in explicitly.

This required fixing `_engine_args_to_serve_flags()`, which dropped `False` bools entirely. vLLM
registers bool config fields with `argparse.BooleanOptionalAction`, so `False` must become
`--no-<flag>`. Without that fix, `async_scheduling: false` was honoured offline and silently ignored
online — the two backends were not running the same configuration.

**On the other environment flags asked about:**

- **`--ipc=host`** — added to `bash_scripts/init_docker.sh`. The script already had `--shm-size=64g`,
  which covers the usual `/dev/shm` exhaustion; `--ipc=host` is the belt-and-braces version NVIDIA
  recommends for PyTorch, and it matches the docker command in the gemma bakeoff that ran cleanly.
- **`NCCL_P2P_DISABLE=0` / `NCCL_IB_DISABLE=0`** — these set the values to their *defaults*
  (0 = "not disabled"). They are no-ops unless something in the environment had set them to 1.
  Nothing in this repo does. My honest read: they did not fix anything, and the credit belongs to
  `async_scheduling` and/or shm sizing. Worth re-testing one variable at a time before adopting them.
- **`NCCL_NET_PLUGIN`** — this repo *does* override it, to `""`, in all three workers. The node
  environment sets `NCCL_NET_PLUGIN=aws-ofi`, so the pipeline is deliberately disabling the AWS OFI
  (EFA) plugin. Fine for single-node tensor parallelism, and pre-existing behaviour — flagged here
  because it is a real, undocumented override that would matter for multi-node.

## 5. Online backend hardening

- **Ephemeral port + identity check.** `ONLINE_PORT = 0` picks a free port. The old hardcoded 8000
  meant any pre-existing listener (a stale server from a crashed run, another user's job) answered
  `/health` with 200 and the whole run was silently generated by **the wrong model**.
  `_verify_served_model()` now confirms `/v1/models` contains the model we launched.
- **`--allowed-local-media-path` is configuration, not a constant.** It was hardcoded to
  `/fsxvision_new`, while `chandra.py` wrote its rescaled images to `/tmp/chandra_ocr_scaled` — so
  every online chandra request was rejected. It now comes from `args.allowed_media_roots`, the same
  value the stage validates paths against, so the two cannot drift.
- **4xx vs 5xx vs transport.** 4xx → `_OnlineFailure` carrying the server's own message (terminal,
  not retried). 5xx / `httpx.TransportError` → `None` plus a subprocess liveness check. Previously
  `raise_for_status()` threw the response body away, so the *reason* never reached any log.
- **Subprocess liveness.** The accept loop polls `proc.poll()` every 5s. It used to keep POSTing
  into a closed port after `vllm serve` died, turning the rest of the database into failures.
- **Sampling params.** `min_p` and `stop_token_ids` are now forwarded. `structured_outputs` raises
  instead of being silently dropped — dropping it produced unconstrained output that then failed the
  task's own validation on every retry.

## 6. Shutdown ordering and Ctrl+C (issue 5)

The existing order (reset stuck paths → `writer.close()`) is already correct, and now says why:
`cli_utils` removes a path from `fetched_paths` the moment it is handed to the writer, so everything
left in that set is work the writer will never see. Resetting first therefore cannot race the
writer's own `mark_done` (1 → 2), and frees the most-likely-abandoned rows before the slower flush.

What was missing was durability of the sequence itself:

- **`_shielded_teardown()`** installs no-op SIGINT/SIGTERM handlers for the whole `finally` block and
  prints why the extra Ctrl+C did nothing. This is the actual answer to "the user presses Ctrl+C too
  many times" — reordering does not help if a third Ctrl+C lands mid-reset.
- **Second sweep.** `writer.unflushed_paths()` returns what the writer accepted but never committed
  (buffer + queue), and those are reset too. Safe by construction: the commit protocol is
  write → fsync → `mark_done`, so anything not marked done was not fsynced and replaying it cannot
  duplicate a committed record.

## 7. Other real defects found while auditing

- **`VLLMService._worker()` dereferenced `self.shm` unconditionally** — an `AttributeError` on the
  default `use_shm=False` path. Unreachable today (`debug_timing = True` always routes to
  `timed_worker`), but broken. Now shares `_unpack_request()` with the timed variant.
- **`self.max_wait_ms = 5000` overwrote the constructor argument** in `VLLMService.__init__`.
- **`write_local_json` was submitted bare to a thread pool** and its Future never read, so every
  sidecar write could fail for an entire run in total silence. `chandra.py`'s signature was in fact
  wrong (`(image_path, output, logger)` vs the `(obj, logger)` VIE calls) — i.e. it *was* raising on
  every image. Both fixed; failures are now logged (first 20 in full, count kept thereafter).
- **`get_state_pct() == 0.0` as an exit condition** — rounds to one decimal, so on a 10M-row DB up to
  ~5000 pending rows read as "0.0%" and the loop declared the dataset finished. Replaced with
  `get_state_count()`.
- **Writer duplicate suppression was an O(n) list scan per image** and dropped the duplicate
  silently. Now an O(1) set, and it logs when it fires (it should never fire).
- **`chandra.py` re-encoded every image to JPEG q95** even when no resize was needed — a lossy round
  trip on 100% of inputs — and wrote one uuid-named scratch file per image with no cleanup, which
  fills the scratch filesystem on a long run. Now: pass the original through untouched when it is
  already large enough, and use a deterministic path-derived scratch name so replays overwrite
  rather than accumulate.
- **`chandra.py` swallowed rescale failures and returned the original path**, making a broken
  preparation indistinguishable from a successful one. It now raises; VIE turns that into a terminal
  failure for that one image with the reason logged.

## Verification

No GPU on the login node, so the checks run against a stubbed `vllm` module plus the **real**
chandra processor from the HF cache (`scratchpad/verify.py`, 22 assertions):

- media validation: missing / outside-root / corrupt / zero-byte / relative / oversized each raise
  their own specific error;
- `file://` round-trip through vLLM's own parser for 7 path shapes;
- serve-flag translation incl. `False → --no-<flag>`;
- payload-kind guard in both directions;
- `VLMHealth` reason reporting;
- end-to-end `VLMPrediction` against a fake worker: dead backend raises `VLMServiceDown` and marks
  **nothing** failed; an unflagged dead backend still trips the fuse and marks nothing failed; a
  healthy backend still produces successes.

Real-model checks (chandra processor loaded from `/hf_cache`): online payload shape, offline payload
with exactly one `<|image_pad|>` per attached image, `is_llm` + image → fatal, over-`limit_mm_per_prompt`
→ fatal, missing file → per-item.

**Not run:** anything requiring a GPU. The engine-side behaviour of `async_scheduling: false`, the
`vllm serve` launch path (ephemeral port, `/v1/models` check, `--no-async-scheduling` acceptance) and
real end-to-end throughput all still need one run on a GPU node before this is trusted in production.

## Deferred (deliberately)

- **Image-loading parity** (`cv2.imread` vs vLLM's PIL + white-background RGBA compositing) — still
  Divergence 3 in `docs/vllm_serve_offline_parity.md`. Now more visible than before (offline and
  online agree on *limits* but still not on *pixels* for RGBA/`tRNS` images), and worth doing next.
- **Chandra sampling-param parity with the upstream repo** (`datalab-to/chandra`,
  `chandra/model/vllm.py`) — `chandra.py::get_sampling_params()` now uses the v1.6 dict-overlay
  contract, so only the fields chandra actually tunes are pinned and everything else resolves from
  `generation_config.json` like `vllm serve` would. The values themselves are still the ones that
  were already in this repo; re-deriving them from upstream is a follow-up (that repo was not
  reachable from this node).
- **The two chat templates in chandra-ocr-2** — the repo ships both a standalone `chat_template.jinja`
  (always emits `<think>\n\n</think>`, ignores `enable_thinking`) and a different one inside
  `tokenizer_config.json` (honours `enable_thinking`). They agree for `enable_thinking=False`, which
  is what this pipeline uses, so it is latent rather than live. It would become a real online/offline
  divergence the moment thinking is turned on.
- **Structured outputs on the online backend** — now an explicit error rather than a silent drop.
- **`repetition_penalty` +0.5 per retry** (`_build_sampling_params`) is a very large step
  (1.0 → 1.5 → 2.0) and now actually reaches the online backend too. Left as-is, but it is worth
  measuring whether retries are being made worse by it.
