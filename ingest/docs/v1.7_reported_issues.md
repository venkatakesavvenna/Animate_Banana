# v1.7 — Reported issues → root cause → fix

Companion to `docs/v1.7_changes.md` (which is the full design log). This file is the short version:
each issue exactly as reported, what was actually wrong, and what changed.

Environment the analysis was done against: vLLM **0.25.1** (`/fsxvision_new/srihari.bandarupalli/
environments/gemma4_new`), urllib3 2.7.0, transformers 5.x, `datalab-to/chandra-ocr-2` from
`/hf_cache`.

---

## 0. The common root cause

Every backend reported every failure the same way — `output = None` on the response queue.
`prediction.py` could only read that as *"retry `max_attempts` times, then `db.mark_failed(path)`"*.
So a dead engine, a missing file, a wrong `is_llm`, and a backend mismatch were all indistinguishable
from "the model produced a bad answer". **v1.7 is about making those look different.**

---

## 1. `async_scheduling` should default off; are `--ipc=host` / `NCCL_*` also involved?

**Reported:** async_scheduling must default to `false` on the AsyncLLM engine or it crashes the node;
also figure out whether `--ipc=host`, `NCCL_P2P_DISABLE=0`, `NCCL_IB_DISABLE=0` were what actually
saved it.

**Root cause — confirmed.** `vllm/config/vllm.py:992-1003`: `async_scheduling` defaults to `None`,
and `None` resolves to **enabled** unless another option forbids it. It was on in every run, on every
backend, with nothing in our logs recording it.

**Second, hidden half.** `_engine_args_to_serve_flags()` translated `True` → bare flag and dropped
`False` **entirely**. vLLM registers bool config fields with `argparse.BooleanOptionalAction`
(`engine/arg_utils.py:345-347`), so `False` must become `--no-<flag>`. Setting
`async_scheduling: false` in the yaml therefore worked offline and was **silently ignored online** —
the two backends were not running the same configuration.

**Fix**
- `vllm_config.py:51` `DEFAULT_ASYNC_SCHEDULING = False`; `get_engine_args()` (`:289`) applies it via
  `setdefault`, so a yaml can still opt in. Applies to all three backends.
- `online_worker.py:276` `_engine_args_to_serve_flags()` now emits `--no-<flag>` for `False`.
- `async_worker.py` logs the resolved value at engine build.
- `examples/chandra_testing/vllm_model.yaml` states it explicitly.

**On the other flags — honest answer**
- `--ipc=host`: added to `bash_scripts/init_docker.sh:63`. The script already had `--shm-size=64g`,
  which covers the usual `/dev/shm` exhaustion, so this is belt-and-braces (and matches the docker
  command from the gemma bakeoff that ran cleanly).
- `NCCL_P2P_DISABLE=0` / `NCCL_IB_DISABLE=0`: `0` **is** the default (`0` = "not disabled"). These are
  no-ops unless something set them to `1`; nothing in this repo does. My read: they did not fix
  anything, and the credit belongs to `async_scheduling` and/or shm sizing. Re-test one variable at a
  time before adopting them.
- Unrelated finding: this repo **does** override `NCCL_NET_PLUGIN` to `""` in all three workers,
  while the node environment sets `NCCL_NET_PLUGIN=aws-ofi`. So the AWS OFI (EFA) plugin is being
  deliberately disabled. Fine for single-node TP; would matter for multi-node. Pre-existing, now
  documented.

## 2. Images sent, model answers as if there is no image (intermittent)

**Reported:** blank/no-image output on async and online; suspect `is_llm`; suspect
`--allowed-local-media-path`; what happens on a missing/corrupt file — error, crash, or silent
run-without-image? Add an assert for `is_llm=True` + images. Error out if a path is outside the
allowed media root.

**Root causes — four independent silent drops.**

| # | Mechanism | Why it was invisible |
|---|---|---|
| a | **Backend/payload mismatch.** `args.backend` reaches two places by two chains: `main.py → VLLMService` (which worker runs) and `cli.py → VLLMConfig` (which prompt shape gets built). Nothing checked they agreed. | Silent **both ways**: offline `engine.generate()` ignores an unknown `"image_paths"` key; `online_worker` did `prompt.get("image_paths") or []` → empty → text-only request. Model answers from text alone. |
| b | **`is_llm: true` with images.** Online did `"image_paths": [] if self.is_llm else img_paths` — dropped on the floor. Offline flattened the message to text but **still attached `multi_modal_data`**, i.e. payload and prompt disagreed. | No error either way. |
| c | **`--allowed-local-media-path` hardcoded to `/fsxvision_new`** while `chandra.py` wrote its rescaled images to `/tmp/chandra_ocr_scaled`. | Every online chandra request → HTTP 400, whose body `raise_for_status()` discarded → the stage saw only `None` → "failed after 3 attempts", no reason. |
| d | **`examples/chandra_testing/main_test.py` never passed `backend`** to `VLLMService`, and `args` had no `backend` at all. | Pinned to `"async"` regardless of intent — and see (a). |

**Fix**
- **Payload-kind stamp.** Every prompt dict carries `_payload_kind` (`"online"`/`"offline"`); each
  worker calls `assert_payload_kind()` (`vllm_config.py:71`) on the first request. Mismatch → mark
  the service dead and stop. Config error, not data.
- **`is_llm` + images is fatal.** `_check_image_inputs()` (`vllm_config.py:313`) raises
  `PromptConfigError` (`:58`). Deliberately **fatal, not per-image**: it affects every image equally,
  so failing them one at a time would march the dataset into state=3. Same for exceeding
  `limit_mm_per_prompt.image`. (A text-only prompt to a *vision* model is legal and needs no flag —
  only `is_llm: true` + images is an error.)
- **Allowed roots are configuration.** `args.allowed_media_roots` feeds both
  `vllm serve --allowed-local-media-path` **and** the stage-side validation — one arg so they cannot
  drift. `backend="online"` on a vision model without it now raises at startup.
- **Placeholder assertion (offline).** After `apply_chat_template`, the count of image-placeholder
  tokens must equal the number of attached images (`vllm_config.py:492`). The chat template is the
  only thing that inserts that token and silently emits none if the message shape is unexpected.

**"What happens with a missing/corrupt file?" — measured, then made uniform**

| Input | Before (online) | Before (offline) | Now (both) |
|---|---|---|---|
| missing file | HTTP 400, body discarded, retried 3×, marked FAILED | `cv2.imread` → None → generic `RuntimeError: Unreadable image` | pre-submit `image file does not exist: '<repr>'`, terminal, one retry-free failure |
| corrupt file | server decodes → 400 (same as above) | `cv2` → None → same generic error | `image cannot be decoded (UnidentifiedImageError: ...)` |
| outside allowed root | 400 `must be a subpath of --allowed-local-media-path` | n/a (no such concept) | `image path is outside the allowed media roots [...]` |
| relative / empty / non-UTF-8 path | undefined | undefined | each has its own message |

Neither backend ever "silently runs the prompt without the image" any more — that path does not
exist. All checks live in one place, `vllm_module/media.py:143` `validate_image_path()`, called from
`get_prompt_with_image` before either backend touches the path.

## 3. Image resolution — crash? silent downscale?

**Reported:** if we send a big image, does it crash, auto-resize, or silently degrade quality? We're
doing a high-quality OCR datagen run; silent resolution loss would be bad, and one big image randomly
killing a run would also be bad.

**What is actually true — three separate things that were being conflated.**

1. **Hard ceiling.** `VLLM_MAX_IMAGE_PIXELS` (default `178_956_970`) is enforced by `vllm serve`
   server-side (`multimodal/media/image.py:load_bytes`) and by **nothing at all** offline —
   `cv2.imread` accepted anything. So "what counts as a legal image" depended on the backend.
2. **The model's own downscaling is real and cannot be disabled.** For `chandra-ocr-2` the processor
   is `Qwen2VLImageProcessorFast` with `size.longest_edge = 16777216` — an **area in pixels**, not an
   edge length. Above that it smart-resizes down; below `shortest_edge = 65536` it scales *up*. This
   is how the model was trained, and it runs **identically online and offline** because both execute
   the same HF processor inside vLLM. It is not a vLLM default we can safely override.
3. **PIL's decompression-bomb limit** fires at ~179M px (warning) / ~358M px (error), independently.

**Fix**
- Same ceiling on every backend: `media.check_pixels()` (`media.py:212`) is applied online from the
  header read and offline from the decoded size. Over-limit = one terminal item failure with an
  explicit message. **One big image can no longer crash a run, and can no longer be silently accepted
  by one backend and refused by the other.**
- The model's downscale threshold is read at startup (`vllm_config.py:192`
  `_processor_max_pixels()`) and logged by `cli()` as `processor_downscales_above_pixels`, alongside
  the allowed roots, the pixel ceiling and the per-prompt image limit. Not preventable — but no
  longer invisible.
- PIL's bomb limit is left **alone** (raising it process-wide would trade an explicit error for an
  OOM); when it trips first, `media.py` translates it into the same oversize message rather than a
  generic decode failure.
- Gotcha found while testing against the real processor: `size` is a transformers `SizeDict`
  (attribute access), **not** a `dict`. An `isinstance(..., dict)` check silently reports "unknown".

## 4. VLM service crash → whole database marked FAILED

**Reported:** when the vLLM service crashes, every prompt comes back `None`, the entire DB runs
through and goes to FAILED. We must know immediately, and those paths must **not** be marked failed —
they should stay in-processing and be reset to state 0 when cli ends.

**Root cause.** `_validate_one()` raised on `pred is None`, which `_classify()` treated as an ordinary
validation failure: 3 retries, then `terminals.put(("fail", path))` → `db.mark_failed()`. Nothing
anywhere knew the difference between "the model gave a bad answer" and "there is no model". A
SIGKILLed `VLLMService` was worse still: responses simply never arrived, `inflight` never drained, and
the pipeline blocked forever.

**Fix — `vllm_module/health.py` (new).**
- `VLMHealth.dead_event` (`mp.Event`) is set by the child the instant it cannot serve:
  `VLLMService.run()`'s `finally` (any exit at all), `_is_engine_dead_error()`
  (`async_worker.py:99`, matches vLLM's `EngineDeadError`/`EngineGenerateError`), the serve
  subprocess exiting, an undecodable request, or a payload-kind mismatch.
- `VLMHealth.proc` is the `Process`, parent-side only (dropped in `__getstate__`) — covers
  SIGKILL/OOM-kill, where the child never runs its own `finally`.
- `_reason` is an `mp.Value("i")` so the child can say *which* failure without a Manager.

**`prediction.py` — four statuses instead of two** (`:410` `_validate_one`):

| status | meaning | action |
|---|---|---|
| `ok` | valid output | terminal success; resets the infra streak |
| `fail` | model answered, output invalid | normal `max_attempts` retry budget |
| `reject` | server refused **this** input (4xx) | **terminal immediately**, carrying the server's own message — re-sending an identical request cannot change the answer |
| `infra` | backend produced nothing | **never** a FAILED path while the backend is at fault |

`infra` handling (`:606` `_classify_infra`):
1. Separate retry budget `MAX_INFRA_ATTEMPTS = 5` (`:91`) — does **not** consume `max_attempts`, since
   an item that never reached the model has not been attempted.
2. Ask `VLMHealth` (`:450`). Dead → raise `VLMServiceDown`. Nothing marked failed.
3. Fuse (`:624`): `max(2·batch_size, 64)` consecutive infra failures with zero successes → treat the
   backend as down even if nothing set the flag.
4. Only blame the individual item when there is evidence the backend works: `_total_success > 0`
   **and** not currently in a failure streak. *(Without that second condition a fully dead backend
   still failed every path — each item exhausted its own infra budget before the global fuse had
   counted enough failures. Caught by the test harness, not by reading the code.)*

`_collect_loop` also checks health when a drain returns empty while requests are in flight — that is
the SIGKILL case, which otherwise hangs forever.

`cli.py:292` catches `VLMServiceDown` explicitly so the shutdown reason names it; the existing
`finally` resets the in-flight paths 1 → `fetch_state`. **Net effect: exactly what was asked — the run
stops, nothing is marked FAILED, and the paths are replayed on the next run.**

## 5. Prioritise resetting stuck paths on shutdown (Ctrl+C spam)

**Reported:** reset stuck paths to state 0 as early as possible, because users press Ctrl+C many
times — but make sure that doesn't cause something worse, like marking a path 0 while it's still
being written.

**Assessment.** The existing order (reset → `writer.close()`) is already correct, and the reason is
subtle enough that it was worth writing down: `cli_utils` removes a path from `fetched_paths` the
moment it is handed to the writer, so everything left in that set is work the writer will never see.
Resetting first therefore **cannot** race the writer's `mark_done` (1 → 2), and it frees the
most-likely-abandoned rows before the slower flush. Reordering further would be the dangerous change,
not the safe one.

What was genuinely missing was durability of the sequence itself.

**Fix**
- `cli.py:23` `_shielded_teardown()` — installs no-op SIGINT/SIGTERM handlers for the entire `finally`
  block and prints why the extra Ctrl+C did nothing. This is the real answer: reordering doesn't help
  if a third Ctrl+C lands mid-reset.
- `cli.py:346` second sweep — `writer.unflushed_paths()` (`writer.py:225`) returns what the writer
  accepted but never committed (buffer + queue); those are reset too. Safe by construction: the commit
  protocol is write → fsync → `mark_done`, so anything not marked done was never fsynced, and
  replaying it cannot duplicate a committed record. Previously those rows stayed stuck in state=1
  until someone ran `reset-stuck` by hand.

## 6. Em-dash path: "file not found" online, blank output offline, `—` in the JSONL

**Reported:** a path with an em-dash failed online with file-not-found; the same path on the AsyncLLM
backend raised nothing but returned blank-image output; and the JSONL showed the escaped unicode, not
the em-dash. Where is the conversion happening — Postgres?

**Findings — three separate things, none of them Postgres.**

**a. The em-dash itself is fine.** Verified against the installed vLLM 0.25.1 / urllib3 2.7.0 path
(`urllib3.util.parse_url` → `urllib.request.url2pathname`):

```
'/fsx/a—b/c.jpg'    -> '/fsx/a—b/c.jpg'    round-trips exactly
'/fsx/a#b/c.jpg'    -> '/fsx/a'            TRUNCATED at the fragment
'/fsx/a?b/c.jpg'    -> '/fsx/a'            TRUNCATED at the query
'/fsx/a%20b/c.jpg'  -> '/fsx/a b/c.jpg'    SILENTLY DECODED to a different file
```

So the real bug is that `file://` URLs were built by raw interpolation and never percent-encoded.
`#`/`?`/`%` in a path either fail as "does not exist" or, worse, cause the server to read **a
different file**. Fixed: `media.to_file_url()` (`media.py:230`) uses `quote()`; all seven tested path
shapes now round-trip byte-exactly.

**b. The `—` in the JSONL is not a conversion.** `writer.py` already writes with
`ensure_ascii=False`, so a real em-dash is written as a real em-dash. Postgres is not involved either:
`psycopg3`'s `copy.write_row` escapes properly and the connection is UTF-8. A literal `—` in the
output therefore means **the DB genuinely holds those six ASCII characters** — i.e. your source path
list contains the escaped form and the filesystem contains the real character (or vice versa). That
is a source-data mismatch, not a pipeline transformation.

**c. Why offline "raised nothing and returned blank".** That is issue 2 — one of the four silent
image-drop paths — not a path-encoding problem. With the image dropped, the model saw text only.

**Fix.** Beyond the encoding fix, the mismatch is now *reported* instead of guessed at:
`validate_image_path()` fails with `image file does not exist: '/path/with/—/x.jpg'` using `repr()`,
which is the only way a bad encoding (mojibake, NFC/NFD, a literal `—`, surrogates from an
undecodable filename) shows up **as itself** in a log rather than as a look-alike character. Paths are
also checked for UTF-8 encodability up front, so a surrogate no longer explodes later somewhere
unrelated.

## 7. Is `backend` routed properly, or is a default taken somewhere?

**Reported:** check the `backend` flag from `main.py` is properly routed everywhere; and separately,
match chandra's upstream vLLM settings the way we did for gemma.

**Root cause.** It was not routed. `examples/chandra_testing/main_test.py` passed no `backend` to
`VLLMService` (defaulted `"async"`) and `build_args()` had no `backend` key at all, so
`cli()`'s `getattr(args, "backend", "async")` also fell back. Both example `model_init()`s built
`VLLMConfig(model, path)` with no `backend=`, silently defaulting. Nothing validated the two chains
against each other.

**Fix.** One `args.backend`, threaded to both chains in all three examples, plus the wire-level
`assert_payload_kind()` from issue 2 so a mismatch fails on request one instead of degrading into
image-less answers. `VLLMConfig`/`VLLMService` both reject an unknown backend string.

**Chandra upstream parity — partially done, and honestly flagged.**
- Done: `chandra.py::get_sampling_params()` now uses the v1.6 **dict-overlay** contract, so only the
  fields chandra actually tunes are pinned and everything else resolves from `generation_config.json`
  exactly as `vllm serve` would fill it in. Returning a full `SamplingParams` (as it did) pinned
  *every* field, including ones nobody chose, to vLLM's neutral defaults.
- **Not done:** re-deriving the values from `github.com/datalab-to/chandra` `chandra/model/vllm.py`.
  That repo was not reachable from this node. The values currently in `chandra.py` are the ones that
  were already in this repo (`temperature=0.0`, `top_p=0.1`, `max_tokens=12384`,
  `repetition_penalty=1.0`).
- Noted while reading the model: chandra-ocr-2 ships **two different chat templates** — a standalone
  `chat_template.jinja` (always emits `<think>\n\n</think>`, ignores `enable_thinking`) and a
  different one inside `tokenizer_config.json` (honours it). They agree for `enable_thinking=False`,
  which is what this pipeline uses, so it is latent — but it becomes a real online/offline divergence
  the moment thinking is enabled.

## 8. `online_worker`/`async_worker` print to stdout instead of logging

**Reported:** VLLMService's online/async workers only `print()` — give them a real logger like every
other component, so debugging is easier. Concern raised in response: doesn't opening/logging around
every image slow the pipeline down? (Separate question, answered without a code change — see below.)

**Root cause.** `VLLMService.run()` and everything downstream of it (`_load_model`, `_worker`,
`async_worker.py`, `online_worker.py`) never had a logger at all. Every diagnostic — server
launch/health/shutdown, per-request failures, engine-load timing, the `[async_worker]`/`[online_worker]`
messages — went to `print()`, which only reaches whatever is attached to the spawned process's stdout
(a terminal, or nothing once backgrounded/`nohup`'d) and isn't durable, unlike `main.log` /
`vlm_prediction.log` / `recovery.log` / `jsonl_writer.log`, which all already go through
`utils.get_logger()`.

**Fix**
- `VLLMService` takes a `logs_dir` param (default `"./logs"`, matching `VLMPrediction`'s own default).
  `run()` builds `self.logger = get_logger(self.logs_dir, "vlm_service")` as the very first thing it
  does **in the child process** — not in `__init__`, because a `logging.Logger` holding an open file
  handle does not survive being pickled across the `spawn` boundary. (`vlm_service.py`)
- Every `print()` in `vlm_service.py`, `async_worker.py`, `online_worker.py` now goes through
  `self.logger` (`online_worker.py`'s two free functions that didn't have `self` in scope,
  `_verify_served_model()` and `_terminate_server()`, now take an explicit `logger` param instead).
- All three active example entry points (`examples/vllm_testing/main.py`,
  `examples/chandra_testing/main_test.py`, `examples/gemma_testing/main.py`) now stamp the run's
  timestamped log directory **once**, in `__main__`, *before* `model_init()` spawns `VLLMService`.
  Previously the timestamp was stamped inside `main_cli()`, which only runs after the GPU process is
  already spawned — so at spawn time there was no final directory to hand it. `VLLMService(...,
  logs_dir=args.logs_path)` and `cli(..., run_specific_log_path_in_args=True)` now read the same,
  already-final directory. **Net effect: `vlm_service.log` lands in the same
  `{logs_path}/{hostname}/{timestamp}/` directory as every other component's log** — one place to
  `tail -f` for a whole run, GPU process included.

**On the side question (image-header validation cost).** Not a defect, no code changed. `read_header`
(`media.py:96`) only opens the file to call `Image.open(path).size`, which PIL reads lazily off the
header — it does not decode pixel data (`.load()` would). It only runs for `backend="online"`;
offline skips it because `load_cv2_pil` decodes the whole image immediately after anyway
(`vllm_config.py:149`). It also runs inside `reader_pool` (`vllm_config.py:474`), a
`ThreadPoolExecutor` sized by `args.local_json_threads`, driven from `prediction.py`'s prep thread —
concurrent with GPU inference, not serialized in front of it. It replaces a strictly more expensive
failure mode: before this, a bad image reached `vllm serve`, failed as an HTTP 400, and was retried
2 more times before the item failed — 3x the I/O for less information.

## Verification status

`scratchpad/verify.py` — **22 assertions, all passing**, against a stubbed `vllm` (no CUDA runtime on
the login node) plus the **real** chandra processor from `/hf_cache`:

- media validation: missing / outside-root / corrupt / zero-byte / relative / oversized each raise
  their own distinct error;
- `file://` round-trip through vLLM's own parser for 7 path shapes;
- serve-flag translation including `False → --no-<flag>`;
- payload-kind guard in both directions;
- `VLMHealth` reason reporting;
- end-to-end `VLMPrediction` vs a fake worker: dead backend raises `VLMServiceDown` and marks
  **nothing** failed; an unflagged dead backend still trips the fuse and marks nothing failed; a
  healthy backend still produces successes.

Real-model checks: online payload shape; offline payload with exactly one `<|image_pad|>` per attached
image; `is_llm` + image → fatal; over-`limit_mm_per_prompt` → fatal; missing file → per-item.

**Not verified — needs one GPU run before production:** the engine-side effect of
`async_scheduling: false`; the `vllm serve` launch path end to end (ephemeral port, `/v1/models`
check, `--no-async-scheduling` acceptance); real throughput.
