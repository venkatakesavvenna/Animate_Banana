# v1.8 — Payload unification, tagged responses, retry hooks

Implements `docs/v1.8_suggested_changes.md`. That proposal came out of a holistic review of the
contract between `prediction.py`, `vllm_config.py`, `vlm_service.py`, `async_worker.py`,
`online_worker.py`, `retry_validate.py` and `health.py`, asked for explicitly to find a *simpler
shape* rather than more guards bolted onto the v1.7 taxonomy.

The one-line summary: **v1.7 gave every silent failure mode its own explicit channel; v1.8 deletes
most of those channels by deleting the ambiguity they were guarding.**

| Removed in v1.8 | Because |
|---|---|
| `_payload_kind`, `assert_payload_kind()`, `BackendPayloadMismatch` | there is one payload shape, so nothing can mismatch |
| `VLLMConfig(backend=...)` and its split prompt building | the worker decides what its engine needs |
| `_OnlineOutput` / `_OnlineCompletion` / `_OnlineFailure` shims | the worker says what happened instead of impersonating a `RequestOutput` |
| `type(pred).__name__ == "_OnlineFailure"` string match, `.usage` duck-typing | replaced by `response.kind` |
| `post_process_full_vllm_object()` | the worker builds the stats dict from what it already knew |
| `retry_validate.collect()` | dead since v1.5 |
| `VLLMConfig._assert_image_placeholders()` | vLLM's own multimodal processor enforces it |
| `VLLMService(allowed_media_roots=...)` | now travels inside `engine_args` as vLLM's own arg |

---

## 1. One payload shape (§1)

**Before.** The stage decided the wire payload's shape from `args.backend`, so two processes had to
agree about that string through two independent call chains (`main.py -> VLLMService` and
`cli.py -> VLLMConfig -> VLMPrediction`). Online got raw text + image paths. Async/batch got a
fully chat-templated string with 3–12 MB of decoded PIL image embedded. Disagreement silently
dropped the images and the model answered from the text alone — the single most confusing failure
this pipeline has had, because it looks like a model quality problem. v1.7 had to *add* the
`_payload_kind` stamp to make that loud.

**Now.** `VLLMConfig.get_prompt_with_image()` returns the same dict for every backend:

```python
{"prompt": <raw user text>, "image_paths": [<abs path>, ...], "enable_thinking": bool}
```

Not templated, no pixels. The worker turns it into what its engine needs, using **vLLM's own
code**:

| Backend | How it renders |
|---|---|
| `online` | `POST /v1/chat/completions` with `file://` image URLs — the server templates and reads files, unchanged from v1.6 |
| `async` | `await engine.renderer.render_chat_async(...)` — literally the call `vllm serve` makes internally (`entrypoints/serve/render/serving.py: preprocess_chat`) |
| `batch` | `LLM.chat(...)` — vLLM's public messages → engine-input → generate path, which uses the same renderer |

`wire.build_chat_messages()` builds the OpenAI-style message list once and all three share it.

**Why this matters beyond tidiness:** online and offline now run *identical* templating code. Before,
they only agreed by coincidence — chandra ships a standalone `chat_template.jinja` that differs from
its `tokenizer_config.json` template, and the two agree only for `enable_thinking=False`
(v1.7 issue 7). That divergence is now structurally impossible.

### Consequences
- **Image decode moved into the worker**, which is where every backend already needed it.
- **`allowed_media_roots` is now required for any vision model on every backend**, not just online.
  vLLM's `MediaConnector` refuses every `file://` URL unless `allowed_local_media_path` is set,
  in-process just as much as in `vllm serve`.
- **Stage-side validation stayed exactly where it was** (`media.py`), and got *stricter*:
  `read_header` is now unconditional, because the stage no longer decodes an image anywhere, so this
  is the only local chance to reject a corrupt or oversized file on any backend. A bad image is
  still one terminal per-item failure with a reason, before submission.
- **shm is now vestigial.** It exists because offline prompts embedded decoded PIL images and the
  kernel copy through `mp.Queue` dominated everything. Requests are paths + text now. It is left in
  place and still works (`use_shm` defaults to `False`), but it no longer has a workload that
  justifies it — deleting the subsystem is a clean follow-up, deliberately not bundled here.

## 2. Tagged responses at the source (§2)

**Before.** The response was an untyped union the stage had to reverse-engineer: `None` meant infra
failure, an `_OnlineFailure` was detected by `type(pred).__name__` (a string match), an answer by
duck-typing `pred.outputs[0].text`, and `.usage` distinguished the online shim from a real offline
`RequestOutput`.

**Now** every worker emits `VLLMResponse(req_id, kind, text, stats, error)` with
`kind ∈ {ok, reject, infra}` (`vllm_module/wire.py`), and `stats` built by the worker from what it
already knew firsthand. `_validate_one` shrank to the one decision a worker genuinely cannot make:
does this output pass *this task's* `validate_output`.

**The real bug this fixes** is that the taxonomy's population used to be backend-dependent. A prompt
over `max_model_len` was:

- online → a 400, tagged `reject`, failed once with the server's explanation. Correct.
- offline → a bare `None`, retried through all 5 infra attempts it could never pass, then logged as
  a **backend** failure. Same input, opposite classification, purely because of which backend ran it.

Both now report `reject` with the message.

`stats_from_usage()` / `stats_from_request_output()` produce key-identical dicts, so
`full_vlm_object` and `PipelineMetrics` read the same on every backend. `mm_tokens` is still
online-only — vLLM's offline `RequestOutput` exposes no per-modality breakdown.

## 3. Retry customization → `project_specific.py` (§3)

`prediction.py` used to hardcode "append the error to the prompt" and "+0.5 `repetition_penalty` per
attempt" for every project regardless of task. That is now
`PromptAndValidation.build_retry_request(sent_prompt, sampling_params, attempt, last_error)`, with a
default that reproduces the old behaviour exactly — no project has to opt in to keep working.

A project can now lower temperature instead, switch instructions on attempt 2, add few-shot
correction examples, or drop the penalty bump for OCR — where the old default is genuinely harmful:
attempt 2 ran at `repetition_penalty ≈ 2.0`, which actively degrades long-form transcription.

**`prediction.py` still owns copy-safety.** The hook receives `dict(rec["orig_prompt"])` and
`copy.deepcopy(base_sp)` — never the originals. `base_sampling_params` is resolved once per
`VLMPrediction` and reused for every record forever, so an override that mutated it in place would
silently corrupt every subsequent *fresh* attempt, not just its own retry.

### Defect 2, fixed for free
`_build_send_prompt` appended `"Previous attempt failed: ..."` to `orig_prompt["prompt"]`. Online
that was raw text, so the server templated it into the user turn — correct. **Offline it was the
already-templated string ending in the generation prompt** (e.g. `<|im_start|>assistant\n`), so the
error text landed *inside the assistant turn*, after the point where the model starts answering.
Retries were materially different requests on the two backends. Since the payload is now raw text
everywhere and templating happens strictly afterwards, the append always lands in the user turn.

## 4. CPU/GPU overlap for the async backend (§4)

Moving decode + templating into `VLLMService` must not block the asyncio event loop, or the GPU
idles and we regress the exact overlap `prediction.py`'s prep/collector split provides.

The proposal suggested a bespoke `run_in_executor(self._prep_pool, ...)`. **That turned out to be
unnecessary** — vLLM's async render path is already fully off-loop, through three separate
executors:

| Step | Offloaded by |
|---|---|
| chat template | `HfRenderer._apply_chat_template_async = make_async(..., executor=self._executor)` |
| `file://` image load + decode | `MediaConnector.load_from_url_async` → `run_in_executor(global_thread_pool, ...)` |
| multimodal processor | `BaseRenderer._process_multimodal_async = make_async(..., executor=self._mm_executor)` |

So `await engine.renderer.render_chat_async(...)` gives the "some requests decoding on CPU while
others stream from the GPU" interleave for free, using the same machinery `vllm serve` uses at full
throughput in production, with no pool of ours to size or tune. Admission is still bounded from the
stage side by `desired_total = 3·batch_size`.

---

## 5. Batch backend (§5)

Deprioritized per the proposal — it is the legacy A/B timing baseline, not a recommended path.
It has no event loop (`LLM.chat()` is one blocking call per collected batch), so rendering happens
**inline, serialized, before generation**. That is a deliberate loss of overlap on this backend only;
double-buffering plumbing was explicitly out of scope.

Two things `chat_batch()` does that the old `model.generate()` call did not:

- **Groups by `enable_thinking`** so a mixed batch still templates each item the way its own payload
  asked for, instead of silently applying one setting to all of them.
- **Isolates a poison item.** A single unreadable image raises out of `chat()` for the *whole batch*.
  Failing a whole cohort for one bad item is exactly what the streaming backends were built to avoid,
  so on a batch-level failure the batch is retried one item at a time. This only runs on the failure
  path.

## 6. Defect 1 — online config errors aborted nothing

Any `_build_chat_payload` exception became `_OnlineFailure(0, ...)` → `reject` → immediate terminal
failure, **per item**, resetting `_consecutive_infra` each time. A `structured_outputs`
misconfiguration therefore marched the whole dataset into state=3 at full speed — the precise failure
mode v1.7 was built to stop, because a config mistake fails every image identically.

Fixed at the only place it can be fixed properly: **startup**.
`VLMPrediction._check_backend_supports_sampling_params()` resolves the sampling params once in
`__init__` and refuses `structured_outputs` + `backend="online"` before a single row is fetched. The
check inside `online_worker` is kept as an unreachable backstop, and any *other* body-build failure
is now reported as `infra` (retried, then the fuse trips) rather than as a per-item rejection.

## 7. Two latent bugs found while implementing

Neither was in the proposal; both were found by reading vLLM 0.19's source while wiring this up.

**a) A second `--allowed-local-media-path` silently overwrote the first.** vLLM models this as a
single `str` (`config/model.py: allowed_local_media_path: str`), on both the engine config and the
serve CLI. `online_worker._launch_server` looped over `allowed_media_roots` appending the flag once
per root — so only the **last** root was ever in force. `examples/chandra_testing` configures
`["/fsxvision_new", CHANDRA_SCRATCH_DIR]` and genuinely sends from both (it only rescales images
below its short-edge threshold, passing larger originals through untouched), which means **every
original under `/fsxvision_new` was being rejected by the server** with "must be a subpath of
--allowed-local-media-path".

Fixed by deriving vLLM's single value from `VLLMConfig.engine_media_root()`: one root is passed
through as-is; several are collapsed to their common ancestor, and `cli()` logs a warning naming the
widening. This is safe because the two checks are not peers — *this* process validates every path
against the exact root list before submitting, so nothing outside them is ever sent, and vLLM's
check is a backstop on a server we launched ourselves, on localhost, against paths we already vetted.

**b) Engine-death detection was load-bearing in a newly dangerous place.** In v1.8 the batch backend
classifies a non-engine-dead exception as `reject`, which is **terminal**. If `_is_engine_dead_error`
missed a real engine death, the batch backend would mark real, untried images FAILED. Two fixes:

- The text heuristic now matches `"enginecore"` (one word), which is what `EngineDeadError` actually
  says — `"EngineCore encountered an issue. See stack trace (above) for the root cause."` The old
  `"engine core" and "died"` pairing matched neither half of that.
- `chat_batch()` downgrades every `reject` to `infra` when **nothing in the batch succeeded**. Same
  evidence rule `prediction.py` already uses: blaming the inputs requires proof the engine is
  otherwise fine. The asymmetry justifies it — a wrong `reject` is unrecoverable, a wrong `infra`
  costs one retry and then trips the fuse with every path still replayable.

## Not changed

- `health.py`'s `dead_event`/`proc`/`reason` machinery, the consecutive-infra fuse, and the
  `others_are_working` condition. Tagged responses shrink how often the heuristics fire; they do not
  replace them (SIGKILL, unwired health, one poison item on a healthy backend).
- The `_owned` conservation counter, the writer commit protocol, and `run_iteration`'s return
  conditions — clean and correct as designed.
- The shm subsystem. Now unjustified rather than wrong; see §1.

## Migration

Existing `main.py` files need two mechanical edits:

```diff
-cfg_model = VLLMConfig(args.vlm_model_name, args.vlm_config_path,
-                       backend=args.backend,
-                       allowed_media_roots=args.allowed_media_roots)
+cfg_model = VLLMConfig(args.vlm_model_name, args.vlm_config_path,
+                       allowed_media_roots=args.allowed_media_roots)

 vllm_proc = VLLMService(
     ...,
-    allowed_media_roots = args.allowed_media_roots,
     logs_dir            = args.logs_path,
 )
```

`args.backend` is still needed — `VLLMService` uses it to pick a worker and `cli()` passes it to
`VLMPrediction` for the startup capability check. `args.allowed_media_roots` becomes **required for
any vision model on every backend**, where before it was only enforced for `online`. Projects that
overrode nothing get the previous retry behaviour unchanged.
