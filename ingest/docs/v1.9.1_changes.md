# v1.9.1 — `VLMHealth` consolidation, `ServiceChannel`, StageWeaver integration

> **STATUS: IMPLEMENTED (2026-08-11), with three deviations — see "As built" below.** Resolves
> `docs/v1.7_stageweaver_gap.md` (open since v1.7 — see §4). The rest of this doc is the design as
> proposed; where the build diverged, the "As built" section is authoritative and `CHANGELOG.md`
> [1.9.1] records the shipped behaviour.
>
> ## As built — deviations from this proposal
>
> **1. `shutdown_event` is kept in the stage `function` signature.** §4.2 proposes
> `function(args, channel, router_coordinator, stage_specific_log_dir)`, silently dropping the
> `shutdown_event` the old signature carried. That is not a safe simplification: `shutdown_event` is
> created *per stage process* and set by that process's own SIGTERM handler — it means "stop this
> stage loop", which is a different question from `stop_event`'s "stop the group's shared resource".
> Folding a per-stage event onto a group-wide object that is pickled once per spawn would be a
> category error, and dropping it outright would break graceful shutdown outright: it is what lets a
> stage reset its in-flight rows from state=1 instead of stranding them. Shipped signature:
>
>     function(args, channel, shutdown_event, router_coordinator, stage_specific_log_dir)
>
> **2. The per-rank `mp.Array` is lock-free (`lock=False`).** §1 shows a plain `mp.Array`, whose
> default lock is a POSIX semaphore. A process SIGKILLed while holding that lock never releases it,
> so every later reader blocks forever — which would poison precisely the code path §3 exists to
> serve: `failure_reason()` asking "was the backend SIGKILLed?" would itself hang on the dead
> process's lock. A heartbeat that can be killed by the kill it is watching for is worse than no
> heartbeat. No lock is needed anyway, because access is single-writer per rank; the reasoning and
> the two benign mid-update orderings are documented in `health.py`.
>
> **3. `ServiceChannel` is defined in StageWeaver, not here.** §0 lists it under this repo's files,
> but StageWeaver must construct it and depends on nothing. StageWeaver therefore owns a bare
> four-field dataclass, and `vision_ingest.core.channel.ServiceChannel.adopt()` wraps whatever
> `cli()` is handed — so the conveniences exist on exactly one side of the dependency boundary and
> there is no parallel surface to drift. `build_channel()` here serves standalone runs, which never
> involve StageWeaver at all.
>
> ### Open questions (§6), as resolved
>
> - **Q1 — constructor shape:** resolved as the doc leaned. `VLLMService`/`FunctionService` keep
>   their explicit parameters (a constructor is not a process boundary that must survive a pickle),
>   plus a `from_channel()` classmethod that removes the call-site boilerplate.
> - **Q2 — `STALE_S`:** shipped at 30s, still an instinct rather than a measurement. **Open.**
> - **Q3 — ceiling on `max_inflight_per_worker`:** yes. `WorkerSpec.resolved_max_inflight()` rejects
>   anything above 512 at construction, mirroring `resolved_n_workers()`.
> - **Q4 — migration order:** shipped together, as one breaking release across both repos.
> - **Q5 — validation:** the two rows of §4.3's table were reproduced without GPUs, using a harness
>   that recreates StageWeaver's exact topology (main → group leader → {backend, stage worker},
>   `spawn` throughout). Cooperative death now reaches the stage worker with a specific reason in
>   ~1s; a SIGKILL is detected there in ~32s via heartbeat staleness, where it previously hung
>   forever. The scripted-kill test against a **real** vLLM backend still has not been run.
>
> **What this touches, at a glance:**
>
> | Piece | Where |
> |---|---|
> | Unified per-rank health/in-flight structure | `vllm_module/health.py` (`VLMHealth`) |
> | In-flight ledger, scoped to the worker pool | `core/service.py` (`FunctionService`, `WorkerSpec`) |
> | Heartbeat liveness | `core/service.py` (`_worker_main`), `vllm_module/vlm_service.py` |
> | `ServiceChannel` | new, likely `vllm_module/health.py` or a new small module |
> | Every `main.py` under `examples/` | rebuild the shared-primitive block around `ServiceChannel` |
> | `drivers/cli.py`, `modules/prediction.py` | drop `shm_name`/`free_slots` params, read `vlm_health` off the channel |
> | `shm/` subsystem | **deleted** |
> | `../StageWeaver/src/stageweaver/db_pipeline.py` | locked signatures change shape (breaking, see §4) |

## 0. Why this is needed

Two independent findings, from tracing `VLMHealth` end to end while extending it for v1.9's
worker-pool model:

**A correctness bug in the v1.9 in-flight tracker.** `VLMHealth._inflight` was one fixed-size slot
per rank — `set_inflight` overwrites it unconditionally, `clear_inflight(rank)` blanks it with no
`req_id` to check. If a worker ever holds more than one request at once (internal micro-batching, an
async/threaded worker — nothing today does this, but `WorkerSpec` was written with SAM3/YOLO in mind,
which naturally want to), a second checkout silently destroys the first's recovery record with no
error. Exactly the failure mode the mechanism exists to prevent, just moved one layer down.

**`vlm_health` never reaches StageWeaver at all**, and has not since v1.7. `docs/v1.7_stageweaver_gap.md`
found this already: `init_fn`/`term_fn`/stage `function` are locked, flat, positional signatures with
no slot for it, so under StageWeaver `cli()` always runs with `vlm_health=None` — silently, because
every consumer treats it as optional. Both the readiness wait (`cli.py:358`) and crash detection
(`prediction.py:633`) are dead code in that deployment; only the heuristic consecutive-failure fuse
protects the DB. That doc left the fix as "options, not yet decided." This doc decides them — see §4.

Chasing both down surfaced a third, structural issue: `VLMHealth` is nine attributes spread across
three different sharing mechanisms (`mp.Event`/`mp.Value`/`mp.Array`, a `Manager()` dict added and then
reverted, two attrs manually stripped from every pickle), two of which (`dead_event`/`ready_event`) turn
out to be pure derived state that's been hand-synchronized for no behavioral reason, and one of which
(`proc`/`procs`-based hard-kill detection) only works in the one process that happens to hold the live
`Process` object — which is never the process StageWeaver runs `cli()` in.

**v1.9 also left `shm` alone deliberately** — its own doc scoped that out to keep the blast radius
down (`docs/v1.9_changes.md` §0: *"Deleting the vestigial `shm` subsystem... would widen the blast
radius for no benefit, and `shm_name`/`free_slots` are still part of StageWeaver's locked 8-arg stage
signature."*). This proposal is already breaking those signatures for `vlm_health`, so that condition
no longer holds — dropping `shm` here is strictly cheaper than a second migration later.

## 1. One shared structure instead of nine attributes

Everything `VLMHealth` tracks is per-rank. It collapses into one `mp.Array` of a ctypes structure,
one entry per rank, built through a small factory so the in-flight capacity (§2) can vary per
instance:

```python
def _make_rank_state(k: int):
    class _RankState(ctypes.Structure):
        _fields_ = [
            ("ready",      c_int8),               # latches 1, never cleared
            ("dead",       c_int8),                # cooperative: worker's own finally ran
            ("reason",     c_int8),                # REASON_* for THIS rank
            ("heartbeat",  c_double),              # monotonic() of last tick — see §3
            ("n_inflight", c_int16),
            ("req_ids",    (c_char * 37) * k),     # exact — uuid4 is always 36 chars + NUL
            ("stages",     (c_char * 256) * k),    # parallel array, generous headroom
        ]
    return _RankState

self._ranks = mp.Array(_make_rank_state(max_inflight_per_rank), n_workers)
```

`dead_event`, `ready_event`, and the standalone `_reason` are deleted. Both events are pure aggregates
over the per-rank flags (`is_ready() == all(r.ready)`, `failure_reason() == all(r.dead or stale(r))`),
and **nothing in the codebase ever `.wait()`s on either one** — every consumer polls
(`cli.py:358`'s `while not vlm_health.is_ready(): ... sleep(1.0)`, because it has to interleave the
readiness check with `shutdown_event` and `failure_reason()` anyway, so it couldn't use `.wait()` even
if the event exposed one). So computing the aggregate on read is behaviorally identical and deletes
the two-step lock dance in every `mark_*` method, plus `mark_alive`'s trickiest piece of logic — the
manual un-latch of `dead_event` and rollback of `_reason` to `REASON_UNKNOWN`, which no longer has
anything to desynchronize from.

`req_ids`/`stages` are **separate fixed-width parallel arrays**, not one delimited blob (today's
`b"<req_id>\x00<stage_name>"` encoding). `req_id` is always exactly 36 characters — `str(uuid4())`,
verified, zero variance — so a 37-byte field can never truncate it. `stage_name` has no length
constraint anywhere in `StageConfig` (`StageWeaver/datamodels.py:19` is a bare `name: str`), so it's
the one actually-variable field; keeping it in its own array means an oversized name can only ever
truncate itself, never corrupt or collide with a `req_id`. (Separately worth adding: a length check on
`StageConfig.name` at config-creation time, so an oversized name fails loudly at startup instead of
silently truncating deep inside a crash-recovery path.)

## 2. In-flight ledger — `K` slots per rank, scoped to the worker pool only

`set_inflight(rank, req_id, stage_name)` / `clear_inflight(rank, req_id)` / `get_inflight(rank)` keep
their v1.9 shapes, generalized from 1 slot to `k` per rank. Overflow past `k` logs an error and drops
that one recovery record rather than silently overwriting another entry — loud, not silent, which is
the actual fix for the bug in §0.

**`k` (`max_inflight_per_rank`) is a constructor parameter, not a shared global constant**, and it
matters which `WorkerSpec` it comes from:

- **`FunctionService`**: `k = WorkerSpec.max_inflight_per_worker`, defaulting to `1` — today's exact
  real behavior for every worker that exists now, zero footprint change. A future worker that
  genuinely batches internally (GPU batch inference, a bounded `asyncio.Semaphore`) declares its own
  real ceiling here — the same number its own code already has to pick for GPU-memory/resource
  reasons. This is deliberately *not* derived from `batch_size` (`prediction.py`'s DB-fetch admission
  control — a different subsystem, tuned for a different reason, and not even a single value when
  multiple stages with different `batch_size`s share one `FunctionService` pool under one StageWeaver
  `init_source` group) and *not* one large flat constant shared by everyone (a ceiling generous enough
  to "never matter" is also generous enough that a real bug — a leaked semaphore permit inflating
  concurrency 5–10x — sails through undetected; the whole point of `k` is that hitting it is a signal
  worth logging).
- **`VLLMService`**: `k = 1` (or effectively unused — `n_inflight` sits at `0` forever). Confirmed by
  grep: `async_worker.py`/`online_worker.py`/`vlm_service.py` never call `set_inflight` today, and
  shouldn't. `VLLMService` is always `n_workers=1`, so any death is total death — already handled
  correctly by the existing coarse path (`dead_event` fires, `VLMServiceDown` propagates, `cli.py`'s
  `finally` resets every state=1 row). There's no "recover this rank's share while N-1 keep running"
  scenario for a single process. AsyncLLM's real concurrency (`desired_total = 3·batch_size`, entirely
  client-driven, easily in the hundreds) isn't a per-process resource ceiling a worker author picks —
  it has no stable value to assign `k`, so it doesn't get one.

## 3. Heartbeat — fixing hard-kill detection across the process boundary

Every worker (either backend family) runs one daemon thread that writes `monotonic()` into its own
rank slot every ~1s, independent of whatever it's actually doing:

```
dead(rank)  =  ranks[rank].dead == True                      # cooperative
            or  now - ranks[rank].heartbeat > STALE_S         # inferred
```

This is what actually closes the gap `docs/v1.7_stageweaver_gap.md` identified and left open: hard-kill
detection today runs through `attach_process`/`_all_procs_exited()`, which needs a live `Process`
object — and `Process` objects don't survive a pickle (`__getstate__` strips `proc`/`procs` to
`None`/`{}` on purpose, because a `Process` handle only means something in the process that started
it). Under StageWeaver that's the group leader; `cli()` runs in a separately-spawned StageWorker, so
today `_all_procs_exited()` there is permanently `False` — not an error, just silently inert. A
heartbeat is read from the shared array, which *does* survive pickling across `spawn` (verified two
levels deep: main → group leader → leaf worker), so `failure_reason()` gives the same correct answer
in any process — a SIGKILL simply means the ticks stop, and any reader notices after `STALE_S`.

`attach_process`/`attach_worker_process` are **not removed** — wherever a live `Process` object is
still available (the group leader itself, standalone's `__main__`), it stays as a faster, more precise
corroborating signal (exact exit code, no `STALE_S` wait). The heartbeat is the baseline guarantee that
works everywhere; `Process`-liveness is an accelerant where it happens to be available. `STALE_S`
should be generous (~30s) — a worker blocked in GIL-holding C code could miss ticks, so this is a
backstop for "gone," not a tight SLA; the cooperative `dead` flag stays the fast path for ordinary
Python-level crashes.

## 4. StageWeaver

This section is the resolution to `docs/v1.7_stageweaver_gap.md`'s open options — specifically a
combination of its options 1 and 2, generalized to also cover `shm` removal and to use the heartbeat
from §3 instead of requiring the group leader to run its own liveness-watch thread.

### 4.1 The gap, restated

`init_fn`, `term_fn`, and stage `function` are locked, flat, positional signatures
(`StageWeaver/CLAUDE.md`):

```
init_fn(args, logger, request_queue, response_queues, stop_event, shm_name, free_slots) -> init_vars
term_fn(init_vars, stop_event) -> None
function(args, request_queue, response_queue, shutdown_event, router_coordinator,
         stage_specific_log_dir, shm_name, free_slots) -> None
```

Nine years — sorry, nine *arguments* — of shared primitives threaded by hand through
`_group_leader_worker` and `_stage_worker` in `db_pipeline.py`, with no slot for `vlm_health` and two
slots (`shm_name`, `free_slots`) carrying a subsystem v1.8 already marked vestigial. Every future
shared primitive costs the same three-signature edit this doc is now paying for `vlm_health`.

### 4.2 The fix: `ServiceChannel`

```python
@dataclass
class ServiceChannel:
    request_queue: mp.Queue
    response_queues: Dict[str, mp.Queue]
    stop_event: mp.Event
    extras: dict = field(default_factory=dict)
```

New locked shape:

```
init_fn(args, logger, channel: ServiceChannel) -> init_vars
term_fn(init_vars, stop_event) -> None
function(args, channel: ServiceChannel, router_coordinator, stage_specific_log_dir) -> None
```

`_group_leader_worker` (`db_pipeline.py:135-`) creates `ServiceChannel` at the same point it creates
`request_queue`/`response_queues`/`stop_event` today (`:175-177`) — still inside the group-leader
process, still before any spawn, so `spawn`'s fd-inheritance requirement is unaffected. `init_fn` (VIE
code, e.g. `model_init`) populates `channel.extras["health"] = VLMHealth(n_workers=..., max_inflight_per_rank=...)`.
Every `StageWorker` the group leader spawns afterward (`:209-224`) gets the *same*, now-populated
channel object — verified experimentally that shared primitives (an `mp.Manager` `DictProxy` in the
test, but the same guarantee covers `mp.Array`/`mp.Event`) survive two spawn levels (main → group
leader → leaf worker) intact.

This preserves StageWeaver's "imports nothing from VIE" rule (`CLAUDE.md:137`) — the framework only
ever sees an opaque `dict` in `extras`; it never needs to know `VLMHealth` exists. A future shared
primitive is an `extras` key, not a fourth locked-signature migration.

### 4.3 What this fixes, against the v1.7 table

| Failure mode | Before this doc | After |
|---|---|---|
| Cooperative death (engine exception, `vllm serve` exit, ...) | Standalone: immediate, specific reason. StageWeaver: heuristic fuse only (`vlm_health=None`) | Both: immediate, specific reason — `vlm_health` now reaches `cli()` via `channel.extras` |
| SIGKILL / OOM-kill | Standalone: `attach_process` catches it. StageWeaver: **hangs forever** — `_all_procs_exited()` is unreachable from a StageWorker | Both: heartbeat staleness catches it from *any* process, §3 — no longer depends on which process holds the live `Process` object |

### 4.4 `shm` removal, folded in

`shm_name`/`free_slots` drop out of all three locked signatures. `init_fn`/`term_fn` no longer
construct or unlink an `Shm` block; `cli()`/`VLMPrediction` no longer accept `shm_name`/`free_slots`
params. This also removes a chunk of the asymmetry `CLAUDE.md` currently documents between standalone's
`model_term()` (which owns `Shm` creation *and* `cancel_join_thread()` itself, single-process) and
StageWeaver's `term_fn` (trimmed, because the group leader owns queue cleanup) — with `shm` gone, both
paths converge on "clean up the queues in whichever process created them," closer to one shared
implementation than two hand-maintained variants.

### 4.5 Standalone convergence

`examples/*/main.py` gets the identical `ServiceChannel` treatment, not just StageWeaver — `__main__`
builds one `channel` instead of eight loose locals, `model_init`/`pool_init` become
`(args, logger, channel) -> vllm_proc`, `model_term` drops its `shm`/`free_slots` params. Standalone
doesn't need to rename these to `init_fn`/`term_fn` — it calls them directly, it isn't going through
StageWeaver's serialized-callable dispatch — only the *shape* (one channel carrying the shared
primitives) needs to match. This closes an asymmetry that existed for its own reasons (`shm` ownership
splitting the two `model_term`/`term_fn` variants) rather than a technical necessity.

Open, not decided here: whether `VLLMService.__init__`/`FunctionService.__init__` should also accept
`ServiceChannel` directly, or keep unpacking `request_queue`/`response_queues`/`stop_event`/`vlm_health`
as today. Leaning toward the latter — those constructors are internal, not a process boundary that
needs to survive a pickle, so there's less reason to force the bundle past that point. Decide when
building.

## 5. Net effect

| | Before | After |
|---|---|---|
| Shared primitives inside `VLMHealth` | 5 + `Manager` process + proxy | 1 array |
| Extra processes per `VLMHealth` | 1 (`Manager` server) | 0 |
| Per-worker in-flight tracking | 1 slot, silent overwrite above that | `k` per `WorkerSpec`, loud log above that |
| Hard-kill detection | only in the process holding the live `Process` object | any process, via heartbeat |
| `vlm_health` reaches StageWeaver | ❌ (`docs/v1.7_stageweaver_gap.md`) | ✅ via `ServiceChannel.extras` |
| `shm_name`/`free_slots` | threaded through every signature, unused since v1.8 | gone |
| `init_fn`/`term_fn`/stage `function` | 7–8 flat positional args | `(args, logger, channel) -> init_vars` shape |

## 6. Open questions

Recorded so the build doesn't have to re-litigate these; none are blocking, but they're unresolved.

1. **`VLLMService`/`FunctionService` constructor shape** — take `ServiceChannel` directly, or keep
   unpacking? See §4.5.
2. **`STALE_S`'s actual value** — 30s was a starting instinct, not measured against any real worker's
   worst-case GIL-holding call. Worth checking against whatever `call_fn` implementations actually land
   first (chrome rendering, SAM3).
3. **Absolute sanity ceiling on `max_inflight_per_worker`** — should `WorkerSpec` reject a clearly-absurd
   declared value (e.g. > 512) at construction time, the way `resolved_n_workers()` already rejects a
   `devices`/`n_workers` mismatch?
4. **Migration order** — `VLMHealth` internals (§1–§3) don't depend on `ServiceChannel` (§4) or vice
   versa; they could land as two separate passes. Worth deciding whether to ship them together or
   sequence them, given §4 is the breaking one across two repos.
5. **No automated test suite exists in this repo** (`CLAUDE.md`: correctness is validated by running
   the actual pipeline). Whatever validates this should include, at minimum, the same scripted-kill
   test `docs/v1.7_stageweaver_gap.md` proposed and never ran: kill `VLLMService`/a `FunctionService`
   worker both gracefully and via `SIGKILL`, under both standalone and StageWeaver, confirm the correct
   abort/recovery path fires within `STALE_S` instead of hanging.
