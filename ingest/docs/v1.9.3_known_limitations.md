## The finding

Patram-Ingest maintains two representations of per-image state in every stage DB:

1. **`images.state`** — the real, authoritative per-row state (`0..4`). Every consumer
   that actually *does* work (`fetch_and_lock_batch`, the DAG's cross-stage handoff)
   reads/writes this table directly. It is always correct.
2. **`state_counts`** — a denormalized cache, one row per state, maintained by manual
   `+N`/`-N` UPDATEs alongside every state transition (`db/db_postgres/db_queries.py`:
   `insert_paths_batch` :72-111, `copy_paths_batch` :114-152, `fetch_and_lock_batch`
   :159-213, `mark_state_transition` :216-263). It exists so `get_state_count()`
   (`db.py:233`) doesn't run `SELECT state, COUNT(*) FROM images GROUP BY state` on a
   100M+ row table on every poll — `get_state_distribution` (`db_postgres/db_queries.py
   :270-279`) just does `SELECT state, count FROM state_counts ORDER BY state`.

**`state_counts` is a private implementation detail of Patram-Ingest.** Every write to it
happens inside the same four helper functions above, all of them called from *inside*
Patram-Ingest's own code paths (ingest, `fetch_batch`, `mark_done`/`mark_failed`).

StageWeaver's cross-DB stage handoff does not go through any of those helpers. When
`RouterSweep` (or a `routing_fn`) activates a downstream stage, it calls
`RouterCoordinator._batch_activate_stages()` (`StageWeaver/src/stageweaver/
router_coordinator/dag_pipeline.py:416-472`), which calls
`RouterDB.stage_db_batch_write_fetch_state_4()` (`router_db/db.py:293-320`), which runs
a **raw SQL UPDATE straight against the downstream stage's `images` table**
(`router_db/db_queries.py:389-396`):

```sql
UPDATE images
SET state = 4
WHERE path = ANY(%s) AND state = 0
```

This is correct and sufficient for `images` — StageWeaver has no reason to know
`state_counts` exists, it's on the other side of a deliberate package boundary (per
StageWeaver's own CLAUDE.md: *"VIE has no knowledge of what's upstream or downstream. It
just processes whatever rows its own DB presents"* — the coupling is intentionally
one-directional). But it means **every StageWeaver-driven 0→4 promotion silently
desyncs `state_counts` from reality**: `state_counts[0]` is never decremented and
`state_counts[4]` is never incremented for those rows.

### Empirical proof (not a synthetic repro)

3-image smoke run through `src/digital_twin`, `html_gen` stage (`fetch_state=4`), after
every image reached `state=2` (done):

```
images (real per-row state):                       [(2, 3)]
state_counts (what get_state_count() actually reads): [(0, 3), (1, 0), (2, 3), (3, 0), (4, -3)]
```

`state_counts[0]` is stuck at 3 — the original ingest count, never decremented, because
the 0→4 promotion (StageWeaver's write) doesn't touch it. `state_counts[4]` is **-3** —
`fetch_and_lock_batch`'s own bookkeeping (`db_postgres/db_queries.py:201-206`) correctly
decremented it by 3 when it fetched those rows, but it decremented from a stale 0 (since
nothing had ever incremented it for the promotion), so it went negative instead of
correctly landing at 0.

### Why every downstream stage hangs forever

`cli_utils.py:process_pipeline()`'s only exit path (`cli_utils.py:232-245`):

```python
if not fresh_paths and pending == 0 and inflight == 0 and in_prep == 0:
    no_pending = db.get_state_count(0) == 0
    no_fetchable = db.fetch_state == 0 or db.get_state_count(db.fetch_state) == 0
    if no_pending and no_fetchable:
        main_logger.logger.warning("No data to fetch, pools empty, nothing in flight; "
                                    "no rows remain in pending or fetchable states. "
                                    "Exiting main loop.")
        break
    ...
    time.sleep(1)
    continue
```

For a downstream stage (`fetch_state=4`), both `db.get_state_count(0) == 0` and
`db.get_state_count(4) == 0` read `state_counts`, and per the proof above they read `3`
and `-3` respectively — **never zero, permanently**, no matter how long the run
continues or how many images actually finish. So the `break` can never fire; the stage
sleeps 1s and polls forever, logging `"Waited N seconds for new data..."` (throttled to
once per 50) indefinitely, even after 100% of its images have reached `state=2`.

**Root stages are unaffected.** For `fetch_state=0`, `no_fetchable` short-circuits to
`True` via `db.fetch_state == 0` without ever reading `state_counts[4]`, and
`state_counts[0]` *is* accurate for a root stage — nothing ever cross-DB-writes into a
root stage's `images` table, so its own `insert_paths_batch`/`fetch_and_lock_batch`
bookkeeping is the only thing that ever touches its `state_counts`, and that bookkeeping
is internally consistent. This is exactly what was observed: in a real run, `layout`
(root, `fetch_state=0`) logged `"Exiting main loop"` and `pipeline_stopped` /
`reason: complete` within ~12 seconds of finishing its 3 images; `html_gen`,
`replace_placeholders`, and `render` (all `fetch_state=4`) never did, in two separate
full runs, one of them left polling for over 20 minutes past completion before being
killed by hand.

### Why this doesn't corrupt anything

Nothing about correctness is at risk — this is purely a self-exit / liveness-reporting
bug:

- The DAG handoff itself reads/writes `images.state` directly, never `state_counts`, so
  activation, fetching, and downstream processing all work correctly regardless.
- `fetch_and_lock_batch`'s `FOR UPDATE SKIP LOCKED` guarantees no double-fetch, so no
  duplicate processing results from this.
- No image is ever lost, silently dropped, or double-counted in output — every image in
  this session's test runs reached `state=2` with correct JSONL + `write_local_json`
  output.
- The stage DB's own `get_db_health()` report (used in `main.log`'s
  `pipeline_started`/checkpoint log entries) reads the same stale `state_counts`, so
  **operator-facing health reporting is also wrong** for downstream stages once
  StageWeaver has promoted rows into them — this is the practical, user-visible
  consequence, not data loss.
- A StageWeaver-orchestrated downstream stage process will **never exit on its own**.
  In production this mostly doesn't matter (the process is meant to run forever,
  polling for new work — see `StageWeaver/CLAUDE.md`'s process-layout section), but it
  means:
  - There is no automatic "the pipeline is done, all processes exited" signal for a
    downstream stage. Completion has to be inferred from the stage DBs' real `state=2`
    counts (query `images` directly, not `get_state_count`/`get_db_health`), or from
    watching JSONL/output files, not from the process exiting.
  - A short test/smoke run has to be torn down by hand (SIGTERM the top-level `main.py`
    process) rather than letting it finish and exit — which is exactly what happened
    debugging this: the first affected run had to be killed manually after 20+ minutes
    of harmless-looking `"Waited N seconds"` polling.

### Relationship to the existing "routing-target stages never complete" limitation

`StageWeaver/CLAUDE.md` already documents a different, narrower gap in the same area:
seeding every stage DB at `state=0` up front means a `routing_fn` target that only ever
receives a *subset* of images leaves the rest stuck at `state=0` in that stage's DB
forever, so `no_pending` never passes for it either. **This is a separate root cause** —
that one is a real, permanent `state=0` count in `images` itself (never promoted at
all); this doc's bug is a `state_counts` *cache* drifting from an `images` table that is
itself completely correct. Both land on the same symptom (`process_pipeline` never
exits) via the same two-line exit check, so a proper fix likely wants to address both at
once — see options below.

## Options, not yet chosen

1. **Have `stage_db_batch_write_fetch_state_4` also touch `state_counts`.** Fixes it at
   the source, but couples StageWeaver's SQL to a Patram-Ingest-private table — the same
   kind of cross-package coupling both repos' CLAUDE.md files currently go out of their
   way to avoid ("VIE has no knowledge of what's upstream or downstream"). Would need
   `router_db/db_queries.py:389-396`'s `UPDATE` to become a `WITH picked AS (...)
   UPDATE ... RETURNING` (matching `fetch_and_lock_batch`'s shape) followed by two
   `UPDATE state_counts` calls keyed off the actual row count changed — mirrors
   `db_postgres/db_queries.py:191-206` almost exactly.
2. **Make `get_state_count`/`get_state_distribution` self-healing**: fall back to a live
   `SELECT state, COUNT(*) FROM images GROUP BY state` when a cached count is negative
   (a value that should be structurally impossible) or when explicitly asked to
   verify. `db/db_verification.py`'s `verify_counts`/`fix_count_drift` already exist for
   exactly this reconciliation (used today by `full-maintenance`/`verify` CLI commands
   and the constructor's `verify=True` flag) — this option is really "call that
   automatically when a downstream-stage's exit check is about to loop instead of only
   on request."
3. **Change the exit check itself to not depend on `state_counts` at all** for
   `fetch_state != 0` — e.g. a live, indexed `COUNT(*) FROM images WHERE state IN
   (0, fetch_state)` (the `idx_images_state` index this exact query needs already
   exists — `db_postgres/db_queries.py:41-43`) instead of reading the cache, since this
   check only runs when the loop is *already* about to sleep 1s (i.e. it is not a
   hot path — the cost of an occasional indexed count against even a 100M-row table is
   not the same order of cost the cache exists to avoid for `fetch_and_lock_batch`,
   which runs every iteration).
4. **Do nothing / document the limitation** if downstream stages are expected to always
   run as long-lived services that get torn down externally (matches
   `StageWeaver/CLAUDE.md`'s stated process model) and the wrong `get_db_health()`
   numbers in logs are judged low-risk. This is the status quo as of this doc.

Whatever is chosen should be validated by re-running the smoke test below and confirming
`html_gen`/`replace_placeholders`/`render` all log `"Exiting main loop"` /
`pipeline_stopped reason=complete`, not just `layout`.

## How to run this pipeline as a test (reproduction / validation steps)

This is the exact procedure used to find and confirm the bug above — kept here so the
fix (whichever option is chosen) can be validated the same way, and so this remains a
runnable repro rather than just a description.

### Prerequisites

- A container with `ocr_env_vllm` (editable-installed against this Patram-Ingest
  checkout and a matching StageWeaver checkout — **the two must be updated together**,
  per both CLAUDE.md files) and 8 free GPUs (Chandra takes 4, Qwen takes 4).
- `postgresql-16` client binaries on `PATH` (`initdb`/`pg_ctl` — on Ubuntu these live at
  `/usr/lib/postgresql/16/bin`, not on `PATH` by default; add it explicitly).
- Chrome + chromedriver reachable (`src/digital_twin/CLAUDE.md`'s "Infra notes" —
  headless Chrome's shared libs, `libatk-1.0.so.0` etc., must be installed system-wide
  if the historical `chrome-deps/` folder isn't present).

### 1. Start Postgres fresh

```bash
export PATH=/usr/lib/postgresql/16/bin:$PATH
rm -rf /opt/dlami/nvme/<user>/dtp_db   # wipe for a clean run; omit to keep history
python -m vision_ingest.drivers.db_driver_postgres serve \
    --data-dir /opt/dlami/nvme/<user>/dtp_db \
    --pg-host <NODE_IP> --pg-port 59511 \
    --pg-user pipeline --pg-dbname dtp_router
```

Runs in the foreground — launch detached (`nohup ... & disown`, or a separate
`docker exec -d`) and confirm with `psycopg.connect(...)` before continuing, not just by
checking the process is alive.

### 2. Point at the 3-image smoke set

`src/digital_twin/main.py`'s `IMAGES_TXT` should point at `images_smoke.txt` (3 images:
1 synthetic + 2 real gazette pages) rather than the 1024-image
`images_regular.txt` — and **`FSYNC_EVERY_LINES` must be small (1)** for a run this
size. At the production default of 256, the JSONL writer never crosses a fsync
boundary for only 3 images, so `DB.mark_done()` (which is what mask-triggers the next
stage) never fires and the run appears to hang for an unrelated reason before you ever
get to observe *this* bug. `src/digital_twin/main.py` already handles this:
`FSYNC_EVERY_LINES = 1 if IMAGES_TXT.endswith("images_smoke.txt") else 256`.

Set `ENABLE_TRANSLATION = False` for a plain 4-stage run
(`layout -> html_gen -> replace_placeholders -> render`).

### 3. Run it

```bash
export PATH=/usr/lib/postgresql/16/bin:$PATH
source /environments/ocr_env_vllm/bin/activate
cd src/digital_twin
python main.py 2>&1 | tee /tmp/main_run.log
```

Expect ~8 minutes for both `vllm serve` processes (Chandra 4 GPUs, Qwen 4 GPUs) to
finish loading weights before any image processing starts — this is normal, not a hang.

### 4. Confirm the pipeline itself works

```
grep "mask-triggered activation" /tmp/main_run.log
```
should show all four stages activated in order, each for all 3 items. Check
`outputs_new/render/*.png` exist at sane dimensions and `outputs_new/html_gen/*.html`
contains real generated markup (not empty/error placeholders).

### 5. Reproduce this specific bug

While `html_gen` (or any downstream stage) is confirmed fully done (all 3 images have
real output files), compare its real state against what the exit check sees:

```python
import psycopg
conn = psycopg.connect(host="<NODE_IP>", port="59511", dbname="dtp_s1_html_gen",
                        user="pipeline", autocommit=True)
cur = conn.cursor()
cur.execute("SELECT state, count(*) FROM images GROUP BY state ORDER BY state")
print("images (real):", cur.fetchall())          # expect [(2, 3)] once done
cur.execute("SELECT state, count FROM state_counts ORDER BY state")
print("state_counts (cached):", cur.fetchall())  # expect stale 0-count + negative 4-count
```

Then confirm the stage's own log never gained an `"Exiting main loop"` /
`pipeline_stopped` line (`grep -c "Exiting main loop" <logs>/1_html_gen/main.log`
should be `0`), while `layout`'s (`<logs>/0_layout/main.log`) has exactly one.

### 6. Tear down

The downstream stages will not exit on their own (that's this doc's bug) — send
`SIGTERM` to the top-level `main.py` process and wait for it to log a clean shutdown
before checking for stray processes. In practice this run leaked the `vllm serve`
process tree for `html_gen`'s Qwen server and all `render` worker processes past the
top-level `SIGTERM`, which needed a follow-up `pkill -f "vllm serve"` /
`pkill -f "spawn_main"` and a GPU-memory check (`nvidia-smi`) before starting a
second run — worth budgeting for in any validation pass, independent of whatever fix
is chosen for the bug above.
