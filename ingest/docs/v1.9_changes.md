> **STATUS: IMPLEMENTED.** This file was the proposal; it has been updated in place to describe
> what was actually built. The design survived contact with the code essentially intact — every
> section below shipped. Where the implementation diverged from the sketch, the section carries a
> **`SHIPPED:`** note saying so and why. §8 records what was actually verified, and what was not.
>
> **What landed, at a glance:**
>
> | Piece | Where |
> |---|---|
> | vLLM-optional import | `vllm_module/vllm.py` (`VLLM_AVAILABLE`) |
> | Opaque payload | `modules/prediction.py`, `vllm_module/wire.py` (`VLLMResponse.output`) |
> | `FunctionTask` / `InputRejected` | `core/task.py` |

> | Example | `examples/html_render/` |

Companion to `docs/v1.8_changes.md`. v1.8 unified the request payload and gave responses a
worker-decided `ok`/`reject`/`infra` kind. This document is about cashing in that unification: the
pipeline should be able to run **an ordinary Python function** — Set-of-Mark annotation, HTML→PNG
rendering through a headless browser, SAM3, a YOLO or HF model — with the same crash-safety, retry,
recovery and StageWeaver behaviour it already gives vLLM.

**The one-line summary: v1.9 does not add a second pipeline. It makes the payload opaque and adds a
second implementation of the process-side of the contract v1.8 already defined.**

---

## 0. Why this is a small change

`prediction.py` already talks to the backend *only* through `request_queue` / `response_queue` and
the `stage()` / `submit_token()` / `drain_available()` helpers. It never imports vLLM's engine.
`CLAUDE.md` states the consequence outright:

> Any inference backend (a plain Hugging Face model, an API call, ...) can replace vLLM as long as
> it consumes the v1.8 payload and emits a `VLLMResponse` — see `vllm_module/wire.py` for the whole
> contract. **The `"online"` backend is exactly this in practice.**

So the entire DB state machine, the write→fsync→router→mark_done commit protocol, `recovery.py`,
admission control (`_owned` / `fetch_n`), the retry and infra-failure taxonomy, `PipelineMetrics`,
and the StageWeaver hooks are all **unchanged in shape**. What is genuinely missing is only:

1. the payload and response are still *typed* as prompt-and-text, even though nothing structural
   requires it (§2);
2. there is exactly one backend process, where function work needs **N processes each holding its
   own resource** — a chrome driver, or a model replica pinned to its own GPU (§3);
3. `prediction.py` cannot be imported without vLLM installed (§1);
4. there is nowhere for **image bytes** to go (§5).

### Output rule, stated once

**The JSONL is always the output — every backend, every job.** Images are *additional*. Only images
go into folders-then-tars. A job may produce both: the image bytes land in a shard, and the JSONL
record says which shard and which member. Nothing about the JSONL mechanism, its shard rotation, its
fsync boundary, or its recovery changes.

### Explicitly out of scope

- **SAM3 itself.** §7 shows it needs zero framework change once this lands; it is an example, not a
  feature.
- **StageWeaver fan-out to derived items** (§6). Item identity stays the input path.
- **Deleting the vestigial `shm` subsystem.** CLAUDE.md already marks it deletable post-v1.8; doing
  it here would widen the blast radius for no benefit, and `shm_name`/`free_slots` are still part of
  StageWeaver's locked 8-arg stage signature.

## 1. Make the package importable without vLLM

**Problem.** `vllm_module/vllm.py:5` does `from vllm import SamplingParams, RequestOutput, LLM` at
module scope, and `prediction.py:17` imports through it. A CPU-only chrome-rendering worker therefore
cannot even `import` the predictor without a full vLLM install.

**Smaller than it looks.** `vllm.py` already carries a full dummy stand-in for `SamplingParams` /
`StructuredOutputsParams` / `LLM` (`vllm.py:8-64`), gated by a hand-flipped `local_testing` module
constant for local dev without a GPU. The only thing missing is making that fallback trigger
automatically when vLLM genuinely isn't installed, instead of requiring someone to flip the constant.

Checked what actually touches a vLLM type at runtime, versus only in a type annotation:

| File | vLLM-adjacent import | Runtime use? |
|---|---|---|
| `prediction.py:17` | `StructuredOutputsParams, SamplingParams` | annotation-only |
| `retry_validate.py:11` | `SamplingParams` | annotation-only |
| `retry_validate.py:9` | `VLLMRequest` (via `vlm_service.py`) | yes — built in `stage()` |
| `vlm_service.py:3` | `LLM, SamplingParams` (via `vllm.py`) | yes — resolves to the dummy classes once `vllm.py` is fixed |
| `health.py`, `media.py` | none | already vLLM-free |

So the fix is one change, not a package reorg: in `vllm.py`, replace `if not local_testing:` with
`try: from vllm import ... except ImportError:` falling through to the existing dummy classes. Every
module above bottoms out at that one import, so the whole chain — including `retry_validate.py`'s
`VLLMRequest` — becomes importable without vLLM the moment `vllm.py` degrades gracefully. No `core/`
package, no seven-file move, no `VLMHealth = ServiceHealth` aliasing, no renaming of working code.

(`VLLMRequest` living in `vlm_service.py` rather than `wire.py` — the request half of the wire
contract sits somewhere the response half doesn't — is a naming wrinkle, not a blocker. Worth tidying
whenever, but it isn't required for this section's goal.)

Everything genuinely new — the worker pool (§3), the shard allocator (§5), `FunctionTask` (§2) — is
new code and can live under a new `src/vision_ingest/core/` package; there's nothing to migrate into
it, only new files to add. `ServiceHealth`'s N-worker generalization (§4) lands in `health.py` under
its current name — `VLMHealth` stays `VLMHealth`.

`examples/` and `src/captioning_dataset_1` keep importing exactly what they import today. The payoff
— `pip install` without vLLM becomes viable for function-only deployments — is achieved without
moving code that already works.

> **SHIPPED as designed**, with two additions worth knowing:
>
> - The module now exposes **`VLLM_AVAILABLE`** (bool), so anything that wants to branch on "is
>   there a real engine here" can, without a second try/import.
> - `local_testing` is **kept** as a manual override — it is still useful for developing against
>   the dummy classes on a machine that *does* have vLLM installed. The ImportError path handles
>   the genuine "no vLLM here" case on its own.
>
> **Caveat, and the one thing §1 does not buy you:** `vllm_config.py` imports **transformers** at
> module scope, and `prediction.py` imports `VLLMConfig` for `PromptConfigError`. So a function-only
> deployment still needs `transformers` installed, just not `vllm`/CUDA. Removing that last
> dependency means making the `VLLMConfig` import lazy in `prediction.py` — a small follow-up, and
> deliberately not done here because it is not what blocked a CPU-only worker.
>
> Verified by blocking `vllm` with a `sys.meta_path` hook and importing `drivers.cli`,
> `modules.prediction`, `vllm_module.retry_validate` and `core` clean. See §8.

## 2. Make the payload opaque

`prediction.py` touches the payload's *contents* in exactly two places. That is the whole coupling.

**1. `prediction.py:451`**

```diff
-rec["sent_prompt_str"] = send["prompt"]
+rec["sent_payload"] = send
```

…with the output record built from `send.get("prompt")`, so the vLLM JSONL is byte-identical.
The constraint to state in the docstring: **a payload is always a JSON-able dict.**

**2. `prediction.py:491`**

```diff
-validated_output = self.validate_and_postporcess_fn(response.text)
+validated_output = self.validate_and_postporcess_fn(response.output)
```

The retry hook `build_retry_request(payload, params, attempt, last_error)`
(`project_specific.py:46`) already takes the payload as a dict and already receives private copies.
**It needs no change at all** — it generalizes for free.

### One discriminator, not a new protocol

Today `VLMPrediction.get_prompts` (`prediction.py:286`) always calls
`self.cfg_model.get_prompt_with_image(...)` (`prediction.py:331`), because `VLMPrediction` always has
a `VLLMConfig`. It already has the right shape to extend, though:
`vlm_config: Optional[VLLMConfig] = None` (`prediction.py:115`) exists purely so the predictor
doesn't have to construct one itself. Extend that same idea one step further instead of introducing a
`RequestBuilder` protocol:

- New optional constructor arg, `function_task: Optional[FunctionTask] = None`, mutually exclusive
  with `vlm_config` / `model_name` / `config_path`.
- `get_prompts()` gets one `if self.function_task is not None:` branch (`prediction.py:298-339`):
  calls `function_task.build_request(path, logger)` per path through the same `reader_pool`, instead
  of the `get_image_specific_prompt` → `get_prompt_with_image` two-step. **Existing vLLM projects
  change nothing** — the two-step path is untouched, just now inside an `else`.
- `_base_sampling_params()` and `_check_backend_supports_sampling_params()`
  (`prediction.py:358, 383`) short-circuit when `function_task is not None`. `params` stays an opaque
  `Optional` slot on `Request` — `None` for function backends, exactly as before.

No `VLLMRequestBuilder` / `FunctionRequestBuilder` class pair, no protocol object plumbed through
`cli()` — one attribute that was already optional, made to mean something when it's set.

> **SHIPPED, with one mechanical difference at `prediction.py:491`.** `VLLMResponse.text` was NOT
> renamed. Renaming it would have touched every construction site in `online_worker`,
> `async_worker` and `timed_worker` for no behavioural gain. Instead `output` is a **property alias**
> on the NamedTuple:
>
> ```python
> @property
> def output(self):   # vLLM: the generated text. function: whatever call_fn returned.
>     return self.text
> ```
>
> so `prediction.py` reads `response.output` exactly as designed, the workers are untouched, and the
> field's type annotation widened from `Optional[str]` to `Optional[Any]`.
>
> **The output record.** `rec["sent_payload"] = send` landed as specified, and the record is built
> from `payload.get("prompt")` — so the vLLM JSONL is byte-identical (same four keys, same order,
> same values; verified, see §8). The full payload is *additionally* recorded as `sent_payload`
> **only on the function path**, where `prompt_str` would otherwise be a useless `None`. The vLLM
> record gains no new key.
>
> **Hook resolution.** `cli()` passes the `FunctionTask` as `prompt_validation_object` *and* as
> `function_task`, so they are normally the same object. `VLMPrediction` still prefers
> `function_task` explicitly when resolving `wrap_and_validate_output` / `build_retry_request` /
> `get_sampling_params`, so a caller that passes them separately still gets a coherent pair rather
> than a silently mismatched one.

This is where `ShardAllocator.reserve()` (§5) gets called, for tasks that declare image output — once
per path, while building that path's request:

```json
{"input_path":  "/in/a.html",
 "output_path": "/out/<host>/shard_00007/a.png",
 "shard":       "shard_00007.tar",
 "member":      "a.png"}
```

`shard` names the **final tar from the moment of reservation**, not the folder — see §5 for why that
stays true even though the tar doesn't exist yet when this dict is built. A task opts into shard
allocation simply by having `build_request()` return an output path; nothing else branches on it.

### `core/task.py`

The `FunctionTask` base deliberately reuses the method names `prediction.py` already calls, so the
predictor's code is identical for both backends:

```python
class FunctionTask:
    def build_request(self, path, logger) -> dict | None
    def wrap_and_validate_output(self, output)              # raise ValueError -> retry
    def build_retry_request(self, payload, params, attempt, last_error)
    def write_local_json(self, obj, logger)
```

### `cli.py`'s one `if`

Around the `VLLMConfig` construction at `cli.py:210-252`: when `args.backend == "function"`,
construct a `FunctionTask` instead of a `VLLMConfig` and call `VLMPrediction(function_task=...)`;
otherwise the existing `VLMPrediction(vlm_config=...)` call path is untouched. Everything else in
`cli()` — DB, recovery, writer, metrics, the health-readiness wait, `_shielded_teardown` — stays as it
is.

## 3. `core/service.py` — the worker pool

Same external contract as `VLLMService` (`vllm_module/vlm_service.py:36`), so `prediction.py` cannot
tell the two apart: reads one shared `request_queue`, writes `response_queues[stage_name]`, stops on
`stop_event`, reports liveness on `ServiceHealth`.

```python
class WorkerSpec(NamedTuple):
    init_fn:   Callable            # (args, rank, device) -> ctx    module-level, picklable
    call_fn:   Callable            # (ctx, payload) -> output       module-level, picklable
    term_fn:   Optional[Callable]  # (ctx) -> None
    args:      dict                # JSON-able (the constraint StageWeaver already imposes)
    devices:   Optional[List[str]] # ["cuda:0", ...] — one process per entry
    n_workers: int                 # == len(devices) when devices is given
```

`FunctionService(spec, request_queue, response_queues, stop_event, health, logs_dir)` spawns
`n_workers` processes, each running a module-level `_worker_main(...)`:

```
device = spec.devices[rank] if spec.devices else None
ctx    = spec.init_fn(SimpleNamespace(**spec.args), rank, device)   # chrome / SAM3 / YOLO / HF
health.mark_ready(rank)

loop until stop_event:
    token -> Request(req_id, stage_name, payload, params)
    health.set_inflight(rank, req_id, stage_name)          # see §4
    out = spec.call_fn(ctx, payload)                       # opens  payload["input_path"]
                                                           # writes payload["output_path"]
    response_queues[stage_name].put(Response.ok(req_id, out, stats))
    health.clear_inflight(rank)

finally: spec.term_fn(ctx); health.mark_dead(rank, ...)
```

**`(rank, device, ctx)` is the whole abstraction.** One shape covers both cases with no branching:

| Workload | `devices` | `n_workers` | what `init_fn` builds |
|---|---|---|---|
| HTML→PNG / SoM | `None` | 32 | one headless chrome per process |
| SAM3 | `["cuda:0", …, "cuda:7"]` | 8 | one model replica per GPU (SAM3 has no tensor parallelism) |
| YOLO / HF model | either | either | whatever that model needs |

**The worker does I/O and nothing else.** It is *given* the exact path to open and the exact path to
write into, both decided in the main process (§5). It never chooses a filename, never picks a
folder, never scans a directory. That is what keeps shard accounting coordinated under a single
authority, and it is why the queue only ever carries paths and small metadata — no decoded pixels,
no rendered bytes.

**Load balancing is free.** N processes competing on `request_queue.get()` is work-stealing by
construction: no scheduler, no per-worker queues, no rebalancing. A slow item occupies one worker and
the other N−1 keep draining.

### Failure classification — no new taxonomy

v1.8's three kinds map onto function failures without inventing anything:

| `call_fn` does | kind | effect (existing, unchanged machinery) |
|---|---|---|
| returns | `ok` | `wrap_and_validate_output()` still decides whether the output is *good* → retry if not |
| raises `InputRejected` | `reject` | terminal on first occurrence, not retried — "this HTML is unrenderable" |
| raises anything else | `infra` | retried on the infra budget; **never** marks a path FAILED |

`infra` as the default for an unexpected exception is the correct bias: a chrome crash or a CUDA OOM
is infrastructure, not data. The existing `_classify_infra` fuse (`prediction.py:660`) already turns
a sustained streak of them into `ServiceDown` — aborting with in-flight paths left at state=1 —
rather than marching the dataset into state=3. That is exactly the v1.7 protection, inherited for
free.

> **SHIPPED as designed.** Four implementation details the sketch left open:
>
> - **`FunctionService` is not a `Process`** (unlike `VLLMService`). There is nothing for it to do
>   in a child; it owns `Process` objects and the supervisor thread that watches them, both of which
>   have to live in the parent. Lifecycle is `start()` / `join(timeout)` / `terminate()`.
> - **`WorkerSpec.args` defaults to `None`, not `{}`.** A NamedTuple default is created once and
>   shared by every instance that omits it, so a mutable default is a footgun; `_worker_main`
>   normalises with `spec.args or {}`.
> - **`resolved_n_workers()`** makes `devices` win, and *fails* on a genuine disagreement
>   ("8 devices, 32 workers") rather than silently reconciling it. `n_workers` left at its default
>   of 1 next to a device list is treated as an omission, not a disagreement.
> - **Respawn is bounded**: `MAX_RESPAWNS_PER_RANK = 3` with a `RESPAWN_BACKOFF_S = 2.0` backoff.
>   Unbounded respawning would put a worker with a broken `init_fn` into a tight crash loop for the
>   whole run; bounding it is also what lets "kill all N" terminate as a clean `VLMServiceDown`
>   abort instead of never converging (§8, test 5).

## 4. `ServiceHealth`: N workers, and no timeouts anywhere

### Explicitly rejected: a per-request timeout

The obvious way to notice a lost request is a deadline on it. **Do not add one.** Under StageWeaver
many stages share one backend (`initialization_source = [0, 0, 0]` in
`src/captioning_dataset_1/main.py` puts three stages on one service), so a request can legitimately
sit queued for a very long time with nothing wrong. A timeout would have to be tuned against
contention it cannot observe, and would begin failing healthy work the moment another stage joined.

The health channel is the right mechanism, for the same reason it was right in v1.7: **the process
that knows the fact reports the fact**, instead of a second process inferring it from a clock.

### Multi-worker health

`VLMHealth` (`vllm_module/health.py:76`) is a single flag today. Generalize it with two `mp.Value`
counters:

- `is_ready()` — true when **all** `n_workers` have reported ready, so `cli.py:298`'s "wait for the
  backend, then start the clock" stays correct and throughput excludes model-load time.
- `failure_reason()` — non-`None` only when **all** workers are dead. One chrome worker dying costs
  throughput, not the run.

`n_workers = 1` reproduces today's behaviour exactly, so `VLLMService` is unaffected.

### Recovering a dead worker's in-flight request, precisely

If a worker is `SIGKILL`ed mid-request, its `req_id` would otherwise sit in `prediction.py`'s
`inflight` dict forever: `_owned` never decrements, `fetch_n` walks to 0, and the pipeline stalls.

Give `ServiceHealth` one small shared slot per rank (`mp.Array`, ~128 bytes) holding the
`(req_id, stage_name)` that rank is currently processing — written immediately after `get()`, cleared
immediately after `put()`. A supervisor thread in the parent watches for a worker exiting while
`stop_event` is clear, and on death:

1. reads that rank's slot and emits `Response.infra(req_id, "worker <rank> died")` on the correct
   response queue. The request is recovered **exactly**, and flows through the existing infra path —
   retried on the infra budget, never marked FAILED;
2. respawns the worker.

**Known, bounded gap to record:** a kill landing between `get()` and the slot write loses that one
request. The window is microseconds and contains no user code. Everything else is covered.

> **SHIPPED as designed**, in `VLMHealth` under its existing name — `VLMHealth` stays `VLMHealth`,
> and `n_workers=1` (the default) reproduces the pre-v1.9 behaviour exactly, which is why
> `VLLMService` needed no change. Concretely:
>
> - `mark_ready(rank=0)` / `mark_dead(reason, rank=0)` keep their old call signatures, so every
>   existing call site still compiles and means the same thing.
> - `ready_event` / `dead_event` became **latches over per-rank flag arrays**: ready when ALL ranks
>   are ready, dead when ALL ranks are dead.
> - `ready_event` deliberately **never un-sets**. cli() waits on it once to decide when to start the
>   clock; a worker dying and respawning mid-run must not send the run back to "still loading".
> - Two methods the sketch implied but did not name: **`mark_alive(rank)`** (the supervisor calls it
>   after a successful respawn, so a pool that lost every worker and got them back is not
>   permanently branded dead) and **`attach_worker_process(rank, proc)`** (re-attached on every
>   respawn, so the parent-side liveness check never looks at a stale corpse).
> - `failure_reason()` requires **all** attached processes to be dead — `all`, not `any`.
>
> Both halves of the recovery story were verified against a real `SIGKILL` (§8, test 5): the
> supervisor read the slot, emitted `infra` for exactly that `req_id`, and the item was retried with
> its attempt count untouched.

This also happens to be the shape that would close the `SIGKILL`ed-`VLLMService`-hangs-forever gap
in `docs/v1.7_stageweaver_gap.md`, which no amount of health-flag threading could reach — worth
considering for `VLLMService` separately.

## 5. `core/shards.py` — folders, then tars, with one authority

**The main process owns folder assignment, not the workers.** A per-worker directory scheme would
mean N independent shard sequences and no single answer to "how full is the current folder". Instead
there is one allocator in the cli process; workers only perform I/O on paths handed to them, and
report back how many bytes they wrote.

Four operations, all in the cli process:

**`reserve(name) -> (abs_output_path, record)`** — called during request build (§2), on the prep
thread. Hands out `{root}/{host}/image_folders/shard_00007/{name}` plus the record
`{"shard": "shard_00007.tar", "member": name}`, and increments `outstanding[7]`.

> The record names the **final tar from the moment of reservation** — not after sealing. So a JSONL
> line is correct both before and after the seal, and sealing never has to touch an immutable shard.
> This is the detail that keeps "JSONL shards are immutable after fsync" true.

**`commit(shard_idx, nbytes)`** — the worker returns `bytes_written` in its response `output`; the
allocator adds it to `bytes[shard_idx]` and decrements `outstanding[shard_idx]`. Rolls by byte size —
same trigger as JSONL rotation: once `bytes[N] >= 10 GB` (configurable) the allocator stops handing
out paths in folder N and starts folder N+1.

**`release_failed(shard_idx, path)`** — called from the same place `cli_utils.process_iteration`
already sees `failed_paths` (`cli_utils.py:100-133`), for any item that reserved a slot but ended
terminally failed (reject / attempts-exhausted / oversize). Deletes `path` if it exists — a
prep-level failure never got far enough to write anything, so this is a guarded `os.remove`, not an
assumed one — then decrements `outstanding[shard_idx]`, same accounting as a success. This is what
keeps a sealed tar free of orphans: every reservation resolves to either a JSONL success record
backed by a real file, or nothing at all. Miss the decrement and a folder with one failed image never
seals; miss the delete and a failed item's partial output ships inside the tar anyway.

**Sealing.** A folder seals once it is closed for allocation (rolled past) **and**
`outstanding[N] == 0` — every request that reserved into it has reached a terminal state, success or
failure. `tarfile`, **uncompressed** (no gzip), into `shard_000NN.tar.tmp` → fsync → `os.rename` to
`.tar` → the DB pointer swap (below) → `rmtree` the folder. Runs on a background thread so it never
stalls the pipeline, and happens continuously through the run as folders fill — not batched to
end-of-run, the same way JSONL shards rotate on the go rather than all at once at shutdown.

**Durability ordering.** The worker fsyncs the file it wrote *before* putting its response on the
queue (knob `image_fsync`, default on). That single rule keeps the existing commit protocol intact
with **zero new recovery code**: by the time `JSONLWriter._flush_group` (`writer.py:103`) commits a
path, its image bytes are already durable — whether or not its shard has sealed yet.

### Two names for the same artifact — how downstream reads it without waiting

A shard is much bigger than a JSONL flush group (10 GB vs. 250 lines), so at the moment a stage
commits a row — and, in multi-stage mode, hands it to the next stage via
`router_coordinator.mark_done()` (`writer.py:153`) — the shard that row's image lives in is almost
always **still open**. Two bad options: make downstream activation wait for the shard to seal (turns
StageWeaver's streaming handoff into one-shard-at-a-time batching — the opposite of "tar as it goes"),
or activate immediately and let downstream sometimes resolve a tar path that doesn't exist yet (a
real correctness bug, not a race worth shrugging off).

The fix is to make both states resolvable, instead of picking one and racing to close the gap in
time:

- The **JSONL record** always names the final tar (`shard` / `member`, from `reserve()` above) —
  reservation-time naming already guarantees this, and it never changes, preserving shard
  immutability.
- The **DB column downstream stages read from directly** starts out holding the **folder path**
  (`.../shard_00007/a.png` — guaranteed to exist the instant the JSONL record is durable, since the
  worker fsynced it first). Once the shard seals, a hook — called right after `os.rename` above
  succeeds, before `rmtree` — updates every DB row referencing that shard from the folder path to the
  tar path.
- **A downstream stage tells the two apart by what it resolves to**: a bare/directory-shaped path
  means "read the loose file"; a `.tar` path means "read this member out of the tar." Both are always
  valid at read time. There is no window where the referenced location doesn't exist, so there is
  nothing to gate on and nothing to wait for.

The seal → update → delete ordering also makes the pointer swap crash-safe for free: if the process
dies between `os.rename` and the DB update, the tar exists, the folder still exists untouched
(`rmtree` hasn't run), and the DB still says "folder" — downstream keeps reading the folder correctly
until the next startup retries the swap. `rmtree` only ever runs after the DB update is durable, so
the folder is never removed out from under a DB row that still points at it.

```python
def on_shard_sealed(shard_id: str, folder_path: str, tar_path: str) -> None:
    """
    STUB — real DB schema TBD. Bulk-updates every row (across however many
    downstream-stage DBs reference this shard) from folder_path to tar_path.
    Called once per shard, after the tar is durable on disk and before its
    folder is removed. Must be safe to call twice: a retry after a crash
    between this call and the following rmtree should be a no-op the second
    time.
    """
    raise NotImplementedError
```

**Recovery on startup.** A leftover `shard_000NN/` with no matching `.tar` yet is sealed immediately
(same path as above) and allocation resumes at `NN+1`. A leftover `shard_000NN/` **with** a matching
`.tar` already present means the process died between `os.rename` and `rmtree` (possibly before
`on_shard_sealed()` finished) — call `on_shard_sealed()` again (idempotent by contract) and then
`rmtree` the stale folder. A stray `.tar.tmp` is deleted and re-sealed from the folder if the folder
is still present.

**Every JSONL, every backend, always.** Unchanged from §0: the JSONL line is written whether or not a
task produces image output — a task opts into shard allocation simply by including an output path in
what `build_request()` returns (§2); nothing about the JSONL commit path branches on it.

### SHIPPED — three divergences, all deliberate

**1. Reservations are keyed on the INPUT PATH, not a shard index.** The sketch had
`commit(shard_idx, nbytes)` and `release_failed(shard_idx, path)`. Shipped:

```python
reserve(input_path, name) -> (abs_output_path, record)
commit(input_path, output)        # bytes_written read off output; falls back to os.path.getsize
release_failed(input_path)        # deletes the file if present, then decrements
```

The reason is that the input path is the identity the pipeline already carries end to end.
`cli_utils.process_iteration` sees terminal results as `failed_paths` (a list of input paths) and
`successful_objs` (each with `obj["path"]`) — so both calls are driven from exactly the place the
sketch wanted them, with **no extra plumbing and nothing for a task to remember**. Had the API kept
`shard_idx`, every caller would have needed a side table mapping path → index, which is precisely
the bookkeeping the allocator exists to own.

A corollary that falls out for free: a **retry re-runs `build_request()` and therefore reserves
again**. `reserve()` detects the same input path reserving twice and releases the earlier slot, so a
retried item cannot pin its first folder open forever.

**2. `on_shard_sealed` ships as a documented no-op, not `raise NotImplementedError`.** The stub as
sketched would make *every seal* raise, which takes the tar creation down with it — strictly worse
than sealing correctly and leaving the pointer swap unwired. So `default_on_shard_sealed` returns
`None`, and a real one is installed with `ShardAllocator(on_shard_sealed=...)` (or `args.on_shard_sealed`).
The contract for whoever implements it is unchanged and is recorded on the function: **must be safe
to call twice**, and **must be durable before it returns**, because `rmtree` runs immediately after.

Everything *around* the hook is real and tested: it fires exactly once per shard with the correct
`(shard_id, folder_path, tar_path)`, strictly between `os.rename` and `rmtree`, and startup recovery
re-calls it for a shard that has both a tar and a folder. **The two-names-for-one-artifact scheme in
this section is therefore implemented on the filesystem side and stubbed on the DB side** — that is
the one piece of v1.9 that is wiring rather than mechanism, and it is blocked on the schema decision
the sketch already flagged as TBD.

**3. `close()` does more than seal.** On shutdown the allocator first **releases every reservation
still unresolved**, then seals the open folder. Those unresolved reservations belong to paths cli()
is about to reset from state=1 back to `fetch_state` — they will be replayed next run, so their
half-written outputs must not ship inside a tar.

Also added, not in the sketch: the seal `fsync`s the **parent directory** after `os.rename`. A rename
is only durable once the directory entry is; without it a crash in that window can leave neither the
tmp nor the final name on disk.

**4. Two directories, and folder deletion is opt-in.** The sketch had one flat directory and an
unconditional `rmtree` after sealing. Shipped:

```
{root}/{host}/image_folders/shard_00007/a.png   <- what the worker writes; KEPT by default
{root}/{host}/shards/shard_00007.tar            <- the packed shard
{root}/{host}/shards/shard_00007.csv            <- its byte-offset index
```

`delete_folders_after_seal` defaults to **`False`** (`args.delete_shard_folders`), so every image
exists twice. That is a deliberate ~2x disk cost, bought for: loose files stay directly readable with
no untarring, a bad tar can be rebuilt from its folder, and a downstream stage that resolved the
*folder* path keeps working forever rather than only until the seal.

Separating the trees makes `shards/` exactly the set of shippable artifacts — `rsync`, `aws s3 cp
--recursive` and a glob all do the obvious thing with no filtering. It also resolves an ambiguity
retention would otherwise create: in the flat layout "is there a folder next to this tar?" *was* the
crash signal, and with retention on that becomes the permanent normal state.

**So the completion marker moved to the CSV**, and the seal reordered to put it last:

```
write .tar.tmp -> fsync -> rename -> fsync(shards/) -> on_shard_sealed() -> write .csv -> [rmtree]
```

Startup recovery keys off it: `.tar` **and** `.csv` means finished — skip, one `os.path.exists` and
nothing else. Without a marker, a run with 10,000 retained folders would re-call the pointer-swap
hook for all 10,000 on every startup. `.tar` with no `.csv` means the seal was interrupted after the
rename, so the tail is re-run (hook, then CSV). Folder with no `.tar` is unchanged: seal it and
resume at `NN+1`.

Flipping `delete_folders_after_seal` on later also cleans up previously-retained folders at the next
startup, without re-running any pointer swap.

### Known limitation: orphan members after a hard crash

The invariant "every reservation resolves to either a JSONL success record backed by a real file, or
nothing at all" holds in normal operation, including terminal failures. It does **not** survive a
`SIGKILL` of the pipeline itself.

On a hard kill, workers may have written and fsynced images whose JSONL records were never committed.
Startup recovery seals that leftover folder — it has no way to tell those files apart from legitimate
ones, since the thing that would distinguish them is the DB record that was never written. Those rows
are replayed and write *new* members into a *new* shard, leaving the originals as orphans inside the
sealed tar.

This is the deliberate trade: an unreferenced member in a tar costs disk, whereas discarding files
that might be legitimate costs data. Observed directly in §8's crash test — 1996 tar members against
1974 JSONL records after one `kill -9`. **Every JSONL record still resolves**, which is the direction
that matters; the tar is a superset, never a subset.

## 6. StageWeaver

**No StageWeaver changes are required.** Its locked 8-arg stage signature
(`StageWeaver/src/stageweaver/db_pipeline.py:107`) is satisfied unchanged: a function stage is a
top-level function that calls `cli()`, exactly like `src/captioning_dataset_1/stage_fns.py:66`. The
group leader's `init_fn` spawns a `FunctionService` instead of a `VLLMService`; `request_queue` /

regardless of `init_fn`.

Two known gaps, neither blocking:

- **`init_vars` never reaches the stage function** (`db_pipeline.py:256` is its only consumer).
  Irrelevant here: the worker pool communicates through the queues, which *are* passed.
- **No fan-out to derived items.** StageWeaver keys everything on `item_key == images.path`, and its
  only stage-DB write is `UPDATE images SET state=4 WHERE path=ANY(%s) AND state=0` — so a
  brand-new output path matches zero rows and is silently dropped with a warning. The sanctioned way
  to chain a derived image already exists in this repo:
  `PromptAndValidation.get_modified_image_path` (`project_specific.py:90`) —

  > *"For given image_path, you can either pass the original image as it is or pass the SOM image
  > saved at a different location. But make sure that different location can be found out using the
  > original image_path."*

  Item identity stays the input path; the derived path is recoverable from it. Real fan-out (one page
  → twelve crops) is a separate StageWeaver change and is not attempted here.

The rejection of request timeouts (§4) is largely a StageWeaver-driven decision — recorded here so
it is not "simplified" back in later.

  `wrap_and_validate_output` rejects a zero-byte or blank render (which then retries, exactly like a

> **SHIPPED**, using **playwright/chromium** as the renderer (`pip install playwright && playwright
> install chromium`). `call_fn` navigates to `file://<input_path>` rather than `set_content()`, so

### SAM3 acceptance criterion

This must be true when v1.9 lands, **without touching the framework**:

`devices=["cuda:0", …, "cuda:7"]` → 8 processes, each `init_fn(args, rank, device)` loading its own

## 8. Acceptance criteria — and what was actually verified

There is no automated test suite (`CLAUDE.md`); correctness is validated by running the pipeline on
small datasets. Status of each criterion as of this commit:

| # | Criterion | Status |
|---|---|---|
| 1 | vLLM regression, byte-identical JSONL | **Partial** — record-level parity proven offline; no GPU run |
| 2 | Function backend, text output, N workers | **Passed** |
| 3 | Function backend, image output + shards | **Passed**, except the DB-column half (stubbed, §5) |
| 4 | Crash safety (`kill -9` mid-shard) | **Passed** |
| 5 | Worker death (one, then all) | **Passed** |
| 6 | StageWeaver two-stage run | **Not run** |

All runs used a stand-in `call_fn` that writes a PNG with PIL (no browser, no GPU on the development
node — see §7), against SQLite, with real worker processes and the real `cli()` path.

**1. vLLM regression — partially verified, and this is the gap to close first.**
A GPU run of `examples/vllm_testing/main.py` on `backend="online"` and `backend="async"` was **not**
performed (the node's GPUs were in use). What *was* proven is the thing §2 actually put at risk: the
output record. Driving `_classify()` with a vLLM-shaped payload and an `ok` response produces

```
['path', 'prompt_str', 'vlm_output', 'full_vlm_object']
```

— the same four keys in the same order with the same values as v1.8, with `prompt_str` still exactly
`send["prompt"]` and no new key added. The function path adds `sent_payload` and nothing else.
`import vllm`-blocked import checks cover §1. **Still owed: an actual two-backend GPU run**, before
this is called done.

**2. Function backend, text/image output, 8 workers — passed.** 8 worker processes confirmed
spawned; JSONL committed on the `fsync_every_lines` boundary; DB settled at 2/3 with **none stuck in
1**. Both non-`ok` kinds were exercised deliberately: an input that raises `InputRejected` failed
terminally on first occurrence with no retry, and an input that raises `RuntimeError` was retried on
the infra budget and only blamed on the item once other requests were demonstrably succeeding.

**3. Image output + shards — passed** (byte-roll threshold lowered to 20–50 KB so rotation happens in
seconds). On a 200-item run: **8 shards rolled and sealed continuously through the run**, not batched
at the end. Asserted and confirmed:

- folders seal into **uncompressed** `.tar` (verified by reading the magic bytes, not just the name);
- **no `.tar.tmp` survives** and no unsealed folder is left behind;
- allocation rolls **only** after the byte threshold (`shard_00000 reached 20598 bytes — closing`);
- a folder seals **only after its last outstanding request returns**, success or failure;
- a terminally-failed reservation's file is **deleted and never appears** in the sealed tar (the
  rejected item's `.png` is absent; member count equals success count exactly);
- `on_shard_sealed()` fires **exactly once per shard** with the correct `(folder_path, tar_path)`;
- **every `{"shard", "member"}` pair in the JSONL resolves** inside its tar — 198/198, and 1974/1974
  on the larger crash-recovery run.

**Not verified: the DB-column half.** "Read the column mid-run, get the folder path; read it after
sealing, get the tar path" cannot be tested while `on_shard_sealed` is a stub and the schema is
undecided (§5). This is the one open item in §5.

**4. Crash safety — passed.** `kill -9` of the whole pipeline mid-shard left 24 rows in state=1, an
unsealed `shard_00008/`, 8 sealed tars and no `.tar.tmp`. On restart: the leftover folder was
**sealed** (`sealing leftover folder shard_00008 from a previous run`), allocation **resumed at index
9**, `recover_last_shard` ran and validated the JSONL tail, and the member check from (3) still
passed for every record. The three recovery branches (folder-without-tar, folder-with-tar, stray
`.tar.tmp`) were additionally driven directly as unit cases. See §5's orphan-member limitation for
what a hard crash does *not* preserve.

**5. Worker death — passed, both halves.**

- `kill -9` **one worker of four**, mid-request: the supervisor emitted `infra` for exactly that
  worker's in-flight `req_id`, `prediction.py` logged `backend failure 1/5 ... — re-queued, attempt
  count untouched`, the worker was respawned (`1/3`), and the run finished with **40/40 in state=2
  and zero in state=3**.
- `kill -9` **every worker, repeatedly**, until the respawn budget was exhausted: the run aborted
  with `VLMServiceDown` naming all four exit codes, and cli()'s teardown **reset 12 in-flight paths
  to `fetch_state`** — final DB `{state_0: 24, state_2: 16, state_3: 0}`. **Nothing marked FAILED**,
  which is the entire point.

*(Note: a worker killed before `init_fn` returns holds no in-flight request, so there is nothing to
recover — the "held no in-flight request" path. Worth knowing when reproducing this: spawning a
worker that imports torch takes ~20s, so a kill timed too early tests startup, not recovery.)*

**6. StageWeaver — not run.** §6 argues no StageWeaver change is required and nothing in the
implementation contradicts that (a function stage is a top-level function calling `cli()`, and the
queues are created and passed for every group regardless of `init_fn`). But the two-stage run with
`route_taken` stamped was not performed, so this remains an argument rather than a result.
