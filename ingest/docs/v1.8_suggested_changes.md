# v1.8 — Suggested changes (proposal)

> **STATUS: IMPLEMENTED.** All of §1–§4 and both defects in §6 shipped; §5 stayed deprioritized as
> decided, with the batch backend rendering inline. See **`docs/v1.8_changes.md`** for what was
> actually built and where it diverged from this proposal — notably §4, where vLLM's own async
> render path turned out to be fully off-loop already, so no bespoke thread pool was needed. This
> document is kept as the design rationale.

Companion to `docs/v1.7_changes.md` / `docs/v1.7_reported_issues.md`. Those fixed v1.7's
reported symptoms by giving every silent failure mode its own explicit channel
(`_payload_kind`, `VLMHealth`, `PromptConfigError`, `_OnlineFailure`, ...). This doc is the
result of a follow-up holistic review of the contract between `prediction.py`,
`vllm_config.py`, `vlm_service.py`, `async_worker.py`, `online_worker.py`,
`retry_validate.py`, and `health.py`, asked for explicitly to find a simpler shape rather
than more guards bolted onto the v1.7 taxonomy. Nothing here is implemented yet — it is a
proposal to evaluate before doing v1.8 work.

**Suggested priority order:** Defect 1 (§6) is worth fixing now — small, protects the DB.
Defect 2 (§6) next. The paths-on-the-wire unification (§1) is the actual v1.8-shaped
change — it's the one that makes `_payload_kind`, shm, and half of `VLLMConfig` disappear
rather than get better-documented.

---

## 1. Payload unification — stop deciding payload shape on the stage side

**Current problem.** Almost every hard edge in this contract exists because payload shape
is decided on the stage side, so two processes must agree on `args.backend` through two
independent call chains (`main.py -> VLLMService`, `cli.py -> VLLMConfig`). That's the root
of: the `_payload_kind` stamp, `assert_payload_kind()`, `BackendPayloadMismatch`, the
`backend` param on `VLLMConfig`, and the two divergent branches in `process_one`
(`vllm_config.py:369-468`) — and it is exactly what v1.7 issues 2a and 7 had to add guards
for, not remove.

**Proposed.** The online backend already demonstrates the simpler contract: the wire
payload is raw text + image paths + sampling params, and the worker owns turning that into
what its engine needs. Do the same for the async backend (batch backend: see §5,
deprioritized): `VLLMService` decodes images and applies the chat template itself, instead
of the stage building a fully-templated, PIL-embedded prompt before it ever reaches the
queue.

**Consequences if applied:**
- `_payload_kind` / `assert_payload_kind()` / `BackendPayloadMismatch` are no longer
  *checked* at runtime — they become structurally impossible, since there is only one
  payload shape and only one process ever consults `backend`.
- `VLLMConfig` loses its `backend` parameter and its split prompt-building; it shrinks to
  engine args + sampling params + image policy. Stage-side `media.py` path validation stays
  exactly where it is (cheap, still gives a terminal-per-item failure before submission).
- The shared-memory subsystem becomes deletable — slots, sizing, oversize-terminal-fail,
  `stage()`'s acquire/pickle split, the exit-hang `cancel_join_thread()` choreography — all
  of it exists only because offline prompts embed 3–12 MB of PIL images. Paths + text fit a
  plain `mp.Queue` fine — already proven in production by the online backend, which never
  needs shm.
- Retry re-staging becomes a trivial re-put; the "oversized prompt can never fit later"
  special case disappears.
- **Templating detail that must be handled correctly:** vLLM's engine
  (`AsyncLLM.generate()` / `LLM.generate()`) does **not** apply chat templates itself — that
  step is done only by `vllm serve`'s `OpenAIServingChat` frontend, in its own subprocess.
  So if async/batch workers start receiving raw text, *something inside `VLLMService`* has
  to replicate that templating step. It should reuse vLLM's own
  `vllm.entrypoints.chat_utils` (`parse_chat_messages` / `apply_hf_chat_template`) — the
  exact functions `vllm serve` itself calls — rather than `VLLMConfig`'s own hand-rolled
  `apply_chat_template` call. This also removes the chandra dual-chat-template divergence
  risk noted in v1.7 issue 7 (the standalone `chat_template.jinja` vs the
  `tokenizer_config.json` template only agree today for `enable_thinking=False`): online and
  offline would then run the identical vLLM templating code path instead of "currently
  happening to agree."

**Anticipated objection.** The stated objection would be the CPU/GPU overlap design
(stage-side `reader_pool` hides decode under GPU time today). But that argument has
weakened: in vLLM v1, `AsyncLLM`'s engine core runs in its own process, so the worker
process has Python-side headroom, and `vllm serve` itself decodes images in-server at full
throughput — the pattern is already validated in production by the default backend. The
worker just needs its own small thread pool ahead of engine submission (see §4).

This isn't a bolt-on; it deletes the guard rails by deleting the thing they guard.

## 2. Tagged responses at the source

**Current problem.** The response wire format is an untyped union: `None` means infra
failure, `_OnlineFailure` is detected via `type(pred).__name__ == "_OnlineFailure"` (a
string match, `prediction.py:429`), "answered" is detected by duck-typing
`pred.outputs[0].text`, and `.usage` is duck-typed to tell the online shim apart from a real
offline `RequestOutput` (`retry_validate.py:282`). `_validate_one` has to reverse-engineer,
after the fact, information the worker already knew firsthand.

**Consequence.** The taxonomy's population is backend-dependent. Only the online backend
can currently say "reject" — a deterministic per-input failure offline (e.g. a prompt over
`max_model_len` raising inside `engine.generate()`) comes back as bare `None`, burns all 5
infra retries it can never pass, and is finally logged as a *backend* failure — while the
identical case online is correctly tagged "reject" via `_OnlineFailure` and fails
immediately with a clear message. Same input, opposite classification, purely because of
which backend happened to run it.

**Proposed.** Workers emit `(req_id, kind, payload)` where `kind` is one of
`{ok, reject, infra}`, and `ok` payloads carry the uniform stats dict directly (the worker
builds it, since it has the real information) instead of `post_process_full_vllm_object()`
reconstructing it afterward via duck-typing. `_validate_one` then shrinks to just the
ok/fail *validation* decision (does the model's actual output pass `validate_output`); the
type-name string check and the `.usage` duck-typing both go away.

Note the four-status taxonomy itself (`ok`/`fail`/`reject`/`infra`) is fine as designed —
the problem is only *where* it's computed.

## 3. Retry customization → `project_specific.py`

**Current problem.** `_build_send_prompt` (`prediction.py:360-376`) hardcodes "append error
text to the prompt" and `_build_sampling_params` (`prediction.py:378-385`) hardcodes "+0.5
repetition_penalty per attempt" inside `prediction.py` — the same retry mechanism is forced
on every project regardless of task, with no override point.

**Proposed hook** on `PromptAndValidation` (`project_specific.py`), default matching
today's behavior exactly so no project has to opt in to get current behavior:

```python
def build_retry_request(self, sent_prompt: dict, sampling_params: SamplingParams,
                          attempt: int, last_error: str) -> tuple[dict, SamplingParams]:
    """Default: append error to prompt text, bump repetition_penalty by 0.5/attempt."""
    prompt = dict(sent_prompt)
    prompt["prompt"] = sent_prompt["prompt"] + f"\n\nPrevious attempt failed: {last_error}\nFix and regenerate valid output."
    sp = sampling_params  # already an isolated copy — see below
    sp.repetition_penalty = getattr(sp, "repetition_penalty", 1.0) + attempt * 0.5
    return prompt, sp
```

- `prediction.py` keeps owning copy-safety: pass `copy.deepcopy(base_sp)` and a fresh dict
  (`dict(rec["orig_prompt"])`) into the hook — never `rec["orig_prompt"]`/`base_sp`
  themselves — so a careless override can't corrupt state shared across retries. `base_sp`
  is computed once per `VLMPrediction` lifetime and reused for every record forever; if an
  override mutates the object it was handed in place rather than the copy, every subsequent
  *fresh* attempt would silently inherit the corrupted value.
- `_stage_and_submit` becomes
  `send, sp = self.retry_fn(rec["orig_prompt"], deepcopy(base_sp), rec["attempts"], rec["last_error"])`
  on retry; fresh items skip it entirely.
- Now a project can lower temperature, switch to a different instruction on attempt 2, drop
  `repetition_penalty` bumping for OCR, add few-shot correction examples, etc. — all without
  touching `prediction.py`.
- No new coupling: still prep-thread-only, still one function call, still a plain-data
  return.

**Interacts with §1:** once payload is unified to pre-template paths+text, the error-append
happens before chat templating on *every* backend, so retries become semantically identical
across backends too — see Defect 2 below for why they currently aren't.

## 4. Parallelizing image decode for the async backend — required, not optional

If §1 moves image-decode + templating into `VLLMService` for the async backend, that CPU
work must not block the async event loop, or the GPU will idle waiting on it —
regressing the exact overlap `prediction.py`'s prep/collector thread split already provides
today. **This has to be implemented alongside §1 for async, not deferred.**

**Proposed**, in `async_worker.py`'s `_handle()`:

```python
async def _handle(self, engine, req, out_q, active):
    prompt = await loop.run_in_executor(self._prep_pool, build_prompt, req)  # CPU decode+template
    async for output in engine.generate(prompt, req.sampling_params, req.req_id):  # GPU
        ...
```

- **Mechanism:** `run_in_executor` hands the blocking PIL-decode+template call to a
  thread-pool worker and immediately frees the event loop — the loop keeps admitting new
  requests and dispatching `engine.generate()` for whichever *other* requests already
  finished decoding, while this one's decode runs concurrently on a separate thread.
- **Net effect:** at steady state, some requests sit in the thread pool decoding while
  others are already inside `engine.generate()` streaming from the GPU — the "few on CPU,
  few on GPU" split happens automatically, because asyncio's scheduler interleaves ready
  coroutines rather than blocking on each one in sequence. No bespoke pipeline logic needs
  to be written for this — you just stop blocking the loop.
- `self._prep_pool` is a new `ThreadPoolExecutor` living inside `VLLMService`'s own process
  (the child), analogous to `reader_pool` in the pipeline process today. Sizing it is the
  same tuning problem as `reader_pool`/`args.local_json_threads` today, just relocated: too
  few workers and decode becomes the bottleneck (GPU starves waiting for prepped requests);
  too many and you're contending with the asyncio loop's own thread for CPU.
- Admission is already bounded from the other side — `prediction.py`'s
  `desired_total = 3·batch_size` caps how many raw requests reach `VLLMService` at once —
  so the executor is never asked to decode an unbounded backlog.
- This does not conflict with "only `VLLMService` touches the GPU": under vLLM v1, the
  actual forward pass runs in `EngineCore`'s own subprocess under vLLM's own multiprocessing
  executor. `VLLMService`'s event loop was already a dispatcher, not where GPU compute
  happens, so adding a CPU thread pool to it is consistent with its existing role, not a new
  kind of contention.

## 5. Batch / `LLMEngine` backend — deprioritized, no plumbing planned

Per explicit decision: the batch backend (`_worker()` / `timed_worker()`) is deprioritized
for now. It's already documented as the legacy baseline kept only for A/B timing
comparisons against the async/online backends.

- Unlike async, batch has no event loop — `model.generate()` is one blocking call per
  collected batch. Getting the same CPU/GPU overlap here would require new double-buffering
  plumbing (a background thread prepping batch N+1 while the main thread blocks in
  `generate()` for batch N) that doesn't exist today.
- **Decision: do not build this now.** If §1's payload unification is ever applied to batch
  too, decode can simply happen inline/serialized before `generate()` — accepting the loss
  of overlap on this backend, since it isn't the recommended path.

## 6. Defects found during the review (independent of §1–§4, worth fixing regardless)

**Defect 1 — online config errors currently fail per-item instead of aborting the run.**
Any `_build_chat_payload` exception in `online_worker.py:226-231` — including the
`structured_outputs` misconfiguration (`online_worker.py:184-189`) — becomes
`_OnlineFailure(0, ...)` → classified "reject" → immediate terminal fail, per item, with
`_consecutive_infra` reset each time. A `structured_outputs` misconfig therefore marches the
whole dataset into state=3 at full speed — exactly the failure mode v1.7 was built to stop.
Cheapest fix today: validate `structured_outputs` against the backend at startup
(`VLMPrediction.__init__` has both the resolved sampling params and the config); the
tagged-response design in §2 fixes the general case.

**Defect 2 — retry prompts diverge semantically between backends.**
`_build_send_prompt` (`prediction.py:360-376`) appends "Previous attempt failed: ..." to
`orig_prompt["prompt"]`. Online that's raw text, so the server templates it into the user
turn — correct. Offline it's the already-chat-templated string ending in the generation
prompt (e.g. `<|im_start|>assistant\n`), so the error text lands *inside the assistant
turn*, after the point where the model starts answering. Retries are therefore materially
different requests on the two backends. The unified paths+text payload (§1) fixes this for
free (templating happens after the append, always); short of that, offline needs the append
to happen pre-template.

## Not proposed to change

- `health.py`'s `dead_event`/`proc`/`reason` machinery, the consecutive-infra fuse, and the
  `others_are_working` condition look heuristic-heavy but each layer covers a case the
  others can't (SIGKILL, unwired health, one poison item on a healthy backend). Tagged
  responses (§2) would shrink how often the heuristics fire, not replace them.
- The `_owned` conservation counter, writer protocol, and `run_iteration`'s return
  conditions are clean and correct as designed. No changes suggested.
- One tuning note, not a contract issue: the current retry `repetition_penalty` bump of
  `+0.5` per attempt is aggressive for long-form OCR transcription — attempt 2 already runs
  at ~2.0, which will actively degrade output. §3's `build_retry_request` hook is the fix —
  a project can cap or drop the bump without touching `prediction.py`.
