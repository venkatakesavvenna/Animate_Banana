# v1.7 × StageWeaver — `VLMHealth` has no path across the process boundary

Working notes, same spirit as `docs/v1.7_changes.md`. **Not fixed yet** — this is a
findings-and-options doc, written so the fix can be picked up later once v1.7 itself
has been tested and confirmed on a GPU node. Nothing in this doc has been implemented.

---

## The finding

v1.7's centerpiece (`docs/v1.7_changes.md` §1, `docs/v1.7_reported_issues.md` §4) is
`VLMHealth`: a shared liveness object that must be created in the **same process**
that spawns `VLLMService`, then handed to both `VLLMService(...)` and `cli(...)` so
`prediction.py` can tell "the engine died" apart from "this image failed". It works
today because `examples/vllm_testing/main.py` does both of those things — spawning
`VLLMService` and calling `cli()` — in one process.

Under StageWeaver (`../StageWeaver/CLAUDE.md`), those two things happen in
**different processes**, and the framework's locked signatures have no slot to carry
`vlm_health` between them:

- `VLLMService` is spawned inside a group's `init_fn`, which runs in the
  **group-leader** process
  (`StageWeaver/src/stageweaver/db_pipeline.py:194-202`, `_group_leader_worker`).
- `cli()` runs inside a separate, spawned **StageWorker** process
  (`db_pipeline.py:107-116`, `_stage_worker`).
- The only thing that crosses that boundary is `init_fn`'s return value
  (`init_vars`), and it is wired to reach **only** `term_fn`
  (`db_pipeline.py:256`) — never `_stage_worker`. Both locked signatures —
  `init_fn(args, logger, request_queue, response_queues, stop_event, shm_name, free_slots) -> init_vars`
  and stage `function(args, request_queue, response_queue, shutdown_event, router_coordinator, stage_specific_log_dir, shm_name, free_slots)`
  — predate v1.7 and were never extended for it.

Net effect: under StageWeaver, `cli()` is always called with `vlm_health=None`.

### Why this doesn't crash

Every consumer treats `vlm_health` as optional and defaults to inert behavior:

- `cli()`'s `vlm_health` param defaults to `None` (`cli.py:78`).
- `VLLMService.__init__` substitutes a fresh throwaway `VLMHealth()` if not given
  (`vlm_service.py:115`) — so the *child* side still marks itself dead internally,
  it just has no audience.
- `VLMPrediction._check_service_alive()` no-ops when `self.vlm_health is None`
  (`prediction.py:450-461`).

So nothing raises, nothing logs an error, nothing looks different in a short test
run. That's exactly why this is worth writing down now rather than discovering it
during an incident later.

## What it costs — two different severities

| Failure mode | Standalone (v1.7, working) | Under StageWeaver today |
|---|---|---|
| Engine exception, `vllm serve` subprocess exit, backend/payload mismatch — anything the `VLLMService` child can run its own code for | Immediate `VLMServiceDown` with a specific reason (`REASON_ENGINE_FAILED` / `REASON_SERVER_EXITED` / …) | Degrades to the heuristic fuse in `_classify_infra` (`prediction.py:606-658`) — `max(2·batch_size, 64)` consecutive infra failures with zero successes in between. Still aborts eventually, but slower and with a generic "N consecutive backend failures" message instead of the real reason. |
| **SIGKILL / OOM-kill of `VLLMService`** | Parent-side `proc.is_alive()` check (`health.py:113-121`) catches it, aborts immediately | **Hangs forever.** No response ever lands on `response_queue`, so `_classify_infra` — which only runs when there *is* a response to classify — never executes, and the fuse never fires. This is precisely the bug v1.7 issue 4 was written to fix, and it is unfixed here. |

The SIGKILL row is the one that matters most: it is not merely "unwired", it is
architecturally harder than passing one more argument. `VLMHealth.__getstate__`
(`health.py:96-101`) deliberately drops `.proc` on pickle, because `proc.is_alive()`
only means something in a process that holds the live `Process` object — that's the
group leader (it calls `svc.start()` inside `init_fn`), never the StageWorker that
runs `cli()`. Adding `vlm_health` to the locked signatures would restore the
*cooperative* signals (`dead_event` / the `mp.Value` reason code both pickle fine
across a spawn boundary) but would **not** by itself restore SIGKILL detection —
that needs the group leader itself to notice, since it's the only process with a
live handle to `svc`.

## Everything else checked — no other break found

- `args.allowed_media_roots` (v1.7, required for `backend="online"` on a vision
  model) is a plain `list[str]` — JSON-serializable, no `StageConfig.args` issue.
- The `write_local_json(obj, logger)` signature-mismatch bug documented in
  `docs/v1.7_reported_issues.md` §8 only exists in
  `examples/vllm_testing/project_specific.py` (the standalone example). There is no
  StageWeaver example in this repo to check against — the one StageWeaver's own
  CLAUDE.md cites as the reference (`StageWeaver/src/test_example/stage_fns.py`)
  does not exist on disk and has never been committed (`git log --all` in
  StageWeaver confirms).
- All of `cli()`'s v1.7-new parameters (`vlm_health` included) are keyword args with
  defaults, so nothing about the call *shape* breaks anything that already calls
  `cli()` without them.
- No other locked-signature parameter count or order changed in v1.7.

## Options, not yet chosen

Recorded so the next pass has somewhere to start — none of this is decided.

1. **Thread `vlm_health` through the locked signatures.** Add it as an explicit
   param StageWeaver forwards from `init_fn`'s `init_vars` into the stage
   `function` call — a locked-signature change on the StageWeaver side (both
   `_group_leader_worker` and `_stage_worker` in `db_pipeline.py`, plus every
   `StageConfig`-consuming call site). Fixes the cooperative-signal rows in the
   table above. Does **not** fix SIGKILL on its own.
2. **Add a group-leader-side liveness-watch thread**, started right after
   `init_fn` returns, polling `svc.is_alive()` (via whatever `init_vars` exposes)
   and calling `vlm_health.mark_dead()` itself if the child disappears without
   having set `dead_event` cooperatively. This is the piece that actually closes
   the SIGKILL gap, and only the group leader can do it (it's the only process
   with the live `Process` handle). Needs (1) to also be done, or this signal has
   nowhere to go.
3. **Do nothing / document the limitation** if StageWeaver-orchestrated runs are
   judged low-risk enough (e.g. always monitored, always restarted quickly) that
   the heuristic fuse + manual recovery is acceptable for now.

Whatever is chosen should be validated the same way `docs/v1.7_changes.md`
validated the standalone path: a scripted kill of the `VLLMService` process (both
graceful and `SIGKILL`) while a StageWeaver multi-stage run is mid-flight, checking
that the affected stage aborts (or the group leader's watch thread catches it)
instead of hanging.
