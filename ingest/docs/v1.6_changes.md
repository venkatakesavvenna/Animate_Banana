# v1.6 — Online-Serving Backend (`vllm serve` over HTTP)

Working-notes record for the v1.6 change, same spirit as `docs/v1.5_changes.md`. This is a
permanent design log, not a tutorial.

## Goal

Swap the offline in-process `AsyncLLM` engine for a **locally-launched `vllm serve`**
(OpenAI-compatible HTTP API) as a selectable backend. Online serving showed better speed/quality in
testing (the Gemma-4 bakeoff). Everything outside `VLLMService` — DB, writer, retries, StageWeaver,
shm — stays untouched, per CLAUDE.md's "any backend that speaks `request_queue`/`response_queue`"
design. Only *how* `VLLMService` fulfils a request changes: subprocess + HTTP instead of in-process
`engine.generate()`.

Key up-front decisions:
- **No Docker.** `vllm serve` runs in the same venv as `main.py`, launched/killed via
  `subprocess.Popen`. Because it is venv-based (not a container), `file://` image paths resolve
  natively — no bind-mount concerns.
- **`VLLMService` still owns the GPU.** It now owns the serve subprocess instead of an in-process
  engine, but it is still "the only thing that touches the GPU" per CLAUDE.md.
- **Retry logic is unaffected.** `retry_q` / attempt-counting / terminal-fail all live in
  `prediction.py`'s collector thread, keyed only on `(req_id, output|None)` — backend-agnostic.

## The wire contract (what makes the swap safe)

Everything upstream of `VLLMService` only ever sees this, and it is preserved exactly:

- **Consume:** `token = request_queue.get()` → `req: VLLMRequest = token` (with `use_shm=False`,
  which is the default, the payload *is* the token).
- **Produce:** `response_queue.put((req_id, output))`.
- Exactly **one response per request**. `output=None` → signals failure → triggers retry in
  `prediction.py` (unchanged).
- `output` must look like a `RequestOutput`: `.outputs[0].text`. A small shim wraps the HTTP
  response text to provide exactly that.

Because online requests carry only **image paths + text** (tiny), there is no multi-MB payload to
keep out of the queue, so the shm pool is irrelevant on this path — the default `use_shm=False`
queue transport is used directly. No slot sizing / oversize handling here.

## The one unavoidable change outside `VLLMService`: prompt-payload shape

The offline prompt dict is `{"prompt": <chat-template-applied string>, "multi_modal_data":
{"image": [PIL, ...]}}`. That shape is doubly wrong for `/v1/chat/completions`:
1. the text is **already chat-templated**, so the server would template it again;
2. images are **loaded PIL objects**, so the worker could only send base64 — defeating the whole
   `file://` speed goal.

So prompt construction must become backend-aware. This is the single change outside `VLLMService`.
The elegant part: online mode reuses the `"prompt"` key so `prediction._build_send_prompt`'s retry
error-append (`send["prompt"] += error`) works **unchanged** for both backends.

- **Offline (unchanged):** `{"prompt": <templated str>, "multi_modal_data": {"image": [PIL]}}`
- **Online (new):** `{"prompt": <raw user text, NOT templated>, "image_paths": [<abs paths>],
  "enable_thinking": <bool>}`

`vllm_config.get_prompt_with_image` branches on `backend`: in online mode it skips `load_cv2_pil`
and `apply_chat_template`, returning the raw text + the paths it already had in hand. Text-only LLMs
(`is_llm`) send no images.

## Backend selection

A single `backend` string in `args`, threaded to the two places that need to agree:
- **Worker dispatch** — `main.py` (`args.backend`) → `model_init` → `VLLMService(backend=...)` →
  `run()` dispatches to `online_worker` / `async_worker` / batch.
- **Prompt-payload shape** — `cli.py` builds `VLLMConfig(..., backend=args.backend)` and passes it
  in via the existing `vlm_config` param, so `prediction.py` stays backend-agnostic (no edits).

Values: `"online"` | `"async"` | `"batch"`. The old module-level `use_async` flag has since been
removed entirely (`backend` alone drives dispatch); `debug_timing` is consulted only for the
`"batch"` sub-choice.

## `online_worker.py` structure (mirrors `async_worker.py`)

```
  Receiver thread            Event loop (main thread)          Sender thread
  ───────────────            ────────────────────────          ─────────────
  req = request_queue.get      req = await incoming.get()        item = out_q.get()
  (use_shm False: token IS     task = _handle_http(req):         response_queue.put(
   the VLLMRequest)              POST /v1/chat/completions          (req_id, output))
  call_soon_threadsafe(          out_q.put((stage, req_id,
    incoming.put_nowait, req)      _OnlineOutput | None))
```

- Receiver/sender are `async_worker`'s `_make_receiver` / `_make_sender` reused verbatim (they
  already branch on `use_shm`).
- `_handle_http` builds the OpenAI body, POSTs via `httpx.AsyncClient`, extracts
  `choices[0].message.content`, wraps it in `_OnlineOutput`, and emits it. Any failure (incl.
  cancellation on shutdown) emits `(req_id, None)` so no `req_id` ever wedges.
- Server lifecycle lives in the worker (symmetric with `async_worker` building its engine):
  `_launch_server` = `subprocess.Popen(["vllm","serve", ...])` + `/health` poll (bails if the
  subprocess dies or a timeout elapses); teardown in the event-loop `finally`:
  `terminate()` → `wait(30)` → `kill()`.

### Payload construction
- **With images:** `content = [{"type":"image_url","image_url":{"url":"file://<path>"}}, ...,
  {"type":"text","text": <prompt>}]`.
- **Text-only:** `content = <prompt>` (plain string — matches the proven bakeoff request shape).
- `chat_template_kwargs.enable_thinking` sent **top-level** in the JSON body (matches the
  requests-based bakeoff), sourced from the validation object's `enable_thinking` (default False).
- `temperature` / `top_p` / `top_k` / `repetition_penalty` / `max_tokens` are forwarded from
  `SamplingParams` field-by-field, **omitted entirely when `None`** rather than defaulting to a
  made-up number — see the 2026-07-28 addendum below for why this now matches `vllm serve`
  byte-for-byte instead of just approximating it.

### `engine_args` → serve flags
`_engine_args_to_serve_flags()` translates the model-yaml `engine_args` dict (the same dict passed
to offline `LLM(**engine_args)` / `AsyncEngineArgs`) into `vllm serve` CLI flags:
- snake_case key → `--kebab-case` flag
- bool `True` → bare flag (store_true); `False`/`None` → omitted
- dict / list → flag + JSON string (e.g. `limit_mm_per_prompt` → `'{"image": 1}'`)
- scalar → flag + `str(value)`

`model` is positional (`serve <model>`); `tensor_parallel_size` is skipped and derived from `gpus`
(mirrors `_load_model`), falling back to `engine_args` only when no GPUs are pinned. So any option
works by adding it to the model yaml `engine_args` — no code change, and offline/online load
identically.

Example — `datalab-to/chandra-ocr-2` (`{max_model_len: 60000, gpu_memory_utilization: 0.95,
trust_remote_code: True}`) becomes:

```
vllm serve datalab-to/chandra-ocr-2 --host 127.0.0.1 --port 8000 \
  --allowed-local-media-path /fsxvision_new --tensor-parallel-size <#gpus> \
  --max-model-len 60000 --gpu-memory-utilization 0.95 --trust-remote-code
```

## Defaults (online-only), in `online_worker.py`

| Setting | Default | Note |
|---|---|---|
| `ONLINE_HOST` / `ONLINE_PORT` | `127.0.0.1` / `8000` | local serve |
| `ONLINE_ALLOWED_LOCAL_MEDIA_PATH` | `/fsxvision_new` | vLLM forbids `file://` outside this root |
| `ONLINE_REQUEST_TIMEOUT_S` | `3600` | per-request HTTP timeout |
| `ONLINE_HEALTH_TIMEOUT_S` | `1800` | max wait for `vllm serve` startup |
| `ONLINE_MAX_CONNECTIONS` | `512` | httpx pool cap (≥ stage's ~3·batch_size in-flight) |

## Unchanged / confirmed no work

- Retry-on-failure semantics (`prediction.py`), `retry_validate.py`.
- DB / `JSONLWriter` / StageWeaver / the shm pool.
- `main.py`'s `model_init()` / `model_term()` (process still spawned/joined identically).

## Deferred (not blocking)

- Guided decoding / structured output via `extra_body`.
- Image loading parity (`cv2.imread` vs vLLM's PIL + white-background RGBA compositing) — see
  Divergence 3 in `docs/vllm_serve_offline_parity.md`. Explicitly out of scope for now.
- Further `vllm serve` flag tuning beyond what the model yaml already carries.
- Thinking-token counting — not implemented; nothing currently sets `enable_thinking=True` in
  production, so it wasn't worth the extra machinery (see the 2026-07-28 addendum below). Revisit
  once thinking is actually in use.
- Raw-prompt deprecation warning on the offline/async backend (`input_processor.py:282`) — see the
  2026-07-28 addendum below. Investigated, not fixed.

Resolved since the original list above: `repetition_penalty` forwarding and `usage` → token-count
metrics — see the 2026-07-28 addendum below.

## Addendum (2026-07-27): `use_async` removed, `use_shm` now a real threaded arg

Small follow-up cleanup, orthogonal to the online-serving feature above but touching the same
files:

- **`use_async` deleted** from `vlm_service.py`. It had already stopped selecting the worker once
  `backend` was introduced (see above) and was kept only as a legacy note — now removed, since
  nothing read it.
- **`use_shm` is no longer a hardcoded module constant** in `timed_worker.py`. It's threaded exactly
  like `backend`: `args.use_shm` (default `False`) → `model_init()` → `VLLMService(use_shm=...)`,
  and `cli()` → `VLMPrediction(use_shm=...)`. `retry_validate.stage()` / `collect()` /
  `drain_available()` / `_decode_response()` all take `use_shm` as an explicit parameter instead of
  importing the old global, so `async_worker.py` / `timed_worker.py` now read `self.use_shm` off
  the `VLLMService` instance they already close over.
- **The shm block is now only allocated when `use_shm=True`.** Previously every example's
  `main.py` called `Shm(create=True, ...)` unconditionally in `__main__`, and both
  `VLLMService.run()` and `VLMPrediction.__init__` unconditionally reconnected
  (`Shm(create=False, ...)`) — even on the `use_shm=False` default path above, where the pool was
  never actually read from or written to. Now `main.py` skips creating the shared-memory segment
  entirely when `args.use_shm` is `False`, and `self.shm` stays `None` in both classes.
  `shm_name`/`free_slots` are still passed down unconditionally (cheap: a name string + an empty
  `mp.Queue`), so the call shape is unchanged either way.
- Default behavior is unchanged: `use_shm=False` everywhere, same as the old hardcoded constant.

## Addendum (2026-07-28): generation_config parity + sampling-param overlay + token metrics

Two follow-ups, both prompted by `docs/vllm_serve_offline_parity.md` (an investigation doc — see
that file for the full root-cause analysis; this section only records what was actually
implemented and where it deviates from that doc's original suggestions). Divergence 3 (image
loading, `cv2.imread` vs vLLM's PIL pipeline) is explicitly **not** part of this — still deferred.

### A. Divergence 1 + 2 — scheduler defaults and generation_config.json merge

**Divergence 1 (`async_worker.py`).** `AsyncLLM.from_engine_args()` was defaulting `usage_context`
to `ENGINE_CONTEXT`, which isn't a key in vLLM's scheduler-defaults table and silently fell through
to `max_num_batched_tokens=2048` / `max_num_seqs=128` — far below what `vllm serve` picks
(`OPENAI_API_SERVER` → `8192` / `1024` on this hardware class). Now passes
`usage_context=UsageContext.OPENAI_API_SERVER` explicitly, so the offline engine schedules batches
exactly like `vllm serve` does. This matters for output *quality*, not just throughput — vLLM's
kernels are not batch-invariant, so how many tokens/sequences get co-batched changes the
floating-point reduction order.

**Divergence 2 (`vllm_config.py::get_sampling_params()`).** Previously hardcoded
`temperature=<yaml value or 0.2>`, `max_tokens=<yaml value or 4096>`, `repetition_penalty=<yaml
value or 1>` — meaning any field not in the yaml silently fell back to a leftover constant from an
old bakeoff script's argparse defaults, not to the model's own `generation_config.json` the way
`vllm serve`'s HTTP layer does per-field. `get_sampling_params()` now:

1. Loads `GenerationConfig.from_pretrained(model_name).to_diff_dict()` and keeps
   `repetition_penalty` / `temperature` / `top_k` / `top_p` / `min_p` / `max_new_tokens` (mapped to
   `max_tokens`) — the exact allow-list `ModelConfig.get_diff_sampling_param()` uses server-side.
2. Layers yaml overrides (`sampling_temperature`, `sampling_max_tokens`, top-level
   `stop_token_ids`/`repetition_penalty`) on top of that, only for fields actually present in the
   yaml.
3. Leaves anything still unset as an **explicit `max_tokens=None`**, not an omitted kwarg —
   `SamplingParams`'s own dataclass default for `max_tokens` is `16`, not `None`, so omitting it
   would have silently capped every response at 16 tokens. Explicit `None` makes vLLM's
   `InputProcessor` (`v1/engine/input_processor.py`, shared by `vllm serve` and every offline
   engine) fill it as `max_model_len - prompt_len` at generation time — the same thing a real
   `vllm serve` client gets by never sending `max_tokens`.

Precedence, end to end: **explicit yaml value > generation_config.json > vLLM neutral default.**
This is model-agnostic — any future model automatically gets `vllm serve` parity without a code
change, not just Gemma 4.

Small adjacent fix in `get_engine_args()`: it used to do `engine_args.update(model_specific_config
["engine_args"])` wholesale, so `sampling_temperature`/`sampling_max_tokens` (consumed only by
`get_sampling_params()` above) would have leaked into `AsyncEngineArgs(**engine_args)` — a
`TypeError` offline, a bogus `--sampling-temperature` serve flag online. Latent, never actually hit
because no yaml set those keys yet, but now that `get_sampling_params()` actively reads them it was
worth closing — `get_engine_args()` explicitly skips them.

### B. Sampling-param override contract — `None`, not a full `SamplingParams`

`get_sampling_params()` on a task's `PromptAndValidation` (the thing users override in
`project_specific.py`) used to mean *"replace the entire sampling config with exactly this object"*
— so every task hardcoded every field (`temperature=0.2, max_tokens=4096, stop_token_ids=[],
repetition_penalty=1, ...`), even fields it didn't actually care about, permanently opting that task
out of the generation_config merge above.

New contract (`prediction.py::_base_sampling_params()`), backward compatible:

| Return value | Behavior |
|---|---|
| `None` (new default) | Use `VLLMConfig.get_sampling_params()` — the generation_config-merged base — untouched. |
| `dict` (new) | Overlay only these keys onto the base; every other field still resolves from generation_config.json. |
| `SamplingParams` (legacy) | Full replacement, exactly like before — kept so existing tasks that deliberately want every field pinned (`chandra_testing`, `archive/raghu_layout` — both have genuinely tuned, non-default values) don't need to change. |

Applied the `None` (or `{"structured_outputs": ...}` when set) pattern to `gemma_testing`,
`vllm_testing`, and the in-package template `src/vision_ingest/project_specific.py`. Left
`chandra_testing`/`archive/*` alone — deliberately-tuned or genuinely archived, not the leftover
`0.2`/`4096` pattern.

**`online_worker.py::_build_chat_payload`** was also only ever forwarding `temperature` (fallback
`0.2`) and `max_tokens` (fallback `4096`) to the HTTP request — `top_p`/`top_k`/`repetition_penalty`
were silently dropped, which meant `prediction.py`'s per-retry `repetition_penalty` bump never
actually reached the online backend. Now forwards `temperature`/`top_p`/`top_k`/
`repetition_penalty`/`max_tokens` field-by-field, **omitting** anything still `None` rather than
inventing a number — since `sp` is already generation_config-merged by the time it gets here,
sending the resolved values reproduces exactly what the server would have filled in on its own,
while still carrying real overrides (e.g. the retry bump) through.

### C. Token/output metrics — `post_process_full_vllm_object` implemented

`retry_validate.py::post_process_full_vllm_object()` was a `TODO`/`return None` stub since v1.5.
Now extracts a backend-uniform dict per completed request:

```python
{"prompt_tokens": int|None, "completion_tokens": int|None, "mm_tokens": dict|None,
 "finish_reason": str|None, "stop_reason": ...}
```

- **Offline** (`async`/`batch`, real vLLM `RequestOutput`): `prompt_tokens`/`completion_tokens`
  counted directly off `prompt_token_ids`/`outputs[0].token_ids`; `finish_reason`/`stop_reason` off
  `outputs[0]`. `mm_tokens` is `None` — offline `RequestOutput` in this vLLM version has no
  multimodal token breakdown field.
- **Online**: distinguished from offline by duck-typing on `.usage`, which only online's response
  shim carries. `online_worker.py`'s `_OnlineOutput`/`_OnlineCompletion` were previously discarding
  everything except `choices[0].message.content` — now also carry `finish_reason`, `stop_reason`,
  and the response's `usage` object verbatim. `usage.prompt_tokens_details.multimodal_tokens` gives
  a real per-modality mm-token breakdown for free (the server already counted it — no re-derivation
  needed), something offline can't currently provide.
- Wrapped in `try/except Exception: return None` — this only feeds diagnostics, and
  `prediction._validate_one()` would otherwise turn a metrics-extraction bug into a false retry of
  an already-successful generation.

`prediction.py::_classify()` also stamps `attempts` (retries consumed before this success) onto the
dict — previously tracked internally (`rec["attempts"]`) but thrown away once a request succeeded.

**Aggregation** (`pipeline_metrics.py`): new `record_tokens(full_vlm_obj)`, called once per
successful item from `cli_utils.py`'s `process_iteration()` (same spot as the existing
`record_inference()` call). Accumulates prompt/completion token lists, per-modality mm-token
sums/counts, a `finish_reason` histogram (so truncation — `finish_reason == "length"` — is visible
in checkpoint logs, not silent), and retry counts. `get_summary()` gained a `token_metrics` block
(`avg_prompt_tokens`, `avg_completion_tokens`, `avg_mm_tokens_by_modality`, `finish_reason_counts`,
`avg_retries_per_success`); no changes needed in `main_logger.py` — it already unpacks the whole
summary dict into the checkpoint log.

**Explicitly out of scope:** cached-token ratio and per-request latency (both available but judged
not worth the added surface right now) and thinking-token counts (would need either an opt-in
`--reasoning-parser` serve flag with no offline equivalent, or manual delimiter-splitting on the raw
text + re-tokenizing — skipped since nothing sets `enable_thinking=True` in production yet).

## Investigated, not fixed (2026-07-28): raw-prompt deprecation warning on the offline/async backend

Symptom, seen only with `backend="async"`:

```
WARNING 07-28 07:31:24 [input_processor.py:282] Passing raw prompts to InputProcessor is
deprecated and will be removed in v0.18. You should instead pass the outputs of
Renderer.render_cmpl() or Renderer.render_chat().
```

**Root cause.** `InputProcessor.process_inputs()`
(`vllm/v1/engine/input_processor.py:242-294`, vLLM 0.25.1) branches on whether the prompt it's
handed is already a rendered `EngineInput` — detected by `isinstance(prompt, dict) and "type" in
prompt` (line 269). If yes, it schedules directly. If no (line 281), it logs the warning and falls
through to the legacy `input_preprocessor.preprocess(prompt, ...)` path (line 291) — still correct,
but the path vLLM has said it will delete in v0.18.

Our `async_worker.py:102` calls `engine.generate(req.prompt, req.sampling_params, req_id)`, and
`req.prompt` is the plain `TextPrompt`-shaped dict built in `vllm_config.py:228-231`
(`{"prompt": text_prompt, "multi_modal_data": {"image": [...]}}` for multimodal, `{"prompt":
text_prompt}` for text-only) — no `"type"` key, so every single call hits the warning branch.

**Why `"online"` never shows it.** `vllm serve`'s chat-completions handler renders the incoming
JSON through its own `Renderer.render_chat()` (`vllm/entrypoints/openai/chat_completion/
serving.py:231`) *before* calling `engine_client.generate(...)` — same underlying
`AsyncLLM.generate()` → `process_inputs()` code as offline, but always with the `"type"`-keyed
dict, so it always takes the non-warning branch. This is a difference in what each backend hands to
`generate()`, not a different code path inside vLLM.

**Fix sketch (not applied).** Construct a `Renderer` off the same `AsyncLLM`/tokenizer we already
build in `async_worker.py`, and call `renderer.render_cmpl([{"prompt": text_prompt,
"multi_modal_data": {...}}])` (or `render_chat(...)`) to get back an `EngineInput` dict, then pass
*that* to `engine.generate()` instead of the raw dict built in `vllm_config.py:228-231`.
`AsyncLLM.generate()`'s signature already accepts `EngineInput` directly, so no call-site change is
needed beyond swapping what gets built before it.

**Why deferred.** Purely cosmetic today — the legacy path still processes requests correctly, and
nothing in our stack depends on `EngineInput`-specific behavior. Revisit before upgrading to vLLM
v0.18, where the raw-prompt path is slated for removal.
